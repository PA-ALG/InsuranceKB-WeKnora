# G3.5 原生准入同名误拒修复与正文职责核验

适用 G35-R2/R3；root 唯一写者。源码基线 `4ecabb717d2d5d51ab73a89370fdf175987c01f6`。本切片没有新增模型调用、构建、部署或业务写入。验证身份和计数见同名 JSON；源码与结果文档独立复核0 BLOCKER；机械记录RED豁免已确认。

## 先确认实际缺口

`native_admission.render_native_admission_context` 已将整个绑定窗口的原文放入 `source_options`，没有按单个候选的 `source_chunks` 缩成短提纲。正文可以生成完整 `body`；候选描述只是限定发现对象，不能当作原文事实。

已保存的旧真实准入输入包含18块、6123字符（含重叠），13候选的details长41—107字符；输出为1 REFERENCE、2 REQUIRES_ENTITY_RESOLUTION、10 REJECT、0正文。拒绝理由包含“通用标准条款不沉淀”和把健康告知字段等同如实告知后果。对应提示词修复在cb69已实现但未部署。这个旧运行没有证明现有模块缺乏完整正文生成能力；也不能与修复解析后DeepSeek原生20知识页做同输入、同模型因果对照。

另有已知R6缺口：当前pipeline在任何未决/实体解析项出现时隔离整个自由知识组，虽保留raw，业务输出仍可归零。增加正文调用不能修复此问题。

独立设计复核结论：先验证exhaustive＋保险Purpose v2＋修订准入；只有确认原生完整草稿有稳定额外收益后才接WikiPageModify。当前不新增逐候选生成阶段。需观察16384输出token预算下的实际终止原因和语义完整性，尚无证据认定发生截断。

## 本次修复

`retain()` 原先仅凭title、canonical_key或aliases与Schema字段短标题/field_key同名，就抛错拒绝整个准入响应。这与“同名字段实例不等于同义概念”的现有合同冲突；没有证据证明它触发了旧真实零产出，不能把本次修复写成历史样本根因已全部解决。

先在既有Spec冻结窄场景，再用页面标题、概念标题、概念名和别名四种碰撞建立RED：4例均在旧名称硬拒绝处失败。最小修复删除该名称判定，完整Schema描述和成员正文继续交给现有语义准入及独立审核。没有引入新字段、评分捷径或发布入口。

## 验证与限制

- 同名不同义内容可经过投影、字段合并和独立审核上下文；原字段结果逐值不变。
- 原生响应注入fields仍拒绝；候选没有chunk关联时仍可用绑定窗口内的真实引文；窗口外引用和错误offset/quote仍拒绝。
- 将已存在字段值换标题作为文章，给定独立审核REJECT/NEEDS_HUMAN时，仍不能组合为通过审核；准确绑定最终内容和来源标志。该测试验证审核处置执行，不证明真实模型必然判对语义。
- 本次最终身份对应25项准入/StageCall回归与17项审核回归通过，共42项；ruff及生产源码mypy通过。加强审核测试时误选空字段值导致8个夹具构造失败，选取非空字段值后受影响17项全部通过。无产品实现因此被放宽。
