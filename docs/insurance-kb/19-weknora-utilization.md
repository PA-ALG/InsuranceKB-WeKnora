# 19 · WeKnora 能力利用清单（对早期调研结论的复核与修订）

> 回应"是不是很多能力没用上"的疑问（2026-07-13）。结论：**平台性能力全量/重度使用，仅"语义生成"一层被有意替换**——这正是早期调研（《WeKnora 企业级知识库能力评估》）推荐的建设方式："WeKnora 负责知识的处理和运行，企业治理平台负责知识的认证和管理"，harness 即那个治理层。

## 1. 利用率盘点

| 层 | 能力 | 状态 |
|---|---|---|
| 运行底座 | 多租户/RBAC/API Key 能力域/审计/REST/模型接入/部署(compose/helm)/Langfuse | ✅ 全量使用（自建成本最高的部分） |
| 处理与服务 | docreader 解析/OCR/切片、向量/BM25/混合检索（兜底轨）、Wiki 载体（存储/渲染/互链/目录/lint/阅读界面）、Agent/RAG、MCP client、IM/网页嵌入入口 | ✅ 重度使用 |
| 语义生成 | 内置 wiki 生成管线、自动 QA 生成、GraphRAG | ❌ 有意关闭（由 harness 替代；GraphRAG P2 重估）——见 02 §10 |
| 待启用 | 数据源同步 connectors、检索问答评估、小程序 | 📋 M2+ 接入期 |

反事实：无 WeKnora 则解析服务/检索栈/权限体系/wiki 界面/Agent 框架/IM 集成需自建或另选型（同样面临治理缺口），harness 工作量是其零头。**选型结论维持。**

**实证补强（2026-07-16，同事独立部署反馈《llm_wiki_WeKnora_problem.docx》，含内部数据截图故不入库、仅存档引用）**：另一团队把 24 份保险文档直接灌 WeKnora **原生 wiki ingest**（即上表有意关闭的"语义生成"层），实测复现了弃用该层的全部理由——172 个页面全部无审核态直接 published、13 条 `wiki:ingest` 死信（concurrent wiki task active）对人不可见、`wiki_page_issues` 恒为 0（问题不进队列）、"责任免除/现金价值/犹豫期"等概念页聚合 12 个产品来源（混源，不可作产品事实）、同一产品/公司多 slug 重复实体、费率表 chunk 化后行列维度丢失。其建议的改造方向（产品身份一级对象/字段级 schema 编译/字段状态流转/冲突 review 队列/表格结构化/回归评测集）与本仓 003/004/006/007/019 已交付能力及 009/011 规格逐项对应；新增吸收两条：**011 H1.7**（任务可靠性进健康报告）、**009 C3.4**（概念页混源防护）。

## 2. 早期调研结论的修订记录

| 原结论 | 修订（2026-07-13） |
|---|---|
| 自动 Wiki 可直接复用 | 拆两半：载体复用、生成管线弃用（02 §10） |
| 知识图谱可复用 | 初期关闭，P2 按 Claim 规模重估 |
| 高风险分级/正式口径分离"完全不具备" | 已在 harness 实现（risk_level 审核门禁；权威序六级 + data_quality 四级） |
| 产品/条款版本管理"完全不具备" | 核心已实现（003 主数据 + 007 版本快照 + 013 as_of_date）；保单维度待业务数据 |
| 评估能力可复用 | WeKnora 评估面向检索问答；字段级金标评估自建（002/005），互补不重叠 |

仍然成立的判断：知识服务网关（013 MCP + API Key 部分覆盖，完整网关 M3+）、规则引擎独立建设（P2，业务方 2026-07-12 拍板不提前）、"不大幅修改 WeKnora 而在其上建治理层"（= ADR-001）。
