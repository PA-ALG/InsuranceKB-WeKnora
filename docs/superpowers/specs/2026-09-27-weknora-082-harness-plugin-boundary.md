# WeKnora 0.8.2 升级与 Harness 插件边界

日期：2026-09-27。

状态：用户已确认优先升级，并要求 Harness 插件化、降低与原版耦合；本文形成该方向的设计草案与实施边界。尚未完成升级、接口迁移或运行验收，不把设计写成已实现能力。

Owner：当前总体规划任务负责范围与设计；功能实施由后续明确的唯一执行 Owner 承接。本工作树只写此设计，不修改产品功能或运行环境。

## 1. 用户价值与顺序

让产品持续获得上游能力与修复，并使后续升级主要影响明确的适配边界。当前顺序为：G3/G3.5 已集成 → 0.8.2 升级及必要边界收敛 → G4。升级属于工程交付，不新增业务 Goal，也不抹除 G3.5 的 QUALITY_PARTIAL、未验证项和 Q0 责任。

“插件”在这里指独立部署、可配置接入、协议边界稳定的领域扩展；不预设上游已有满足需求的动态插件 SDK，不以目录改名代表解耦。继续保留 Python Harness，Go 只负责平台能力。无需新建插件市场、通用加载器、消息系统或一套知识平台。

遵循 [AGENTS.md](../../../AGENTS.md) 的核心工程原则和 [工程质量与执行效率基线](../../insurance-kb/28-development-execution-charter-830.md#engineering-quality-baseline)。唯一 serving authority 沿用 [现有 ADR](2026-07-29-weknora-sole-serving-active-release-authority-adr.md) 与 [Amendment 2](2026-07-29-enterprise-llm-wiki-authority-amendment-2.md)。

## 3. 目标边界与取舍

| 位置 | 负责 | 不承担 |
|---|---|---|
| WeKnora 原生平台 | 上传、解析、原件、权限、检索、Wiki 载体与可复用发现算法 | 寿险字段定义、产品采信规则、领域冲突裁决 |
| WeKnora 侧集中适配与必要平台扩展 | 安全暴露解析快照/原生操作，校验版本化请求；承载唯一原子 Release、同版读取；业务 UI 的有限注册入口 | 另一份编译流程、领域规则、独立审核决策、第二个任务编排器 |
| Python Harness 领域插件 | Schema、实体与语义准入、证据审查、Candidate/ChangeSet、审核策略和发布授权，后续 G4 增量裁决 | 直接访问 WeKnora 表、内部队列或可变运行时对象；另建 serving Head |
| Harness 侧 WeKnora adapter | 平台协议与领域输入/输出的显式转换，平台版本差异、错误和能力兼容检查 | 把 WeKnora ORM/API DTO 泄漏进领域模块，或用兼容层维持已替换的内部实现 |
| 现有业务 UI 模块 | 字段页、自由知识、来源、任务和审核的业务展示 | 为每次上游布局变化重写领域能力，或另造一套前端平台 |

采用独立服务插件 + 集中适配 + 有界平台补丁。纯用当前上游公开 API 的方案尚未证明能满足整版发布、pinned read 和证据合同；把 Harness 改为 Go 进程内插件又会增加编译及运行耦合，均不作为当前目标。

deep modules 的复杂性留在其负责模块内部。协议 adapter 可以薄；它后面的平台 Release 模块负责发布完整性与权限，领域编译模块负责语义不变量。不得为了“集中”把不同事务和权威合成一个万能模块。

## 4. 只收敛四组必要接缝

以下是职责分组，不要求新建四套 API 或四个服务。先定位当前调用方、复用已有版本化入口，确有缺口再修改所属 OpenSpec。

1. **来源与生命周期**：按 tenant/Space/principal 读取不可变 SourceRevision、解析快照和精确定位；创建、替换、撤回沿既有 lifecycle/Outbox 协议投递。接收方按来源版本和事件身份幂等处理，重试、重放和乱序不能丢掉撤回或覆盖新版本。进程内 event bus 不能直接替代此合同。
2. **原生知识操作**：复用 G3.5 的发现/引用等操作接口。平台返回候选与证据引用，Harness 负责准入并沿原 StageCall 保存请求、响应和调用结果；该接缝不得隐式再启动完整原生发布。重试与续写需沿既有唯一 Owner 和预算记账，不能叠加无记录调用。
3. **发布与读取**：Harness 提交不可变 Candidate 与合法授权，平台验证并完成 preparation、原子 activation、receipt、current/pinned read。保留已有通用 Release 能力和当前 ACL；不退化为连续 PUT 多个页面，也不向 Harness 暴露第二个 active pointer。
4. **业务入口与状态**：继续用集中 bridge 暴露上传意图、任务状态、审核和页面入口；复用现有前端组件，将少量路由/菜单挂载点集中。当前未证明原生 UI 动态插件能力，不引入微前端或远程脚本加载平台。

协议显式标识版本、scope、来源/候选身份、幂等键和可分类错误；大正文使用已授权的不可变引用或有界按需读取。实现版本升级本身不使业务依赖失效；模型/提示词/解析语义真正变化时，不得强复用旧输出。

能力与支持版本放进现有配置/握手机制即可。缺少必要能力时，只阻断受影响的编译或发布并给出明确原因，不能静默切到普通 Wiki 直写；不建立独立能力注册中心。

## 5. 原版补丁的管理方式

本次先对实际升级接缝内的差异归类，不开展全仓历史清理：

- 原版已覆盖的通用能力：验证行为后删除本地重复实现，保留相应回归。
- 领域语义：收回 Harness，避免在原版 service/router 内扩散；不能为此破坏已经确认的跨语言验证合同。
- 协议、权限和来源转换：集中到适配边界，核心对象不穿透。
- 唯一 Release、不可变来源等原版尚未提供的必要平台能力：保留少量、集中、可说明的补丁；优先通用化为可向上游贡献的扩展点。

对保留的原版核心修改，用现有设计/任务记录写明路径、理由、测试、上游替代条件和 Owner。必要对外兼容有明确支持范围与退出条件；不长期维护两个内部执行路径。不能承诺以后升级零冲突，但应能够说明每个接触原版核心的原因。

禁用 Harness 后，普通非托管知识库保持原生行为；已由 Release 管理的内容仍受保护，不能因插件离线或关闭而恢复普通直写。插件故障时，平台继续提供仍合法有效的已发布快照，新编译/发布可见失败，不能悄悄降级绕过审核。来源撤回和当前 ACL 继续生效。

## 6. 实施顺序：沿真实链路逐步收敛

**阶段 A：最小兼容设计。** 已完成源码差异和模拟合并。继续明确模型配置/凭据引用的迁移、数据库迁移及回滚、旧解析快照/定位的读取兼容。原生模型重构应迁入其新扩展点，不恢复被删的旧整套模型模块。不要求先完成所有未来插件能力。

**阶段 B：一条可保留的 tracer bullet。** 从产品集成基线隔离适配到固定 v0.8.2，选择 G3.5 已有代表材料和解析制品，贯通共享来源 → 原生发现操作 → Harness 准入 → 原审核/发布 → 网页原文定位。保留现有环境和数据；优先复用历史响应验证协议，只在真正依赖变化或真实验收需要时新增受控调用。不手工造业务结果。

**阶段 C：集中收敛被该链路实际触及的耦合。** 在上述接缝内消除重复编排、私有调用和直接业务侵入，不增加 G4 功能，不整仓重构。检查模型重构、材料删除、恢复、普通 KB 与托管 Wiki 的行为隔离。

**阶段 D：交付与 G4 交接。** 按影响组件集中构建，验证迁移/回滚和关键业务链；保留旧制品/数据恢复点。源码升级不要求重解析历史原件，旧解析快照不可原地覆盖。不能未经实际依赖分析就声称关闭 AnyDoc 可同时省掉 BrowserSkill。无关新能力不默认启用，但也不为删光上游代码形成更大的长期分叉。

后续 G4 消费相同领域协议和平台接口，避免继续把冲突、版本、采信规则嵌入原生核心。

## 7. 验收约束

| ID | 可核验结果 |
|---|---|
| UPG-01 升级身份 | 固定上游版本、产品提交、组件制品与实际部署身份；构建成功不代替业务成功 |
| UPG-02 平台边界 | 同一 Harness 构建在已声明兼容的旧/新平台协议上通过必要契约检查；差异封装在 adapter；并不承诺永久双版本支持 |
| UPG-03 领域独立 | 代表性 Schema/准入规则改动只影响 Harness 的适用模块，不要求修改或重建 WeKnora Go 应用；新增协议能力按实际影响另评估 |
| UPG-04 业务连续 | 既有 FieldAssertion、自由知识、模型生成标识、正式关系、来源、历史快照在新平台可读；一条真实链路正常审核发布与 source click |
| UPG-05 恢复与成本 | 历史成功结果保留；重复提交/进程重启不无故重解析或重发成功调用；新发、复用、未知结果分别记账；上游续写/重试纳入同一预算 |
| UPG-06 隔离与故障 | 普通 KB、托管 Wiki 行为正确；插件关闭/离线不开放旁路写；租户/Space/当前 ACL、源撤回和失败关闭保持 |
| UPG-07 迁移与回滚 | 核实迁移真实变化与数据兼容；区分应用回滚和数据库恢复，不能只凭保留旧镜像声称可回滚 |
| UPG-08 构建范围 | Python、Go、前端按真实依赖独立交付；历史材料浏览/普通配置不触发编译；记录冷/暖构建实际成本，不预先许诺分钟数 |
| UPG-09 核心修改可解释 | 每处保留的上游核心补丁有必要性与回归证据；内部已替代实现删除，不以文件数或接口层数冒充低耦合 |

上述为升级验收草案，进入功能实施时在适用 OpenSpec 冻结映射。复用 G3.5 的有效证据，只重验升级影响、实际失败和尚未覆盖风险，不重开逐样本质量调参。
