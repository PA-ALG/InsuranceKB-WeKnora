# S12c-1b · 编译器升级的变更判定

> 状态：Claude 2026-10-28 提出 ｜ 作者：Claude Code
> 依据：
> - #390 消融结论：取值协议 v2 明显减少"混入其他字段"和"写错"；
> - S12c-1（#394）已合并：编译输出记录了 `value_protocol`。
> - 发现的问题：在材料没有变化时，`changes/decision.py::_verdict` 会做如下判定：
>   - 线上已有值、新编译值不同 → KEEP；
>   - 新编译值为 unknown → KEEP。
>
>   这条规则是 S8 的防抖设计，目的是不让模型的随机差异来回改线上值。但它也挡住了编译器升级：线上重编译后几乎没有变化，v2 的改进到不了线上。
> - claim 的 `provenance.compiler_version` 目前只有字段卡版本，判定时无法区分"编译器升级"和"同一编译器的随机差异"。
>
> 实现方：Claude ｜ 审核方：Codex ｜ 真实调用：0 ｜ 不改 `contracts/`（两个字段本来就是自由字符串）

## 1. 编译器身份

`claims_from` 写入 claim 的 `provenance.compiler_version` 时，按以下规则取值：
- **一般情况**：字段卡版本 + 取值协议版本，格式为 `"<cards_version>+value:<value_protocol>"`。
- **编译输出没有 `value_protocol`**（S12c-1 之前的输出）：保持原样，只写字段卡版本。这样已有输出发布出去的内容与过去逐字节一致。
- **对外接口**：新增 `compiler_version(output: CompileOutput) -> str`（`compilers/schema_fields/claims.py`）。缺少字段卡版本时，仍按原规则报 `CARDS_VERSION_UNKNOWN`。

发布报告里的 `cards_version`、候选包的 `compiler_identity` 不变。

## 2. 新判定 `UPGRADE`

在 `_verdict` 中，`SUPERSEDE`（材料撤回）之后、两条 KEEP 之前，增加一条规则。同时满足以下条件时判为 `UPGRADE`：
- 线上值存在，且没有 `expert_lock`；
- 新旧不等价；
- 线上值不是 unknown（是 unknown 时仍按 FILL 处理）；
- 本条 claim 的材料没有撤回，也没有引用新材料；
- 线上值与新值的编译器身份 `(provenance.compiler, provenance.compiler_version)` 不同。

新值是 present 还是 unknown 都适用。新值为 unknown，表示新协议认为材料里没有这一项，是否采纳交给审核决定。

以下情况不变：
- **编译器身份相同**：仍按原规则判 KEEP（新值 unknown，或没有新材料）或 CONFLICT（有新材料），防抖保留。
- **专家锁定**：仍判 CONFLICT，不会被编译器升级覆盖。
- **其他情况**：撤回判 SUPERSEDE 或 RETRACT，补全判 FILL，新增判 ADD，等价判 UNCHANGED 或 REFRESH，各自不变。

`UPGRADE` 与 `SUPERSEDE` 的处理方式相同：
- 进入候选包的成员，`maintenance.revision_no + 1`，`maintenance.reason = "upgrade"`；
- 照常进入审核路由：所属险种还没有通过准入时，进入人工或模型评审队列，不会自动上线。

发布报告的 `counts` 自动增加 `upgrade` 一项。

## 3. 安全性

- **每条 UPGRADE 都要过审核**：线上值是审核通过后上线的，换成新编译器写的值，同样要经过一次审核。
- **回退靠审核**：旧协议无法重新运行，所以审核是唯一的把关。评委拒绝的点不会上线，线上保持旧值。
- **新值为 unknown 的 UPGRADE 一律走人工**（#397 审核 R1）。这种升级等于删除一条已发布的事实，而独立审核的提示词只判断 present、absent_explicitly 的值是否被引文支持，判断不了"删除"对不对。因此：
  - 本次发布中只要有新值为 unknown 的 UPGRADE，路由就加上原因 `UPGRADE_TO_UNKNOWN`，整个产品进入人工或模型评审队列，即使分数文件里给了它分数也不例外；
  - 在打标规则里，maintenance.reason 为 `upgrade` 的 claim 一律算作"需要审核"（`_reviewed`）：走机器路由时必须有自己的分数。

  其他 unknown 维持 RV2a 的口径：不评分，也不阻塞。
- **防抖的范围**（#397 审核 R2，接受现行为）：一条 claim 在以新编译器身份首次发布之前，以后各轮只要编出不等价的值，仍会判为 UPGRADE；它可能先判为 UNCHANGED（等价，不发布），之后又判为 UPGRADE。每次 UPGRADE 都要经过审核。一旦这条 claim 以新身份发布，后续同身份的随机差异照常判为 KEEP。

## 5. 验收（RED）

`harness/tests/changes/test_compiler_upgrade.py`：
- **编译器身份的格式**：带协议、不带协议两种情况；字段卡版本为空时报错。
- **编译器身份不同、材料不变**：
  - present 改为不同的 present，判 UPGRADE，成员的修订号加一、reason 为 `upgrade`；
  - present 改为 unknown，判 UPGRADE。
- **编译器身份相同**：
  - 新值不同：判 KEEP，防抖保留；
  - 新值为 unknown：判 KEEP；
  - 引用新材料：判 CONFLICT。
- **编译器身份不同，但属于其他情况**：
  - 专家锁定：判 CONFLICT；
  - 材料撤回：判 SUPERSEDE；
  - 新编译里没有这一项、材料撤回：判 RETRACT；
  - 线上值为 unknown：判 FILL；
  - 新旧等价：判 UNCHANGED。
- **发布报告**：`summarize` 的计数中有 `upgrade`。
- **跨轮序列**（R2）：Active 为旧身份 A；新身份 B 先编出等价值，判 UNCHANGED；之后 B 编出不等价值，判 UPGRADE；以 B 发布后，B 的随机差异判 KEEP。

`harness/tests/changes/test_compiler_upgrade_routing.py`（R1）：
- **路由层**：新值为 unknown 的 UPGRADE 判 human，原因含 `UPGRADE_TO_UNKNOWN`，即使分数文件里有它且达到门槛也一样；present 的 UPGRADE 仍要求自己的分数；普通 unknown 仍不评分、不阻塞；机器打标时 upgrade 的 claim 必须有分数。
- **真实发布入口**（`publish_changes.main`，HTTP 用 fake）：已准入的险种中，一个 present 的 UPGRADE（0.99 分）加一个新值为 unknown 的 UPGRADE，结果为人工路由，不提交决定，也不激活。
