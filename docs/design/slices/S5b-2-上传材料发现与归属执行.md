## 1. 目标

S5b-1 只回答"这份材料属于谁"。本片让判定接入实际运行：

1. 找出 Space 的 RAW 库里新上传、已解析完成的材料；
2. 读取前两页文本，调用 `identity.attribution.attribute`；
3. 能自动归属的写进本 Space 的**产品登记**，其余进入待处理清单；
4. 报告本次受影响的产品，交给 S5b-4 编译发布。

**产品登记**取代目前每款产品一份、手写的来源映射，成为本 Space"哪些产品、各有哪些材料"的唯一记录。原有的编译与发布命令仍读来源映射：登记按需导出同一格式，不另存第二份。

## 2. 改动

### 2.1 产品登记 `ingest/registry.py`（本 Spec 冻结格式与接口）

文件格式 `product-registry.v1`，JSON，由运维指定路径（与现有来源映射一样放在仓库外）：

```json
{
  "contract": "product-registry.v1",
  "space_id": "s4-demo-1828",
  "raw_kb_id": "<RAW 知识库 id>",
  "products": {
    "<product_id>": {
      "names": ["<标准名>", "<已批准别名>…"],
      "clause_codes": ["<条款编号>…"],
      "schema_pack_id": "<知识包>",
      "origin": "seeded | created",
      "materials": [{"knowledge_id": "…", "parse_attempt": 1, "sha256": "<64 位十六进制>", "role": "terms", "file_name": "…"}]
    }
  },
  "pending": [{"knowledge_id": "…", "parse_attempt": 1, "sha256": "…", "file_name": "…", "attribution": {"…": "S5b-1 的 Attribution"}}],
  "decisions": [{"knowledge_id": "…", "parse_attempt": 1, "sha256": "…", "attribution": {"…": "…"}}]
}
```

- **校验**：严格模式，拒绝未知字段。`product_id` 与 `knowledge_id` 沿用来源映射的标识规则。以下情况都视为文件无效（`REGISTRY_INVALID`）：
  - 同一 `knowledge_id` 出现在两处（两个产品之间、产品与待处理之间）；
  - `names` 为空；
  - `role` 不在材料角色中。
- **`pending`**：待处理的材料，判定为 `NEEDS_CONFIRM` 或 `QUARANTINE`。
- **`decisions`**：只追加的判定记录，每次归属与重判都留一条，带 `policy_ref`，用于按规则版本审计与重判。
- **接口**：
  - `load_registry(path) -> ProductRegistry`；
  - `save_registry(registry, path)`：写同目录临时文件后 `os.replace`，失败时原文件不变；
  - `registry.registered() -> list[RegisteredProduct]`：交给 S5b-1 判定；
  - `registry.source_map() -> SourceMap`：导出与现有来源映射相同的格式与校验，产品按编号排序，材料按 `knowledge_id` 排序；
  - `registry.facts(product_id) -> ProductFacts`：标准名与知识包，供 S5b-4 替代数据集文件夹。

### 2.2 读取 RAW 库 `ingest/raw_sources.py`

- `RawSources(base_url, api_key, transport=None).completed(raw_kb_id) -> list[RawSource]`：
  - 调用 WeKnora 原生 `GET /api/v1/knowledge-bases/:id/knowledge`，分页读完；
  - 只返回 `parse_status == "completed"` 的条目，含 `knowledge_id`、`current_parse_attempt`、`file_name`、`file_sha256`；
  - 列表总数与实际条目不符、字段缺失或 SHA 不是 64 位十六进制时，整次失败（`RAW_LISTING_INVALID`），不按部分结果归属；
  - HTTP 写法与 `evidence.weknora_pages` 相同（可注入传输层，错误只给代码）。
- 页文本复用 `WeKnoraSourcePages.pages(space_id, knowledge_id, attempt)`，`head` 取第 1、2 页文本按页序拼接。

### 2.3 执行 `ingest/uploads.py`

`attribute_uploads(registry, sources, pages, policy=None) -> UploadRun`：纯函数，不写文件；返回新登记与报告。

1. **候选**：`sources` 中 `knowledge_id` 不在登记材料里、也不在 `pending` 里的条目；加上 `pending` 中判定为 `QUARANTINE` 的条目（每次重判）。`NEEDS_CONFIRM` 的条目等人工处理（S5b-3），不重判。
2. **顺序**：
   - 候选按 `knowledge_id` 排序，逐个判定并立即应用；
   - 一轮中若登记有变化，就把本轮仍为 `QUARANTINE` 的候选再判一轮，直到没有变化；
   - 同一批上传的条款、说明书、费率表因此在一次运行中全部归属，与列表顺序无关。
3. **应用**：

| 结论 | 对登记的改动 |
|---|---|
| `DUPLICATE` | 不加入材料，只记 `decisions` |
| `SUPPLEMENT` | 材料加入该产品 |
| `NEW_VERSION` | 该产品去掉 `replaces` 中的旧条款，加入新条款，`clause_codes` 追加新编号 |
| `CREATE` | 新增产品：`names=[display_name]`、`clause_codes=[clause_code]`、`schema_pack_id`、`origin="created"`、材料为这份条款 |
| `NEEDS_CONFIRM`、`QUARANTINE` | 写入或更新 `pending`；已归属的条目移出 `pending` |

   每次判定都在 `decisions` 追加一条。
4. **报告** `UploadRun.report`：
   - 各结论的数量；
   - `affected_products`：本次有材料加入、替换或新建的产品，按编号排序；
   - 待处理条目数；
   - 页文本读取失败的条目：该条目本次不判定，下次重试，不写入登记。
5. **幂等**：对同一登记与同一列表重复运行，第二次不改变登记（除重判隔离条目时追加的 `decisions`；结论不变时不追加）。

### 2.4 初始登记 `seed`

用现有材料建立第一份登记：

- 来源：现有的若干份来源映射，数据集 `product_meta.json` 中的标准名（`clauseName`）与条款编号（`sccode`），知识包按现有 `declared_pack` 取得；
- 每份材料的 `file_name`、`sha256` 取自 RAW 库列表，`role` 用 `material_roles.role_of` 判定；
- 判不出角色、或来源映射中的材料不在 RAW 库已完成列表中时，整次失败（`SEED_INVALID`），不写文件；
- 产出与手写来源映射等价：`registry.source_map()` 与原来源映射合并后的内容相同。

### 2.5 命令

```text
python -m insurance_harness.ingest.uploads seed --registry PATH --space ID --raw-kb ID \
    --source-map PATH [--source-map PATH …] [--dry-run]
python -m insurance_harness.ingest.uploads run --registry PATH [--dry-run]
```

- 读取 `HARNESS_WEKNORA_BASE_URL`、`HARNESS_WEKNORA_API_KEY`。
- 输出 JSON 报告（只含编号、代码与数量，不含材料原文）。
- `--dry-run` 不写文件。
- 同一登记文件同时只允许一个运行：用同目录锁文件，拿不到锁立即失败（`REGISTRY_BUSY`）。

**不做**：
- 不编译、不发布（S5b-4）；
- 不做待确认页面（S5b-3）；
- 不改 Go 与前端；
- 已登记材料被删除或重新解析的处理，留到 S8 来源撤回；本片只在报告中列出，不改登记。

## 3. 验收（RED，Claude 编写，受保护）

`harness/tests/ingest/test_registry.py`、`test_uploads.py`。离线运行：用假的 RAW 列表与页读取器，材料开头文本复用 S5b-1 的样例（13 款产品、7 个险种）。

1. **格式**：
   - 能载入与保存，保存后再载入相同；
   - 未知字段、重复 `knowledge_id`、空 `names`、未知角色都被拒绝；
   - 保存时 `os.replace` 失败，原文件内容不变；
   - `source_map()` 通过现有 `SourceMap` 校验，顺序确定。
2. **补充**：已登记产品只有条款，上传其说明书 → 材料加入、`affected_products` 含该产品、`source_map()` 多一条。
3. **整批新产品**：一款未登记产品的条款、说明书、费率表同批上传，列表顺序正反两种，一次运行后都为一个新产品带三份材料，编号为 `sc-` 开头。
4. **先到的说明书**：
   - 只上传说明书 → 进 `pending`（`QUARANTINE`）；
   - 下次运行时条款也到了 → 条款新建，说明书归入，`pending` 清空。
5. **新版本**：已登记产品上传新编号条款 → 旧条款移出，新条款加入，`clause_codes` 追加，`decisions` 留记录。
6. **人工确认不重判**：`NEEDS_CONFIRM` 条目保留在 `pending`，下次运行不再判定、不追加记录。
7. **重复与跳过**：
   - 与已登记材料 SHA 相同 → 不加入，只记录；
   - 未解析完成的条目与已登记的条目不判定。
8. **幂等**：同一输入运行两次，第二次登记不变。
9. **读取失败**：某条页文本读取失败，该条不进登记也不进 `pending`，报告列出，其他条目照常。
10. **列表无效**：总数不符或 SHA 非法 → 整次失败，登记不变。
11. **初始登记**：
    - 用 3 款产品的来源映射与假列表建立登记，`source_map()` 与输入合并后一致；
    - 有材料判不出角色时失败。
12. **并发**：锁文件已被占用时 `run` 立即失败，登记不变。
13. **命令**：`--dry-run` 不写文件；报告不含材料原文。

**行为回归**：`harness/` 下 `uv run pytest`、`ruff`、`mypy` 照常通过。
