## 0. S5b 的拆分

上传后的完整链路是：发现新材料 → 判定归属 → 自动归属或进待确认 → 只编译、发布受影响的产品。拆成四片：

| 片 | 内容 | 组件 |
|---|---|---|
| **S5b-1（本片）** | 归属判定核心：给定一份材料与已登记产品，确定性地给出归属结论，无模型调用 | Harness `identity/` |
| S5b-2 | 发现与执行：轮询 RAW 库的新材料，读取页文本，调用判定；自动结论写入来源映射与产品登记，不确定的写入待确认 | Harness |
| S5b-3 | 企业知识页"待确认材料"：通用的待确认接口与页面，人工选"归到某产品 / 新建 / 替换 / 作为补充 / 忽略" | Go + 前端 |
| S5b-4 | 归属后自动编译、发布受影响的产品（会调用模型，需预算） | Harness |

## 1. 材料中的确定性依据（2026-10-24 用数据集 13 款产品、39 份材料核实）

- **条款**：前两页开头为"条款编号 + 产品名 + 阅读指引"，例如"平安人寿〔2025〕疾病保险174号平安安佑福（全能版）重大疾病保险阅读指引…"。条款编号即 `product_meta.json` 的 `sccode`，产品名即 `clauseName`。
- **说明书、费率表**：开头只有完整产品名，没有条款编号。说明书为"产品名 + 产品说明书"，费率表为"《产品名》…"或"产品名 + 费率表"。
- **产品代码**（`planCode`，如 1828）：不出现在任何材料中。
- **名称包含**：产品名可能是另一产品名的一部分。例如"平安盛世金越（尊享版26）终身寿险"同时出现在"…（分红型）"和"平安创享盛世金越…"中。在文本里搜已登记名称会出错：未登记的"…（分红型）"会被当成那款较短名称产品的新版本。所以先从标题取出完整产品名，再与登记的名称做精确比较。
- **前 300 字足够**：依据都在文本最开头（条款编号在第 0 字，产品名在第 0–22 字）。
- **知识包可推断**：去掉名称末尾的括号限定语后，按最长的险种词推断知识包。13 款产品的推断结果与 `dataset/product_packs.json` 和 Golden 清单的人工结论全部一致，覆盖 7 个险种。

## 2. 改动

### 2.1 判定策略（版本化数据）`identity/attribution_policy.json`

| 字段 | 含义 |
|---|---|
| `version`、`basis` | 版本与依据；改任何规则都要升版本 |
| `anchor_chars` | 只读规范化文本的前若干字（300） |
| `clause_code_pattern` | 条款编号的正则，形如"发文机构简称〔年份〕类别序号号"。发文机构简称在正则中逐一列出（目前为"平安人寿"），这样编号前的"条款编号："等标签不会被吞进编号；不认识的机构不算编号（审核 R3，2026-10-24 修正） |
| `title_brackets` | 标题括号（"《""》"）：标题以左括号开头时，产品名为括号内的文字 |
| `title_end_markers` | 产品名之后的结束标记（"阅读指引""条款""产品说明书""说明书""费率表""金额表"），取最先出现的一个 |
| `max_title_chars` | 产品名的最大长度（60）；超过视为取不出标题 |
| `created_id_prefix`、`created_id_hex` | 新产品编号 = 前缀 + 条款编号规范化后 SHA-256 的前若干位十六进制（`sc-` + 10 位） |
| `classifications` | 险种词 → 分类与知识包，例如 `{"suffix": "重大疾病保险", "classification": "critical_illness_insurance", "schema_pack_id": "schemapack_critical_illness_insurance"}`；分类必须在该知识包的 `applicable_classifications` 中；推断时先去掉名称末尾的括号限定语，再取末尾最长的匹配 |

### 2.2 判定接口 `identity/attribution.py`（本 Spec 冻结）

```python
class RegisteredMaterial(BaseModel):  # 已归属的材料
    knowledge_id: str; sha256: str; role: str
class RegisteredProduct(BaseModel):   # 已登记的产品
    product_id: str
    names: tuple[str, ...]            # 标准名在前，其后为已批准的别名
    clause_codes: tuple[str, ...]     # 已知的条款编号（各版本）
    schema_pack_id: str
    materials: tuple[RegisteredMaterial, ...]
class Upload(BaseModel):              # 一份新材料
    knowledge_id: str; file_name: str; sha256: str
    head: str                         # 前两页文本，按页序拼接
class Attribution(BaseModel):
    outcome: Literal["DUPLICATE", "SUPPLEMENT", "NEW_VERSION", "CREATE", "NEEDS_CONFIRM", "QUARANTINE"]
    reason: str                       # 见 §2.4
    product_id: str | None            # 归属或新建的产品
    role: str | None                  # material_roles 识别出的角色
    clause_code: str | None           # 材料中的条款编号（规范化后）
    display_name: str | None          # CREATE 时从条款标题取出的产品名（规范化后）
    schema_pack_id: str | None        # CREATE 时推断的知识包
    replaces: tuple[str, ...]         # NEW_VERSION 时被替换的旧条款 knowledge_id
    candidates: tuple[str, ...]       # NEEDS_CONFIRM 时可选的产品，按编号排序
    policy_ref: str                   # attribution-policy@<version>

class AttributionInputError(ValueError):  # code 为 "REGISTRY_DUPLICATE_PRODUCT"
    ...

def load_attribution_policy() -> AttributionPolicy: ...
def attribute(upload: Upload, registry: Sequence[RegisteredProduct],
              policy: AttributionPolicy | None = None) -> Attribution: ...
```

- 纯函数：不读文件系统以外的状态，不发网络请求，不调用模型。结果与登记顺序无关。
- 登记中的 `product_id` 必须唯一。出现重复（不论定义是否相同）时抛 `AttributionInputError("REGISTRY_DUPLICATE_PRODUCT")`，不按顺序挑一个，也不合并（审核 R4）。
- 文本按 NFKC 规范化并去掉空白后比较，与 `material_roles` 相同；条款编号与名称都按此规范化。
- 角色复用 `material_roles.role_of(file_name, head)`，不另立规则。

### 2.3 判定顺序

1. **重复**：材料的 `sha256` 已在登记中 → `DUPLICATE`，归属该材料所在的产品。
2. **无文字**：规范化后的窗口为空 → `QUARANTINE / text_unavailable`。
3. **找依据**（只看窗口内）：
   - **条款编号**：第一个匹配 `clause_code_pattern` 的片段；登记中有该编号的产品记为编号命中。
     - 只有位于窗口开头（第 0 字）的编号才是**本材料自己的编号**：条款以它开头，后面紧跟标题；
     - 其他位置的编号只是**引用**（如标签"备案编号："之后，或正文"请参见…"），只能用来核对已有产品（仍须名称一致，第 4 步），不能用来新建产品或判定新版本（审核 R3 余项，2026-10-25 修正）；
   - **标题名**：
     - 起点：条款编号位于窗口开头（第 0 字）时，从编号之后取；否则从窗口开头取。说明书正文里顺带提到的条款编号不会改变标题，编号前有标签时标题也不会从编号后误取（审核 R3）；
     - 从起点开始，若以 `title_brackets` 左括号开头，取到右括号为止；
     - 否则取到最先出现的 `title_end_markers` 为止，包括位于起点（第 0 字）的标记，此时标题名为空（审核 R2）；
     - 取不到，或长度超过 `max_title_chars` 时，标题名为空；
   - **名称命中**：
     - 标题名与登记产品的名称或别名完全相等，该产品即命中；
     - 没有完全相等时，若标题名中出现两款及以上已登记产品的名称（互不覆盖），记为多产品；
     - 只出现一款已登记产品的名称作为一部分（如"…（分红型）"含"…终身寿险"），不算命中。
4. **定产品**：
   - 编号命中某产品，但名称命中的产品中没有它 → `QUARANTINE / anchor_conflict`。这包括名称命中为空的情况：标题缺失、超长，或不等于任何登记名称。只凭编号不自动归属，两类依据必须一致（审核 R1）；
   - 编号命中某产品 → 该产品（`matched_by_clause_code`）；
   - 名称恰好命中一个产品 → 该产品（`matched_by_name`）；
   - 名称完全相等的产品不止一个（登记冲突），或标题含多款产品名（合并材料）→ `NEEDS_CONFIRM / multiple_products`，`candidates` 为这些产品；
   - 都没命中：
     - 材料是条款且有**自己的**条款编号 → 走新建（第 6 步）；
     - 否则 → `QUARANTINE / no_product_anchor`。说明书、费率表要等它的条款先到；S5b-2 每次运行都会重新判定隔离中的材料。
5. **已有产品**（记为 P）：
   - 角色无法识别 → `NEEDS_CONFIRM / role_unresolved`（`candidates=(P,)`）；
   - 条款，且有**自己的**条款编号、该编号不在 P 的已知编号中 → `NEW_VERSION / new_clause_code`，`replaces` 为 P 现有条款材料。只替换条款；说明书、费率表要等新的同类材料到达后再确认。只有引用编号的条款不判新版本，按下面两条处理；
   - P 已有同角色材料（内容不同，因为第 1 步已排除重复）→ `NEEDS_CONFIRM / same_role_differs`（用户 2026-10-24 规则：交人工选替换、补充或忽略）；
   - 否则 → `SUPPLEMENT`，原因沿用第 4 步（`matched_by_clause_code` 或 `matched_by_name`）。
6. **新建**：
   - 产品名 = 第 3 步取出的标题名，为空 → `QUARANTINE / no_product_anchor`；
   - 知识包按 `classifications` 推断，推断不出 → `NEEDS_CONFIRM / pack_unresolved`（`candidates` 为空）；
   - 编号按 §2.1 生成，若与已登记产品冲突 → `QUARANTINE / anchor_conflict`；
   - 否则 → `CREATE / new_product`（用户 2026-10-24 规则：按条款编号自动生成编号）。

## 3. 验收（RED，Claude 编写，受保护）

`harness/tests/identity/test_attribution.py`，样例 `harness/tests/identity/fixtures/attribution_heads.json`。样例是 13 款产品、39 份材料的前 300 字（规范化后），附真实 SHA-256、产品代码、条款编号、标准名与知识包。

1. **策略**：
   - 能加载，版本固定；
   - 每个 `classifications` 的知识包都存在于 `catalog/schema_packs.json`，且该包的 `applicable_classifications` 与之对应。
2. **留一新建**：对每款产品，登记其余 12 款，判定它的条款应为 `CREATE`，`display_name`、`clause_code`、`schema_pack_id` 与样例一致，编号符合 `sc-` + 10 位十六进制。覆盖 7 个险种（防止按样本拟合）。
3. **补充**：
   - 只登记某产品的条款时，其说明书、费率表为 `SUPPLEMENT / matched_by_name`；
   - 只登记说明书时，其条款为 `SUPPLEMENT / matched_by_clause_code`。
4. **名称包含**：
   - 登记盛世金越三款（各只有条款），每款的说明书、费率表都归到它自己的产品；
   - 只登记较短名称的那款时，"…（分红型）"与"平安创享…"的条款都应为 `CREATE`，不得判为它的 `NEW_VERSION`。
5. **重复**：`sha256` 已登记 → `DUPLICATE`。
6. **同类不同内容**：已有说明书时再来一份内容不同的说明书 → `NEEDS_CONFIRM / same_role_differs`。
7. **新版本**：
   - 条款编号改为未登记的值，产品名不变 → `NEW_VERSION / new_clause_code`，`replaces` 为旧条款；
   - 编号为 A 产品、名称为 B 产品 → `QUARANTINE / anchor_conflict`。
8. **多产品**：
   - 标题同时含两款已登记产品的名称（如"A、B 产品说明书"）→ `NEEDS_CONFIRM / multiple_products`，`candidates` 有序；
   - 两款登记产品共用同一别名、标题与之相等 → 同上。
9. **隔离**：
   - 未登记产品的说明书 → `QUARANTINE / no_product_anchor`；
   - 空文本 → `QUARANTINE / text_unavailable`。
10. **人工确认**：
    - 文件名不含角色词 → `NEEDS_CONFIRM / role_unresolved`；
    - 条款产品名的险种推断不出 → `NEEDS_CONFIRM / pack_unresolved`。
11. **确定性**：打乱登记顺序结果不变；同一输入重复调用结果相同；新建编号只取决于条款编号。
12. **审核 R1–R4 反例**（2026-10-24 补）：
    - R1：编号命中、标题为另一未登记名称、为空或超长 → `QUARANTINE / anchor_conflict`；
    - R2：编号后紧接结束标记、正文里才有产品名 → 不新建，`QUARANTINE / no_product_anchor`；
    - R3：
      - 编号前有"条款编号："或无冒号的标签，已登记产品有旧条款时，不得判为 `NEW_VERSION`，应为 `QUARANTINE / anchor_conflict`；
      - 未登记时不得新建；
      - 不认识的发文机构不算编号；
      - 说明书正文提到本产品条款编号时仍为 `SUPPLEMENT`（正控制）；
    - R4：登记中 `product_id` 重复时抛 `REGISTRY_DUPLICATE_PRODUCT`，任何顺序都一样。
13. **审核 R3 余项**（2026-10-25 补，默认发文机构、虚构产品）：
    - 编号前有任意标签（如"备案编号："、"编号"）、未登记时 → `QUARANTINE / no_product_anchor`，不新建；已登记时 → `QUARANTINE / anchor_conflict`；
    - 正文只引用另一编号的条款，名称命中已登记产品且该产品已有条款 → `NEEDS_CONFIRM / same_role_differs`，不判 `NEW_VERSION`；未登记时 → `QUARANTINE / no_product_anchor`；
    - 正控制保持：开头编号的新建、真实新版本、说明书正文引用本产品编号仍为 `SUPPLEMENT`。
