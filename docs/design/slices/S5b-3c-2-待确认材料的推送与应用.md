# S5b-3c-2 · 待确认材料的推送与应用

> 状态：Claude 2026-10-25 提出 ｜ 作者：Claude Code
> 依据：
> - S5b-3a（#339）：通用待确认项接口。提交方提交、人作答、提交方关闭；`applied` 关闭时由平台在锁内核对答案是不是最新的；
> - S5b-3c-1（#343）：选项与结论（`choices` / `conclude`），登记表记录人工决定（`record`）；
> - S5b-2（#337）：登记表、`run` 命令与登记表锁。
>
> 实现方：Claude ｜ 审核方：Codex（跨组件 REST、并发与故障恢复、真实调用链路）｜ 真实模型调用：0

## 1. 目标

新增命令 `uploads confirm`，每次运行完成一轮同步：

1. 把登记表中等人确认（`NEEDS_CONFIRM`）的材料推送成待确认项；
2. 读回人的选择，按 S5b-3c-1 得出结论、写入登记表，并关闭待确认项；
3. 关闭已经不需要的待确认项。

隔离区（`QUARANTINE`）的材料不推送，仍按 S5b-2 每次运行重判。

## 2. 关键规则

### 2.1 一项待确认 = 一个问题

| 字段 | 取值 |
|---|---|
| `subject` | `material:<knowledge_id>` |
| `revision` | 问题摘要：`knowledge_id`、`parse_attempt`、`sha256`、`pending` 中的归属结论，以及登记表中这份材料已有的判定记录条数，取其 canonical JSON（键排序、无多余空白）的 SHA-256 前 32 位十六进制 |
| `title`、`detail`、`options` | 由文案数据生成（§3.2），选项来自 `choices()` |

- 同一份材料的同一个问题，`subject` 与 `revision` 不变；文案改动只改变平台算出的 `content_digest`。
- 选择之后得出新问题（例如 `same_role_differs`）时 `revision` 改变，平台上成为新的一项。
- 计入判定记录条数是为了让作废后重新判定、又得出同样问题时成为新的一项。否则平台会把它当成已关闭的旧项，人就看不到了。
- 判断平台上的项是不是当前问题时，比较 `subject`、`revision` 以及标题、说明、选项的内容；Harness 不复算平台的 `content_digest`。
- 只处理 `subject` 以 `material:` 开头的项，其他提交方的项不动。

### 2.2 先关闭，再写登记表

- 关闭是提交点：平台在 `applied` 关闭时于锁内核对这是不是最新答案，关闭之后不能再作答。所以顺序是：
  1. 读到一个有答案的待处理项；
  2. 用 `conclude` 得出结论；
  3. 以该答案关闭（`applied`）；
  4. 关闭成功后用 `record` 写入登记表并立即保存。
- 关闭时平台报 `ANSWER_STALE`（这期间有人改了选择）：本轮跳过这一项，登记表不变，下一轮按新答案处理。
- 关闭时平台报 `CONFIRMATION_CLOSED`：本轮跳过，下一轮按 §2.3 恢复。
- **恢复**：关闭成功后、保存登记表之前中断时，下次运行先读已处理的项。某项同时满足以下条件，就补上这次记录：
  - 以 `applied` 关闭；
  - `subject` 和 `revision` 对应登记表里仍在等人确认的问题；
  - 关闭指向的 `answer_id` 还没记录过。

  不会再次关闭。同一问题有两个以上这样的项时不猜，报 `CONFIRMATION_AMBIGUOUS`，这一项本轮不处理。

### 2.3 选择已不适用

- `conclude` 报 `CHOICE_STALE` 或 `CHOICE_UNKNOWN`，表示提问之后登记表已经变了。处理方式：
  - 以 `obsolete` 关闭这一项；
  - 从 `pending` 中移除这份材料，下次 `uploads run` 会重新判定它；
  - 在报告中列出。
- 页面会显示"已无需处理"。如果重新判定后仍需要人确认，会推送一个新问题。

### 2.4 关闭不需要的项

一轮结束时，以 `obsolete` 关闭符合以下条件的待处理项：

- `subject` 以 `material:` 开头；
- `subject`、`revision` 与内容（标题、说明、选项）不属于当前要问的问题。

例如材料已经处理，或文案版本改了，同一问题已由新的一项代替。

## 3. 改动

### 3.1 `bundle/client.py`

- 新增模型：`ConfirmationOption`、`ConfirmationAnswer`、`ConfirmationClosure`、`ConfirmationItem`（与 S5b-3a 的 JSON 一致，时间为字符串）、`ConfirmationInput`（`subject`、`revision`、`title`、`detail`、`options`）。
- 新增方法：
  - `submit_confirmations(space_id, items)`：`POST …/confirmations`，请求体 `{"items": [...]}`，返回平台保存的项，顺序与输入一致；一次最多 200 项，超过时报 `INVALID_REQUEST`，由调用方分批；
  - `confirmations(space_id, status)`：`GET …/confirmations?status=open|closed`；
  - `close_confirmation(space_id, item_id, reason, answer_id=None)`：`POST …/confirmations/<id>/closure`，请求体 `{"reason", "answer_id"}`；`obsolete` 时不带 `answer_id`。
- 平台错误码加入 `CONFIRMATION_INVALID`、`CONFIRMATION_NOT_FOUND`、`ANSWER_INVALID`、`CONFIRMATION_CLOSED`、`ANSWER_STALE`。
- 响应仍按严格 JSON 解析，字段不符时报 `INVALID_RESPONSE`。

### 3.2 文案数据 `ingest/confirmation_wording.json`（新）

- 字段：
  - `version`；
  - `title`：标题模板，占位符 `{file}`；
  - `details`：按原因的说明模板；
  - `options`：按选项种类（`product`、`pack`、`role`、`replace`、`supplement`、`ignore`）的文字模板；
  - `roles`：材料角色的显示名。
- 由 `ConfirmationWording` 模型读取（严格模式，禁止多余字段）；四种原因、六种选项、全部材料角色都必须有文案，缺一项时报 `WORDING_INVALID`。
- 险种包的显示名取策略中该包的第一个分类后缀（如 `重大疾病保险`）。
- 说明里写出文件名、产品名称、材料角色和条款编号，只用登记表与归属结论里已有的事实。
- 长度在 S5b-3a 的上限内：标题 200 字、说明 2000 字、选项 200 字。
  - 文件名过长时截断，并以 `…` 结尾；
  - 文案仍超长，或含换行以外的控制字符时，报 `WORDING_INVALID`；
  - `subject` 不合 S5b-3a 的格式（knowledge id 过长）时，报 `QUESTION_INVALID`；
  - 这两种情况都是这一项不推送，计入 `skipped`，其他项照常处理。

### 3.3 `ingest/confirmations.py`（新）

```python
def load_wording() -> ConfirmationWording
def question_of(entry: PendingEntry, registry: ProductRegistry,
                wording: ConfirmationWording | None = None) -> ConfirmationInput
def sync(registry: ProductRegistry, client: PlatformClient, pages: PageReader, *,
         write: bool, save: Callable[[ProductRegistry], None],
         wording: ConfirmationWording | None = None) -> ConfirmationRun
```

- `sync` 不修改传入的登记表，返回新的登记表与报告，与 `attribute_uploads` 相同。
- 问题按 knowledge id 排序处理。

`sync` 的一轮：

1. 读已处理的项，按 §2.2 恢复；
2. 推送当前所有问题，每批最多 200 项。平台保留已有的项，并返回其最新答案与关闭记录。返回的项已经关闭（例如文案改回了旧版本）时，计入 `CONFIRMATION_CLOSED`；
3. 处理有答案、未关闭的项：§2.2 应用，或 §2.3 作废；
4. 第 3 步产生新问题时，再推送一次；
5. 读待处理的项，按 §2.4 关闭不需要的项。

- 每次写入登记表后都调用 `save`。
- `write=False`（演练）：
  - 不推送、不关闭、不调用 `save`，平台上只有读取；
  - 在内存中照常推演：假定关闭都会成功，把结论写入内存中的登记表，并据此得出新问题；
  - 报告与实际运行（无并发改选时）相同。
- 报告 `ConfirmationReport`，只列 knowledge id 与计数，不含文件内容：
  - `pushed`：本轮推送（演练时为将要推送）的问题；
  - `applied`：按人的选择写入登记表的材料（含恢复）；
  - `reopened`：选择已不适用、移出 `pending` 的材料；
  - `obsoleted`：以 `obsolete` 关闭的 `material:` 项；
  - 以上都是 knowledge id 列表，排序；
  - `waiting`：本轮结束时 `pending` 中等人确认的材料数；
  - `skipped`：按错误码计数（`ANSWER_STALE`、`CONFIRMATION_CLOSED`、`CONFIRMATION_AMBIGUOUS`，以及页面读取的错误码）。
- 读取某份材料的页面失败（重新判定需要开头文本）：这一项本轮跳过，按错误码计入 `skipped`，其他项照常处理。
- 平台请求失败：
  - 按错误码结束本轮；
  - 已经关闭并写入的部分已保存；
  - 其余下次重来。

### 3.4 命令 `uploads confirm`

```
python -m insurance_harness.ingest.uploads confirm --registry PATH [--dry-run]
```

- 与 `seed`、`run` 共用登记表锁与环境变量 `HARNESS_WEKNORA_BASE_URL`、`HARNESS_WEKNORA_API_KEY`；
- 输出报告 JSON；
- 退出码与 `run` 相同：0 成功、1 错误码、2 缺配置、3 `REGISTRY_BUSY`。

**不做**：

- 不编译、不发布受影响的产品（S5b-4）；
- 隔离区的材料不交给人；
- 不改平台接口与页面。

## 4. 验收（RED，Claude 编写，受保护）

`harness/tests/ingest/test_confirmations.py` 等。平台用 `httpx.MockTransport` 模拟，按 S5b-3a 的规则实现：

- 相同 `subject`、`revision`、`content_digest` 只保留一项；
- 答案只追加；
- 每项只能关闭一次；
- `applied` 必须指向最新答案，否则报 `ANSWER_STALE`。

材料用 S5b-1 的真实开头文本，至少覆盖两个险种。

1. **推送**：
   - 等人确认的材料各推送一项：`subject`、`revision`、标题、说明、选项与文案一致，选项键来自 `choices()`；
   - 隔离区的材料不推送；
   - 第二次运行不新增项，登记表不变；
   - 作废后重新判定、又得出同样的问题时，推送新的一项。
2. **应用**：
   - 人选"替换"后运行：该项以这个答案 `applied` 关闭；登记表得出 `REPLACE`，带 `confirmation`；
   - 再运行，不再关闭，也不再记录。
3. **新问题**：选产品得出 `same_role_differs` 时：
   - 旧项以 `applied` 关闭；
   - 同一轮推送新的一项（`revision` 不同）；
   - 新问题照常处理。
4. **作废**：登记表在提问之后变化，选择已不适用：
   - 该项以 `obsolete` 关闭；
   - 材料移出 `pending`；
   - 之后 `uploads run` 重新判定它。
5. **并发改选**：读到答案之后、关闭之前有人改了选择：
   - 本轮关闭报 `ANSWER_STALE`，登记表不变；
   - 下一轮按新答案关闭并记录。
6. **恢复**：
   - 关闭成功、保存前中断（模拟 `save` 抛错），下次运行从已处理的项补上记录，不重复关闭；
   - 同一问题有两个可恢复的项时报 `CONFIRMATION_AMBIGUOUS`，不猜。
7. **清理**：
   - 已不需要的 `material:` 项以 `obsolete` 关闭；
   - 文案版本改了时，旧项作废、新项推送；
   - 其他提交方的项不动。
8. **演练**：
   - 平台上没有任何写请求，`save` 未被调用；
   - 报告与随后实际运行的报告相同，包括应用后产生的新问题。
9. **页面读取失败**：这一项跳过并计数，其他项照常应用。
10. **文案**：
   - 标题、说明、选项都在长度上限内，长文件名截断；
   - 四种原因的说明都写出了对应的事实；
   - 不含 `subject`、`revision`、产品 id 的哈希等内部值。
11. **客户端**：
    - 三个方法的路径、编码与请求体；
    - 超过 200 项时拒绝；
    - 错误码；
    - 严格解析响应。
12. **命令**：
    - 缺配置时返回 2；
    - 登记表被占用时返回 3；
    - 平台失败时返回 1 并输出错误码，已经写入的部分保留。

**门禁**：在 `harness/` 下运行 `uv run pytest`、`uv run ruff check .`、`uv run mypy src tests`；架构守卫。
