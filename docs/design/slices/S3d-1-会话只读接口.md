# S3d-1 · 会话只读接口：登录用户按 Space 读取发布版本、打开引用与原文

> 状态：用户已确认开工（2026-10-17，S3d 拆分方案） ｜ 作者：Claude Code
> 依据：蓝图 §5.4（Release 读取）、§7.4（回跳顺序）、§7.5（访问控制、`access_scope`）、硬边界 5；S4c-2a/2b Spec；2026-10-17 S3d 调研
> 分支：`slice/s3d1` ｜ 工作目录：`.worktrees/s3d1` ｜ 实现方：Codex（Go 平台、鉴权与隔离） ｜ 审核方：Claude

S3d（第一批用户可见的企业知识页面）拆为三片：**S3d-1 本片（Go 会话只读接口）**、S3d-2（Harness 在发布中带上实体与展示数据）、
S3d-3（前端页面与原文查看器）。三片写域不重叠，可并行；S3d-3 依赖前两片的接口形状，按本 Spec 与 S3d-2 的合同先行开发。

## 1. 目标

浏览器里登录的用户（JWT 会话）今天调不了企业接口：`enterprise.requestPrincipal`（`mount.go`）只接受全权限、不限 KB 的服务密钥。
本片为会话用户新增一组**只读**路由，服务密钥路由保持不变：

1. 列出调用者租户下已配置的企业 Space；
2. 读取某 Space 的 Active 或指定 Release；
3. 按 Release 打开引用（页、引文、高亮框）与原始 PDF 字节。

## 2. 现状（`main@28bf12de9`）

- 认证：`middleware.Auth` 对 JWT 会话设置 tenant、user、`Principal{Type: web_user}`、角色与 Caller，**不设** `TenantAPIKeyScope`
  （`internal/middleware/auth_context.go:50-86`）；对 API key 另外附上 `TenantAPIKeyScope`。API key 闸门（`api_key_gate.go`）放行
  JWT、对未登记策略的路径默认拒绝 API key。
- `release.Service` 的 `Release`/`Evidence` 只要求 tenant 与 subject 非空；Space 归属由 `releasestore` 按 `Spaces.Scope(tenant, space)` 检查。
  会话被拒只因 `mount.go` 的服务密钥闸门。
- 既有会话只读路由的守卫做法：`g.Viewer()` + `g.KBAccessRead(param)`（`internal/router/rbac.go:195,556`；
  `middleware.RequireKBAccess(resolver, OrgRoleViewer, ...)` 接受自定义 `KBIDResolver`，RBAC 关闭时也强制）。共享 KB 时该守卫可能改写执行租户。
- Harness 给所有成员与证据设 `access_scope="space"`；Go 存取但从不过滤。

## 3. 设计

### 3.1 `internal/enterprise`（新文件，例如 `session.go`）

```go
// SpaceDirectory lists the configured enterprise Spaces of a tenant (releasestore.Spaces implements it).
type SpaceDirectory interface {
    SpaceIDs(tenantID uint64) []string                                        // sorted
    KnowledgeBases(tenantID uint64, spaceID string) (rawKB, wikiKB string, ok bool)
}

// SessionDeps are the read-only collaborators of the browser routes.
type SessionDeps struct {
    Candidates *release.Service
    Sources    *source.Service
    Files      SourceFiles
    Spaces     SpaceDirectory
}

// MountSessionReads registers read-only routes for logged-in users on a group mounted at
// /api/v1/enterprise. viewGuards run on every /spaces/:space_id/view/* route after the session
// check and before the handler (production: tenant viewer role + KB read on both Space KBs).
func MountSessionReads(r gin.IRouter, deps SessionDeps, viewGuards ...gin.HandlerFunc)
```

- 路由（全部 GET；响应形状与服务密钥路由一致，`{"success":true,"data":...}`）：
  - `/spaces` → `{"spaces":[{"space_id":"…"}]}`：调用者租户下的 Space，按 id 排序；没有则空数组。
  - `/spaces/:space_id/view/releases/active`、`/spaces/:space_id/view/releases/:release_id`；
  - `/spaces/:space_id/view/releases/:release_id/citation?member=&evidence=`：返回体中的 `file` 指向会话路径
    `/api/v1/enterprise/spaces/<sid>/view/releases/<rid>/sources/<kid>/attempts/<n>/file`；
  - `/spaces/:space_id/view/releases/:release_id/sources/:knowledge_id/attempts/:attempt/file`。
  - 校验、错误码与上限沿用 S4c-2b-2（显式 Release、`active` 别名不接受于 citation/file、未引用的 attempt 不打开文件、256 MiB、
    先校验指纹再响应、取消即停）；复用现有处理函数，不复制逻辑。
- **会话身份**（每条路由的第一个中间件，先于 viewGuards）：
  - 必须同时满足：上下文与 gin 中的 tenant 一致且非零；`Principal.Type == web_user` 且 ID 非空；**请求上下文没有 `TenantAPIKeyScope`**。
    否则 403 `RELEASE_ACCESS_DENIED`，不调用守卫或服务。
  - 记下此时的调用者租户，后续一律用它（守卫若因共享改写执行租户也不影响）；release 服务的 Principal 为
    `{TenantID: 调用者租户, Subject: principal.StorageID()}`。
- **Space 归属**（会话检查之后、viewGuards 之前）：`space_id` 不在 `Spaces.SpaceIDs(调用者租户)` 中 → 404 `RELEASE_NOT_FOUND`
  （不区分"不存在"与"属于他租户"），不调用守卫与服务。执行顺序：会话身份 → Space 归属 → viewGuards → 处理函数。
- **`access_scope` 过滤**（蓝图 §7.5 首期）：会话读取只返回 `access_scope == "space"` 的成员；其他取值一律当作不存在
  （Release 读回中省略；citation 对这类成员返回 `MEMBER_NOT_FOUND`；file 路由只认可见成员的 `evidence_refs`）。服务密钥路由不过滤。
- 会话路由不登记任何 API key 策略（API key 闸门默认拒绝），也不提供任何写操作（候选、决定、激活、退役、固定查询）。

### 3.2 `internal/enterprise/releasestore`

- `Spaces` 增加 `SpaceIDs(tenantID uint64) []string` 与 `KnowledgeBases(tenantID uint64, spaceID string) (string, string, bool)`，实现
  `enterprise.SpaceDirectory`。

### 3.3 装配（`internal/router/router.go`，已登记的上游补丁文件）

- `registerEnterpriseRoutes` 另外调用 `enterprise.MountSessionReads(v1.Group("/enterprise"), deps, viewGuards...)`：
  - `viewGuards` = `guards.Viewer()`，以及两条 `middleware.RequireKBAccess(resolver, types.OrgRoleViewer, ...)`，resolver 分别把
    `:space_id` 映射到该 Space 的 RAW KB 与 wiki KB（`EnterpriseSpaces.KnowledgeBases(调用者租户, space)`，找不到返回 404 apperror）。
  - `deps.Files` 与服务密钥路由相同（`releasestore.SourceFiles`）。
- 会话路由与服务密钥路由路径前缀不同（`/view/`），gin 不会冲突；服务密钥 `Mount` 不改。

### 3.4 不在本片

会话写操作、Space 显示名（来自 S3d-2 的发布数据）、按用户粒度的 `access_scope`（目前只有 "space"）、跨租户共享、审核方式与维护记录
（成员级来源追踪）、前端（S3d-3）。

## 4. 验收

- 受保护验收（Claude 写，RED 单独提交）：`internal/enterprise/mount_session_test.go`（会话上下文按 `applyAuthSession` 的方式注入）：
  - 列出本租户 Space（排序）、不列他租户；
  - 读 Active 与指定 Release，`access_scope` 非 "space" 的成员被省略；
  - citation 走会话路径且 `file` 指向会话路径；file 路由返回字节；不可见成员的引用与文件均不可得；
  - 服务密钥身份、非 web_user 身份、缺 tenant → 403，且不调用守卫与服务；
  - viewGuards 只作用于 `/view/` 路由，按注册顺序在会话检查之后执行；守卫中止即不调用服务；
  - 他租户 Space 与未配置 Space → 404，且不调用守卫之后的逻辑。
- 实现方补：`releasestore` 两个新方法的测试；router 级测试（无 KB 读权限 → 403，有权限 → 200；API key 访问会话路由被闸门拒绝）。
- Go：`go test ./internal/enterprise/... ./internal/router/... ./internal/container/...` 相对 S0 失败清单不新增；`golangci-lint
  --new-from-merge-base` 通过；守卫通过（G10 数不增）；CI 全绿。
