## 1. 现状与目标

现状：`uploads confirm` 只推送 `NEEDS_CONFIRM` 的材料（S5b-3c-2 §1）。`QUARANTINE` 的材料留在登记表 `pending` 里，每次 `uploads run` 重判，从不出现在"待确认材料"页。线上就有一例：一份"产品说明书.pdf"因为找不到产品锚点（`no_product_anchor`）被隔离，实际是"平安附加学生门诊急诊医疗保险"的说明书，页面上看不到它。

目标：隔离材料也推送成待确认项，写明隔离原因，让人选择它属于哪个已登记产品，或确认它不属于任何已登记产品。

**合同结论：不需要改平台或前端。** S5b-3a 的待确认项是通用格式（标题、说明、1–50 个选项、原文件引用），页面按通用格式显示、作答、打开原文件。本片只改 Harness。

## 2. 规则

### 2.1 哪些隔离材料提问、给哪些选项

`identity/confirmation.choices()` 接受 `QUARANTINE`，按原因给选项（顺序固定，最后都是"忽略"）：

| 隔离原因 | 含义 | 选项 |
|---|---|---|
| `no_product_anchor` | 找不到能确定产品的锚点（不是带自身编号和标题的条款） | 每个已登记产品（按登记表顺序）；忽略 |
| `anchor_conflict` | 锚点互相矛盾（同一文件已属于别的产品、条款编号属于别的产品等） | 只有"忽略" |
| `text_unavailable` | 开头没有可读文字（多为扫描件） | 只有"忽略" |

- 人的选择不放宽规则（S5b-3c-1 §1）：`anchor_conflict` 时按人选的产品重判仍会得出锚点矛盾，`text_unavailable` 时没有文字可判，所以这两种只能确认"不要这份文件"，或者不作答、继续隔离。改正冲突的锚点要改登记表数据，不在本片。
- 产品选项的键与 S5b-3c-1 相同（`product:` + 产品 id 的 SHA-256 前 16 位）。
- 选项超过平台上限 50 个（已登记产品超过 49 个）时报 `NOT_CONFIRMABLE`，这份材料本次不提问，计入 `skipped`，材料继续隔离。退出条件：S11 引入可搜索的产品选择后取消这个上限。
- 其他原因（隔离原因只有上表三种）报 `NOT_CONFIRMABLE`。

### 2.2 选择之后的结论（`conclude`）

| 选择 | 结论 | 成立条件（不满足报 `CHOICE_STALE`） |
|---|---|---|
| 产品 P | `attribute(upload, registry, policy, product=P)` | 与 S5b-3c-1 的"产品 P"相同：结论针对 P，且是 `DUPLICATE`、`SUPPLEMENT`、`NEW_VERSION`，或 `NEEDS_CONFIRM`（`role_unresolved` / `same_role_differs`，再问一次） |
| 忽略 | `IGNORED / confirmed_ignore`，字段取自隔离结论 | 无 |

- 材料角色仍由 S5b-1 从文件名和开头识别；认不出时得出 `NEEDS_CONFIRM / role_unresolved`，再问角色。确认的角色按 S5b-6 用于编译。
- 绝不自动归属：只有人的选择才让隔离材料归入产品。
- `IGNORED` 是终局结论（`FINAL`），记录后这份材料（按 knowledge id）不再参与 `run` 的重判，也不再提问。

### 2.3 与"每次重判"共存（幂等）

- 问题的 `revision` 规则不变（S5b-3c-2 §2.1）：取决于 `pending` 中的结论和已有判定记录条数。`run` 重判得出相同的隔离结论时不追加判定记录（S5b-2 原有行为），所以 `revision` 不变，不会重复推送。
- 重判结论变了（例如后来上传了条款、锚点变得确定，自动归入产品；或隔离原因变了），`pending` 中的这条随之变化，旧的待确认项在下一次 `confirm` 时按 S5b-3c-2 关闭为 `obsolete`，必要时推送新问题。人已经作答但还没应用的答案，这时不会被应用：规则能确定时以规则为准。
- **正在落实的人工决定不被重判打断**：`pending` 中带 `settlement`（`confirm` 已保存、正在关闭或执行的人工决定）的材料，`run` 不重判（`uploads._candidates` 排除），否则重判会用新条目替换掉这条 settlement。

### 2.4 登记表

- `pending` 中带 `settlement` 的条目，结论可以是 `NEEDS_CONFIRM` 或 `QUARANTINE`（原来只允许 `NEEDS_CONFIRM`）。
- `record(..., confirmation=...)`：要求这份材料（knowledge id、解析次数、SHA 都相同）在 `pending` 中且结论属于 `WAITING`（`NEEDS_CONFIRM` 或 `QUARANTINE`）；否则仍报 `CONFIRMATION_UNEXPECTED`。
- `contract` 仍为 `product-registry.v1`；旧文件照常读取。

### 2.5 文案

`confirmation_wording.json` 为三种隔离原因各加一段说明：

- `no_product_anchor`：说明没找到能确定产品的依据、材料暂被隔离；知道属于哪个已登记产品就选它，都不是就选"忽略"，忽略后不再参与归属判定。
- `anchor_conflict`：说明依据互相矛盾、系统不能自动归属也不能按人工选择改判；请打开原文件核对，不需要时选"忽略"。
- `text_unavailable`：说明开头没有可读文字（可能是扫描件）；扫描件识别尚未支持，不需要时选"忽略"，否则保持隔离。这一种不附"文件开头"（没有可读文字；页面可打开原文件）。

文案版本号不变（`2026-10-26.1`）：已有四种原因的文字一字未改，已有待确认项的 `revision` 不变，页面上已有的问题不会被关闭重推（版本号参与 `revision`，改版本会让已作答未落实的问题被当作过期关闭）。以后改写任何已有文字时照常升版本。

## 4. 验收

1. `no_product_anchor` 的选项为每个已登记产品加"忽略"；`anchor_conflict`、`text_unavailable` 只有"忽略"；已登记产品超过 49 个时报 `NOT_CONFIRMABLE`。
2. 隔离的说明书选择产品后，归入该产品（角色由规则识别）；选择"忽略"记为 `IGNORED / confirmed_ignore`，带人工决定来源，`pending` 不再有它，之后的 `run` 不再重判它。
3. `confirm` 把隔离材料推送成待确认项：说明写明隔离原因并附文件开头（`text_unavailable` 除外），带原文件引用；报告的 `waiting` 计入隔离材料。
4. 推送后再运行 `run`（重判出相同隔离结论）和 `confirm`：不新增待确认项，不关闭原项。
5. 带 settlement 的隔离材料不被 `run` 重判，settlement 保留。
6. 已有四种原因的文案与版本号不变。
7. 门禁：Harness `pytest -m "not integration_postgres"`、ruff、mypy、`tests/architecture`、`git diff --check`。

## 5. 上线

合并后运行 `uploads confirm`（无模型调用），线上已隔离的材料出现在"待确认材料"页。回滚：回退本片代码后，已推送的隔离项会在下一次 `confirm` 时作为不再提问的项关闭；已记录的人工决定保留在登记表中。
