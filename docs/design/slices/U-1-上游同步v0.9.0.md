## 2. 目标与不做

- 目标：`main` 包含上游 v0.9.0 的全部代码；我们的企业包、Harness、合同与已登记补丁的行为不变；守卫 G10 的
  `upstream_base` 改为 v0.9.0 后，被改上游文件数不高于同步前（预期下降：S7f-1 回退的文件与上游已吸收的改动不再计入）。
- 不做：ParadeDB 镜像升级；启用上游新功能的配置（automations、agent collaborations、sandbox 分配等保持默认关闭或现有配置）；
  S11b 的适配实现（U-1 之后另片）。

## 3. 顺序与做法

1. **前置**：S7f-1（#448）先合并（消掉 17 个冲突）。合并期间冻结其他改动上游文件的切片。
2. 在 `slice/u1` 上 `git merge v0.9.0`（不 rebase，保留上游历史），一次合并提交。
3. **冲突处理规则**：
   - 我们未改过、只是上游改了的：取上游。
   - 已登记补丁：以上游新版本为底，重新施加我们的补丁；能改用上游新增扩展点的，借机撤掉补丁并在
     `upstream-patches.md` 标记退出；不能的，补丁内容不变、登记行更新"对应上游版本"。
   - "pre-831"整体登记行下的文件：逐个判断是否仍需要；不需要的取上游（G10 下降），需要的补登记逐行。
   - 前端语言包：上游新增词条全部保留，我们的词条保留；冲突处按 key 合并。
   - 依赖：`go.sum`、`package-lock.json` 由工具重新生成（`go mod tidy`、`npm install --package-lock-only`），不手改。
4. 迁移：上游迁移原样进入；核对 000093/000094/000099 的修改对已执行过这些迁移的库无影响（迁移按版本号只跑一次）；
   企业账本不动。
5. 守卫：`upstream_base` 改为 v0.9.0 的提交 id，用基线脚本重算 G10，只允许下降或持平（新增的被改上游文件必须逐行登记）。

## 4. 门禁

- Go：`go build ./...`、`go vet ./...`、`go test ./...`（与同步前在同一环境对比失败集合，只允许本机环境类既有失败）；golangci-lint。
- 前端：`npm ci`、`npm run type-check`、相关测试、`npm run build`。
- docreader：其自带测试。
- Harness：`uv run pytest -m "not integration_postgres"`、ruff、mypy（Harness 不应受影响，用于确认合同未变）。
- 架构守卫 `pytest -q tests/architecture`；`git diff --check`。
- 企业验收：RED（待定）覆盖企业路由挂载、Active 读取、发布、引用、快问快答与 Agent 的企业规则（QA1–QA4）在同步后不变。
- 本机端到端：在测试 Space 上跑一次编译发布与问答冒烟（不碰 live），确认迁移在 live 同版本的 Postgres 上能顺利执行。
