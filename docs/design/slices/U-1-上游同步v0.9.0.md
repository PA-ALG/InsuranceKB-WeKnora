## 2. 目标与不做

- 目标：`main` 包含上游 v0.9.0 的全部代码；我们的企业包、Harness、合同与已登记补丁的行为不变；守卫 G10 的
  `upstream_base` 改为 v0.9.0 后，被改上游文件数不高于同步前（预期下降：S7f-1 回退的文件与上游已吸收的改动不再计入）。

  S11b 的适配实现（U-1 之后另片）。

## 3. 顺序与做法（三个阶段）

0. **前置**：S7f-1（#448/#450）先合并（消掉 17 个冲突），并合入删除临时 `.golangci.yml` 排除的收尾 PR。

**阶段 a：合并前先回退（U-1a，单独 PR，行为不变）**——对旧基线 `3e8b0bfc8` 回退附录 A 中的 L 类 184 个文件
（v0.8.2 升级期 lint/校验提交独占、未引用我方任何新增符号）与 D 类 4 个遗留文件（删掉对应的死代码路径）。
做法同 S7f-1：逐文件恢复为上游字节；`--new-from-merge-base` 的 lint 不会把上游原有行算作新问题，必要时用同样的
临时排除再立即收尾。测试类 L 文件恢复后若在我们的 CI 环境失败，保留原改动并改记为 X（附原因），不 skip。
预期 G10 由 349 降到约 160。本地模拟（S7f-1 head 上先回退这 188 个文件，再 `git merge --no-commit v0.9.0`）：合并冲突由 **83 个降到 53 个**；剩下的 53 个按族为 PINNING 14、前端 16、构建部署 6、ANSWER 5、CAPTURE 3、WIKIINGEST 3、KBPOLICY 3、接线 3（模拟只计冲突，不代表回退后能直接编译：D 类需同时删掉死代码路径）。

**阶段 b：合并 v0.9.0（U-1 本体）**

1. 在 `slice/u1` 上 `git merge v0.9.0`（不 rebase，保留上游历史），一次合并提交。
2. **冲突处理规则**（按附录 A 的族决定，**优先扩展点，不优先重放补丁**）：
   - 我们未改过、只是上游改了的：取上游。
   - 上游 v0.9.0 已提供等价能力的（Office 定位 `internal/sourceloc`、原文件预览与高亮）：取上游，撤掉我们的补丁。
   - 纯新增或几乎纯新增的补丁（81 个，附录 A 的 PINNING/KBPOLICY/CAPTURE 为主）：把新增的类型与方法移到同包内
     **我方新文件**，上游文件只保留必须的一行调用；若上游文件因此回到上游字节，G10 随之下降。
   - 其余已登记补丁：以上游新版本为底重放，语义不变，登记行更新"对应上游版本"。
   - 前端语言包：我们的词条移出上游 5 个语言文件，放进我方 locale 文件在启动时合并（见 §7），上游文件取上游。
   - 依赖：`go.sum`、`package-lock.json` 由工具重新生成（`go mod tidy`、`npm install --package-lock-only`），不手改。
3. 迁移：上游迁移原样进入；核对 000093/000094/000099 的修改对已执行过这些迁移的库无影响；我们对历史迁移 000077
   的改动撤回到上游，确有需要的改为企业迁移；企业账本不动。
4. 守卫：`upstream_base` 改为 v0.9.0 的提交 id，用基线脚本重算 G10，只允许下降或持平。

**阶段 c：合并后的逐族去耦（U-2 起，独立小切片，可与质量工作并行）**——按 §7 的顺序，每片只动一族，

## 4. 门禁

- Go：`go build ./...`、`go vet ./...`、`go test ./...`（与同步前在同一环境对比失败集合，只允许本机环境类既有失败）；golangci-lint。
- 前端：`npm ci`、`npm run type-check`、相关测试、`npm run build`。
- docreader：其自带测试。
- Harness：`uv run pytest -m "not integration_postgres"`、ruff、mypy（Harness 不应受影响，用于确认合同未变）。
- 架构守卫 `pytest -q tests/architecture`；`git diff --check`。
- 企业验收：RED（待定）覆盖企业路由挂载、Active 读取、发布、引用、快问快答与 Agent 的企业规则（QA1–QA4）在同步后不变。

## 8. 升级演练（CI，只报告）

新增定时工作流（每周一次，也可手动触发）：取上游最新正式 tag，在临时分支上与 `main` 合并；记录冲突文件数与清单；若能合并，
跑 Go build/vet/test、前端 type-check/build、架构守卫；把结果作为制品上传，并更新一个固定 Issue"上游升级演练"。
它从不推送到 `main`，不阻塞任何 PR。用它度量 §7.3 的"无缝"目标，并提前发现上游对我们扩展点的改动。
