## 1. 目标

S3d-3 的页面要显示"这是哪款产品、它的字段按什么分组和顺序展示"。两者都是领域数据，Go 与前端不能自己知道（硬边界 4）。
本片让 Harness 发布时在**同一个候选包**里另外带上：

1. 一个 `entity` 成员：产品身份（备案名称、实体类型、分类标签、产品代码）；
2. 一个 `presentation_profile` 成员：该 pack 的展示分组（分组键、分组名、组内字段顺序与短标题）。

它们与 claims 进入同一个 Release，页面、引用与内容遵守同一版本。

## 2. 现状（`main@28bf12de9`）

- `bundle.assemble` 只产生 `kind=claim` 成员；`schema_fields.publish` 只发布 claims。
- Go 对成员 `kind` 与 payload 一视同仁：只读 payload 的 `origin`、`state`、`evidence`，缺这三项的成员原样存取
  （`internal/enterprise/release/evidence.go`），所以本片不改 Go。
- Catalog（`internal/handler/schema_pack_catalog_830_g3.generated.json`）每个 entry 有：
  - `pack`：`entity_type`、`applicable_classifications`、`presentation_profile_ref`、`fields`；
  - `profile`：`presentation-profile.v1`，含 `profile_id`、`profile_version`、`profile_sha256`、`schema_pack_id`、`sections[]`。
  - 11 个 pack 的现状：profile 字段与 pack 字段一一对应，短标题与引用一致；每个 pack 的 `applicable_classifications` 各不相同。
- `Entity` 合同已有（`contracts/entity.schema.json`）。产品备案名称在数据集 `product_meta.json` 的 `clauseName`，编译时已用
  `eval.product_sources.source_directory` + `display_name` 读取。

## 3. 设计

### 3.1 新合同 `PresentationProfile`（从 `insurance_harness.contracts` 包导出，生成 `contracts/presentation_profile.schema.json`）

```python
class ProfileField(ContractModel):
    field_key: NonBlank
    short_title: NonBlank

class ProfileSection(ContractModel):
    section_key: NonBlank
    display_name: NonBlank
    fields: list[ProfileField] = Field(min_length=1)

class PresentationProfile(ContractModel):
    profile_id: NonBlank
    profile_version: NonBlank
    profile_sha256: Sha256
    schema_pack_id: NonBlank
    classification_labels: list[NonBlank] = Field(min_length=1)
    sections: list[ProfileSection] = Field(min_length=1)
```

- 校验：`section_key` 不重复；`field_key` 在全部分组中不重复。
- 读者用法（S3d-3 依此实现）：
  - profile 的 `classification_labels` 与实体的 `classification_labels` 有交集，就用该 profile 展示实体；
  - 实体的 claim 按 `subject_ref == entity_id` 选出，按 `sections` 顺序、以 `short_title` 为标签显示；
  - Release 中没有 claim 的字段不显示；不在任何分组里的 claim 归入"其他"；
  - 同一 Release 中，一个分类标签只对应一个 profile（catalog 现状保证，§3.2 校验）。

### 3.2 产品页数据（新文件 `harness/src/insurance_harness/compilers/schema_fields/page.py`）

```python
@dataclass(frozen=True)
class ProductPage:
    entity: Entity
    profile: PresentationProfile

def product_page(catalog_path: str | Path, pack_id: str, *, entity_id: str, name: str) -> ProductPage
```

- Entity：
  - `entity_id` = 传入值（编译输出的 entity_id）；`names` = [传入的备案名称]；
  - `entity_type` = pack 的 `entity_type`；`classification_labels` = pack 的 `applicable_classifications`；
  - `identifiers` = `{"product_code": entity_id}`；`owner_module` = `"harness/schema_fields"`；`aliases` 为空。
- Profile：取该 pack 的 catalog `profile`；`classification_labels` = pack 的 `applicable_classifications`。
- 拒绝时抛 `BundleError`，原因码：
  - catalog 读不了或结构不对 → `CATALOG_UNREADABLE`；
  - pack 不在 catalog → `PACK_UNKNOWN`；
  - `presentation_profile_ref`（id、version）与 profile 不一致，或 profile 的 `schema_pack_id` 不是该 pack → `PROFILE_MISMATCH`；
  - profile 违反合同（重复键、空分组等），或含 pack 没有的字段，或短标题与 pack 不一致 → `PROFILE_INVALID`；
  - 另一个 pack 的 `applicable_classifications` 与本 pack 有交集 → `PROFILE_INVALID`（否则读者无法唯一匹配）。

### 3.3 候选包（`bundle/assemble.py`、`compilers/schema_fields/claims.py`）

- `assemble(claims, *, compiler_identity, base=None, entities=(), profiles=())`：
  - 每个实体一个成员：`kind="entity"`，slug `entity/<entity_id>`；
  - 每个 profile 一个成员：`kind="presentation_profile"`，slug `presentation/<profile_id>`；
  - payload 为合同模型的 JSON（`model_dump(mode="json")`），`member_digest` 算法同 claim，`evidence_refs` 为空，`access_scope="space"`；
  - slug 在全部成员中唯一，否则 `DUPLICATE_LOGICAL_KEY`。
- `candidate_bundle(..., page: ProductPage | None = None)`：
  - 带 page 时加入其实体与 profile；
  - `page.entity.entity_id != output.entity_id` 或 `page.profile.schema_pack_id != output.pack_id` → `PAGE_MISMATCH`；
  - 不带 page 时行为不变（S4g 的单元验收）。
- 增量：成员是对 base Release 的覆盖写；同一 pack 的另一款产品会发布同一个 profile，slug 与 digest 都相同。

### 3.4 发布命令（`compilers/schema_fields/publish.py`）

- 新参数 `--repo`，默认仓库根（与 `compile_run` 相同）。发布前读取：
  - `<repo>/internal/handler/schema_pack_catalog_830_g3.generated.json`；
  - 数据集中该产品的 `product_meta.json`，用 `source_directory` + `display_name`，与编译同一规则。
- 据此构造 ProductPage，**总是**放入候选包。
- 这一步在任何网络请求之前完成。失败时：
  - 找不到或读不了产品元数据 → `{"stopped":"PRODUCT_META_MISSING"}`；
  - ProductPage 被拒 → `{"stopped":"BUNDLE_INVALID","reason":<§3.2 原因码>}`。
  - 输出不含路径或输入内容。
- 摘要里的 `members` 计入实体与 profile 成员。
