# S12c-11 字段边界：给付专属的不给付条件与伤残鉴定出具机构

> 状态：Spec（2026-10-31，Claude）。实现方 Claude，审核方 Codex（字段卡进入编译器身份；第一步与第二步请求都变）。
> Issue：#473（Owner 裁定，2026-10-31）。真实调用：消融 DeepSeek ≤ 40、GPT-6 Astra xhigh ≤ 2 个会话；实现与测试为 0。

## 1. 裁定（#473，Owner）

1. 条文中只针对某一项给付的不给付条件与限制（如“车辆用于以营利为目的的经营活动的，不承担本项保险金责任”）
   **同时属于该项给付的规则字段与 `exclusions`**，写进各给付规则卡的 includes。
2. 伤残鉴定由谁出具（出具机构及其资质）属于 `disability_definition_and_assessment_criteria`；理赔时提交的申请材料
   （鉴定书本身作为一项材料）属于 `claim_application_deadline_and_documents`。

背景：S12c-10 的消融里，同一版卡下 #458 的评委与 S12c-10 的评委对这两类事实判法相反（S12c-10 Spec §2）；
卡片原先没有写明这两条边界。

## 2. 改动（卡片数据 `draft-2026-10-31a` → `draft-2026-10-31b`）

### 2.1 给付规则卡

下列 9 张卡的 includes 末尾加同一句：

> ；条文中只针对本项责任的不给付条件与限制（如“……的，我们不承担本项保险金责任”）也属于本字段，同时选入责任免除（exclusions）

`accidental_death_benefit_rules`、`additional_benefit_rules`、`disability_benefit_rules`、`death_benefit_rules`、
`maturity_benefit_rules`、`survival_benefit_rules`、`premium_waiver_rules`、`income_loss_benefit_eligibility_conditions`、
`income_loss_care_benefit_conditions`。

选卡口径：定义为“某一项给付（或豁免）的条件与规则”的卡。收入损失类只加在两张给付条件卡上（金额、期限、上限卡的
定义不含给付条件）。不加：`coverage_responsibilities`、`coverage_summary`（责任总览，S12c-9 的 writing_rule 仍把免责句
划给 `exclusions`）、`benefit_interaction_rules`（只写责任之间的关系）。

与裁定冲突的旧文本一并改：

- `death_benefit_rules` 的 excludes“导致身故不赔的情形及退还现金价值 → exclusions”改为“责任免除条款列出的导致身故
  不赔的情形及退还现金价值”；
- `income_loss_benefit_eligibility_conditions` 的 excludes“不予给付的免责情形 → exclusions”改为“责任免除条款列出的
  不予给付情形”；同卡 1806 示例的 pitfalls 去掉“既往疾病免责”（先例：S12c-9 按 #443 裁定改过 1806 的 pitfalls）。
  示例的 value 不改；
- `exclusions` 的 includes 末尾注明“（这类句子同时属于该项责任的给付规则字段）”。

### 2.2 伤残鉴定出具机构

- `disability_definition_and_assessment_criteria`：includes 加“伤残鉴定由谁出具（如二级以上医院或鉴定机构出具伤残
  程度资料或鉴定书），理赔申请材料条文中写明的出具机构要求也属于本字段”；excludes 加“理赔时须提交的申请材料清单 →
  `claim_application_deadline_and_documents`”。
- `claim_application_deadline_and_documents`：includes 加“伤残鉴定书等材料写明的出具机构要求同时选入伤残定义与认定
  标准（`disability_definition_and_assessment_criteria`）”。

两张卡现有的 1803 示例（伤残定义卡 value 第 5 项与 pitfall“漏选……出具伤残资料要求”、理赔卡 value）已与裁定一致，不改。

### 2.3 请求的变化

includes 同时进入第一步与第二步的卡片 payload（与只到第二步的 writing_rule 不同），所以含这些字段的第一步批次请求会
改变。引擎只把第一步判为 present 的字段送入第二步：第一步判 absent 或 unknown 的字段不经过第二步，也就看不到第二步里
的这句。

### 2.4 不做

不改提示词与协议版本（仍 `2026-10-29.4`）、引擎、选段算法、writing_rule、其他卡片与示例 value、Golden。
