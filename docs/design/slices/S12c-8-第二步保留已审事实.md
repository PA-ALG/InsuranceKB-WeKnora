> 状态：Spec（2026-10-29，Claude）。实现方 Claude，审核方 Codex（复杂档：值协议与编译器身份）。
> 真实调用：消融 DeepSeek ≤ 60、GPT-6 Astra xhigh ≤ 3 个会话（Owner 批准）；实现与验收为 0。

## 1. 问题与诊断

S12c-6b（#434 评论 6493886116）发现：线上条件（带 S12c-4 carry）下，#436 的"遗漏关键内容"拒绝几乎都出在第二步。
Codex 审 #439 时指出那个结论只是页级启发式。本片按事实逐条归因（零调用，数据在仓库外 `s12c8-20261029/data/`）：

1. 对 #436 的 53 条"遗漏关键内容"，逐条写出评委所指的缺失事实，用原文检索键定位到**具体段落**（用线上编译同一读取与顺序重建的分段）；
2. 用 #436 重放（请求指纹与线上一致）记录的每字段第二步输入（第一步选段、carry 段、并集补段），核对这些段落**是否在该字段的第二步请求里**；
3. 再看事实是否在线上值中、是否在新值中。检索键命中但新值仍含近似文字的 9 条，逐条人工核对，确认缺的确实是那处细节。
   检索键是正则，命中不等于语义真值；9 条近似命中的判断依赖具体条件或分支。

| 归类 | 条数 | 含义 |
|---|---|---|
| A 不在第二步输入 | 4 | 含该事实的段落既没被第一步选中，线上值的证据引文也没引用它，carry 无从传入 |
| N 线上值也没有 | 1 | 新增字段（add），不是"丢了线上事实" |
| 丢了线上事实 | 48 | 段落在该字段的第二步输入里，线上值有这条事实，新值没有 |
| 其中：长旧值中的细节遗漏（线上值 ≥ 1500 字） | 20 | 疾病释义、疾病名单、费用范围等长枚举；其中 8 条的新值比线上值更长 |
| 其中：概括变短（新值 < 线上值 80%） | 12 | |
| 其中：事实只在 carry 段里，被忽略 | 8 | |
| 其中：长度相近，丢了某个条件 | 8 | |

观察（不是唯一根因的证明）：

- 48 条中有 47 条，线上值自己的证据引文用同一检索键也能命中该事实。也就是说，已审核过的事实及其原文都在第二步输入里，新值仍然把它丢了。
- "长旧值"一类按线上值 ≥ 1500 字划分，其中 8 条的新值反而比线上值长（例如 1816 `disease_definitions_and_criteria` 8069 → 18491 字，
  仍漏掉某病种对应的免责例外）。所以这一类描述的是"长旧值中的细节遗漏"，不是"被压缩"。
- 值协议已有"列全……不得概括，不得用'等'省略"的要求，但这不能排除指令执行、上下文长度、任务难度或抽样的影响。
- 一个可干预的输入差异是：第二步看不到已审核的线上值（S12c-4 只传引文、不传旧值），每次从头重写。本片对这一点做干预，
  §8 的消融只说明这次干预在所测样本上的效果，不证明它是唯一原因。

## 2. 机制

### 2.1 carry 同时传已审核值

`carry_for` 在记录引文的同时，记录每个被 carry 的字段的已发布值（`Carry.values`）：只取本产品、本字段、
所有引文都是本次编译材料的 present Claim（与引文同一筛选，不另设口径）；同一字段多条 Claim 时按 logical key
排序、换行拼接；非字符串值用规范 JSON。`Carry.digest` 在有值时把值一并算入（引文相同、值不同即视为不同输入）；
只有引文、没有值的 Carry 摘要与 S12c-4 相同。

### 2.2 何时交给第二步

`SchemaFieldsCompiler.compile(reviewed=...)` 只在同时满足以下条件时，把已审核值交给该字段的第二步：

1. 第一步判该字段 present（unknown/absent 照旧，不抄旧值）；
2. 该字段的每条 carry 引文都能在本次分段中唯一定位（`locate` 非空）；
3. 定位到的段落没有一个属于该字段不可用的受限表头段（与 carry 同一 TrustPolicy 规则）。

满足时，第二步请求中该字段附 `reviewed_value`（已审核值）与 `reviewed_segments`（它的证据引文定位到的段落，按条件 2、3
必然都在该字段的给定段落中）。任一条件不满足即不传值，退回现状。

注意：传值时，已审核值里可能有它的证据引文没有覆盖的内容（§8 的 1816 医院定义就是一例）；这类内容是否被写入，只取决于模型是否
遵守 §2.3"给定段落不支持的内容不写入"，没有确定性检查。

### 2.3 第二步规则

只在请求里至少有一个字段带 `reviewed_value` 时，在值协议系统提示末尾追加以下规则（原样）：

```
部分字段附有 reviewed_value：本产品本字段上一版经审核发布的值；
reviewed_segments 是它的依据段落，都在本字段的给定段落中。
reviewed_value 只是参考，事实以给定段落为准：
reviewed_value 中给定段落仍然支持的事实，value 必须保留，不得删减其中的数值、条件、例外、期限与适用对象，可以调整措辞与顺序；
给定段落与 reviewed_value 不一致的，以给定段落为准；给定段落不支持的内容不写入；
按上面其他规则不应写入的内容（如属于其他字段的内容、与条款冲突的说明书说法），即使出现在 reviewed_value 中也不写入；
给定段落中有、reviewed_value 中没有的本字段内容，要补充进 value。
```

没有任何 `reviewed_value` 的请求（首次编译、无 carry、所有字段都不满足 §2.2）与协议 2026-10-29.3 **逐字节相同**，
旧的重放仍然有效。

### 2.4 身份

`VALUE_PROTOCOL_VERSION` 升到 `2026-10-29.4`。carry 摘要随值变化（§2.1）。

证据规则沿用 S12c-4 §2.3（`engine._used_carried`，本片未改）：第一步选段始终进证据；carry 段与并集补段中，第二步在
`used_segments` 里声明、且能解析为给定段落的进证据；`used_segments` 缺失、为空或没有任何可用编号时，兼容回退为保留全部已提供的
carry/并集段。声明与回退都不能证明模型在语义上用了这些段落。已审核值本身不是证据。

## 6. 风险

- **照抄与固化旧问题**：消融中 t 的新值与线上值逐字相同的比例为 75%（基线 8%，口径见 §8）。照抄本身不算错，但线上值原有的
  遗漏与串字段会被保留（§8：评委审到的照抄字段里 16 个遗漏、5 个属于其他字段）。与线上值等价的新值在 `changes/decision.py`
  中判 UNCHANGED（材料撤回时 REFRESH），不产生可发布变更，也不进评委批次；所以已经在线上的串字段不会因为"观察本轮变更点的
  评委拒绝比例"而被发现或改正。
- **Owner 对"已审核值是否服从字段卡"的回答（2026-10-29）**：已审核值同样服从字段卡 excludes 与本字段定义，§2.3 规则已写明
  （"按上面其他规则不应写入的内容……即使出现在 reviewed_value 中也不写入"），不再加同义句。本机制没有确定性的事实归属检查，
  不能认定它或评委足以清除旧错误。对已保留线上值的语义纠偏是后续切片的范围：它要覆盖这些保留值本身，不能只看本轮变更点，
  记为 S12c-9（#442）的依赖。
- **请求变长**：带值的字段多出已审核值的长度，批次字符估算没有计入。实际输入超过模型配置的 `max_input_chars` 时，
  客户端报类型化的 `InputTooLarge`，不发送；这只是失败关闭，不解决长上下文下的质量问题。
- **回退**：恢复 S12c-7/6b 的代码只影响之后的编译，不回退已发布内容，也不改写已有候选。

## 7. 上线

协议身份变化后，旧输出不能复用，下一次重编的每条内容仍按 `changes/decision.py` 的顺序判定：无线上值 ADD；新值缺失时，材料已撤回且非专家锁定
RETRACT、否则 KEEP；专家锁定且不等价 CONFLICT；等价 UNCHANGED（材料撤回时 REFRESH）；线上为 unknown 时 FILL；材料撤回时
SUPERSEDE；**没有新材料且编译器身份不同**才判 UPGRADE；其余情况新值为 unknown 时 KEEP、没有新材料时 KEEP、有新材料时 CONFLICT。

普通路由加载默认 review_policy v3（准入 pack 为空），升级为 unknown 的内容（`review/routing.py` 的 `UPGRADE_TO_UNKNOWN`）进人工队列；评委批次 → 机器通道是用户另行授权的运维路径，
与普通路由分开。本 PR 不改准入、不部署，不保证新输出会发布。回退本协议只影响之后的编译，不改写已有候选，也不回退已发布 Release。

上线观察：下一轮按 pack 对比"遗漏关键内容"拒绝比例与 #436。由于等价值判 UNCHANGED 不进评委批次，这个观察只覆盖发生变化的点。

单一评委模型（GPT-6 Astra）的代理判定；同一生产模型、四款产品。这些结果不能代替整体质量结论或 pack 准入。
