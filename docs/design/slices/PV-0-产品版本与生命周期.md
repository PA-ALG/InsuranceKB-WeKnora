# PV-0 产品版本与生命周期（设计）

> 状态：设计稿（2026-11-01，Claude），待 Codex 设计审核。跟踪 Issue 见 PR 描述。
> 本片只写设计，不改代码；真实调用 0。实现按 §9 的 PV-1–PV-4 分片进行，每片开工前补 RED。
> 依据：用户 2026-11-01 两条裁定（§0）；蓝图 §5.1、§6.5、§7.3、§7.8；S5b-1、S11c Spec；平安在售/停售仓库元数据统计（§1）。

## 0. 背景与用户裁定

批次一接入与 Office 端到端时暴露出：我们的产品登记没有“版本、年份、销售期、在售/停售”的概念，而业务材料
（尤其销售与培训材料）通常只写“产品品牌 + 年份”。用户 2026-11-01 的两条裁定：

1. **培训材料与产品严格按年份/版本对应**："这个是严格对应的年份的"。例：一份 2024 年的税优护理险培训材料，
   只能对应 2024 年在售的那个版本（2635-1 平安智盈倍护终身护理保险），不能挂到后来的 2648-1 平安智盈倍护（2026）
   终身护理保险上。
2. **方案 A**：培训材料按“品牌 + 年份/日期”只匹配到**唯一**一个已登记版本、年份或日期明确、类型词不冲突时，
   **自动归属**，记为机器结论；零个或多个候选时交人，并在待确认材料页给出候选与依据。这**修订 S11c §2.5 第 4 条**
   “即使只有一个候选也不自动归属”。

另一条既有底线在本设计中继续成立：**内容锚点优先**——条款编号、首页标题与文件夹或清单冲突时一律以内容为准。
仓库确有放错的文件（L3223 文件夹里放的是另一款附加门诊急诊医疗险的产品说明书）。

## 1. 事实（平安在售/停售仓库元数据，只读统计）

数据：`PA-ALG/pingan-life-product-documents` 全部 1841 个 `product_meta.json` 与在售/停售两份 `products_manifest.csv`
（2026-11-01 稀疏检出，统计脚本在仓库外）。

| 事实 | 数值 |
|---|---|
| 文件夹 = 一个报备版本，键 `planCode-versionNo`（如 `2635-1`） | 1841 个（在售 338、停售 1503） |
| 每个版本都有起售日 `startDate`；停售版本都有停售日 `endDate` | 1841 / 1503（在售 0 个有 `endDate`） |
| 产品编码 `planCode`；有多个版本（同编码重新报备）的编码 | 1342 个；324 个（每个 2–8 个版本） |
| 同编码相邻版本：上一版停售日 = 下一版起售日 / 名称完全相同 | 499 对里 496 / 497 |
| 条款报备号 `sccode`：在售全有；停售缺失；被多个版本共用 | 停售缺 157 个；10 个号被共用 |
| 名称带四位年份标签（2026）/（2026Ⅱ） | 在售 70、停售 354（在售 338 个名称里只有 74 个带年份，含 4 个“版26”式） |
| 年份标签与起售年的关系 | 相同 235 例；**标签 = 起售年 + 1** 73 例（“（2026）”多在上一年第四季度上市） |
| 同一品牌系列同时在售多个名称（如 e生保 6 个、御享金越 5 个） | 65 个系列 |
| 每年新增版本 / 停售版本 | 100–200 / 75–200（2025 年 189 / 84） |
| 名称中的其他限定 | 附加 877、版别（悦享版、A款…）167、渠道前缀“创” 9、分红型 246、万能型 73、税优 1 |

结论：

- **版本是天然单位**：仓库按报备版本组织，每个版本有自己的名称、条款号、销售期；同名产品会因重新报备换版本（例：
  1733 平安御享金越终身寿险 1733-1 2023-11-01→2024-01-11，1733-2 2024-01-11→2024-09-01，条款号不同）。
- **名称里的年份不可靠**：多数名称没有年份，有年份的也常比起售年晚一年。“产品 + 年份”必须结合**销售期**判断。
- **同一品牌并行变体多**：只凭品牌与年份常有多个候选，需要类型词（分红、万能、附加、税优、险种）收窄，仍不唯一就交人。
- 本次涉及的四类私有培训材料（只在本机读取，GitHub 只作抽象描述）：
  - 2024 年的税优护理险培训材料 → 唯一对应 2635-1（〔2023〕护理保险088号，2024-04-23→2024-09-01，已停售）；
  - 2023 年的某分红型终身寿险培训材料 → 两个并行版本（普通型、分红型，同一销售期）都对得上，需人定；
  - 2024 年的百万医疗培训材料两份 → 对应 2024 年在售的主险版本及其附加险，现登记的同系列版本均为 2025-09 以后上市，不对应；
  - 综合集训手册（Word、Excel）→ 覆盖多款产品，不挂单一版本。

## 3. 模型

### 3.1 产品版本（事实与材料的挂载单位）

一个报备版本 = 一个登记条目 = 一个发布的产品实体。字段（登记表 v2，均可为空的标注“可空”）：

| 字段 | 来源 | 说明 |
|---|---|---|
| `product_id` | 不变 | 现有 id（planCode 或 `sc-…`）保留，Release slug 依赖它 |
| `version_key` | 仓库 `planCode-versionNo` | 新条目的首选标识；仓库里查不到时可空，以条款号为准 |
| `plan_code`、`version_no` | 仓库 | 可空 |
| `names`、`clause_codes`、`schema_pack_id` | 不变 | `clause_codes` 仍是内容锚点 |
| `sale_start`、`sale_end` | 仓库 `startDate` / `endDate` | 半开区间 `[start, end)`，日历日；在售时 `sale_end` 为空 |
| `sale_status` | 由日期推出 | `on_sale` / `discontinued`；不单独存一个可能与日期矛盾的状态 |
| `year_tag` | 名称解析（数据规则） | “（2026）”“（2026Ⅱ）”“版26”→ 2026；可空 |
| `channel`、`plan_type` | 仓库 | 只作类型词匹配与展示 |
| `supersedes` | 同 `plan_code` 上一版本 | 可空 |
| `family_key` | 名称派生（§3.3） | 只用于分组与候选 |
| `metadata_source` | 仓库提交 SHA 与文件路径 | 可追溯；同步时更新 |

**销售期不是 Claim 的业务有效期**。蓝图 §5.1 的 `effective_from/to` 指条款对保单的适用期；停售只影响新单销售，
在保客户仍按原版本服务。Claim 不继承 `sale_end`。

### 3.2 产品编码链

同一 `plan_code` 的版本按 `sale_start` 串成链，后一版 `supersedes` 前一版（发布为 §5.1 的 `supersedes` Relation）。
链只表达“谁接替谁”，**不撤回旧版本的知识**：旧版本的 Claim 留在后续 Release 中，供在保客户的服务问答使用。

### 3.3 品牌系列（派生，只作分组与候选）

`family_key` 由名称按数据规则派生：沿用 S11c 的品牌核心（去公司名与“附加”“创”等前缀、去全部括号限定、去最长险种
后缀，NFKC 折叠）。它**永远不是归属锚点**，只用于：生成培训材料的候选、产品库分组展示。规则写在归属策略数据中，
不写产品编号特判。

## 4. 归属规则

### 4.1 内容锚点优先（不变）

条款编号、首页标题（S5b-1、S5b-5、S5b-7）仍是唯一能**新建**版本或**直接认定**归属的依据。文件夹、清单、下载来源只能
作辅助证据：与内容一致时可以佐证；不一致或内容没有锚点时，照旧进待确认，不得按文件夹归属（#497 已据此修订）。

### 4.2 新版本不再替换旧版本（修订 S5b-1）

同名、新自有条款号的条款到达时：

- 现在：`NEW_VERSION / new_clause_code`，旧条款材料移入 `retired`；
- 改为：新建一个版本条目（`version_key` 从仓库元数据按条款号查得，查不到时用 `sc-` + 条款号），记 `supersedes` 指向
  原条目；原条目的材料与已发布知识**保留不动**；后续到达的说明书、费率表按其内容锚点归属到对应版本。
- 线上 27 条的 `retired` 全空，此项无存量迁移。

### 4.3 培训材料按“品牌 + 年份/日期”归属（方案 A，修订 S11c §2.5 第 4 条）

适用范围：`brand_roles` 中的角色（销售/培训类）与无法识别角色的 Office 文件——与 S11c 相同，**不扩展到条款、说明书、
费率表**。

1. 材料信号（只读材料本身，数据规则）：
   - 品牌：文件名或开头窗口含某版本 `family_key` 的前缀（S11c 规则不变）；
   - 年份/日期：开头窗口或文件名中的年份，或落款日期（如“20xx年x月”）；
   - 类型词：分红型、万能型、附加、税优、护理、年金、终身寿险、两全、医疗……（策略数据中的词表，与险种分类一致）。
2. 候选：同一品牌系列中，满足任一条件的**已登记版本**——`year_tag` 等于材料年份；或材料日期落在 `[sale_start, sale_end)`；
   再用类型词收窄（材料出现的类型词与版本名称、`plan_type` 矛盾的去掉）。
3. 判定：
   - **恰好一个候选**、材料年份或日期**明确**、类型词**不冲突** → 自动归属到该版本，`outcome` 为 `SUPPLEMENT`，`reason`
     为 `matched_by_version_period`。这是**机器结论**：`DecisionEntry` 不带 `confirmation`，页面与报告显示“机器判断”，
     不记成人工确认；
   - 零个或多个候选 → `NEEDS_CONFIRM`（或无品牌时 `QUARANTINE`），页面列出排好序的候选与依据（“材料日期 2024-05，
     2635-1 销售期 2024-04-23→2024-09-01”、命中的类型词），人选择或忽略；
   - **严格对应**：材料从不归属到年份或销售期都对不上的版本，即使同一系列只有那一个已登记版本。
4. 正确版本尚未登记时：判定为零候选并交人；PV-2 同步得到的仓库清单若有唯一匹配的未登记版本，页面附一行“可先登记
   `planCode-versionNo` 名称（销售期）”的建议。登记仍走正常接入（下载该版本的条款、说明书、费率表，按内容锚点新建）。
5. 角色：自动归属还要求材料角色已确定为 `brand_roles` 中的角色。S11c 的私有离线端到端里 Office 文件的角色识别为 0，
   因此 PV-3 同时补“培训/销售”角色信号（封面或标题中的“培训”“学习课程”“销售方法”“话术”等，词表为数据）；仍识别不出
   角色时，版本已唯一匹配的材料只问角色一个问题（候选版本已定，页面写明依据），不再问版本。
6. 方案 A 的风险边界：`sales_training` 角色只作 4 个销售类字段的证据（S11c TrustPolicy 不变），仍经评委与抽检；
   误归可由“解除归属”回退（登记表移除材料、下一轮编译撤回对应 Claim）。

## 5. 生命周期

### 5.1 主数据同步（PV-2）

- 来源：平安仓库固定提交的两份 manifest 与 `product_meta.json`（或日后官网导出），提交 SHA 写进同步报告。
- 输出差异：新版本、停售（新增 `endDate`）、改名、条款号变化。
- 已登记版本：`sale_end` / `sale_status` 等元数据变化直接更新登记表（机器、留记录），**不触发重编**；下一次发布时实体属性随之更新。
- 新版本：只生成“待接入建议”，由批次接入决定是否下载、编译（控制成本）；同编码新版本接入后自动补 `supersedes`。
- 频率：建议每周一次，手动触发；同步本身零模型调用。

### 5.2 停售不删知识

停售版本的知识继续留在 Release 中，页面与问答标注“已停售（YYYY-MM-DD）”。

### 5.3 问答

- 销售类问题（推荐、对比、能不能买）默认只用在售版本；
- 服务、理赔、保全类问题按客户持有的版本回答；无法判断时追问投保时间或产品全称；
- 回答引用的产品标注版本名称、销售期与在售/停售。
- 首个落地（PV-4）：检索默认带在售过滤，问题点名停售版本名称或给出投保日期时放开；意图分类细化另行排期。

### 5.4 页面

产品库按品牌系列分组，组内列版本（名称、年份标签、销售期、在售/停售标签），默认只显示在售，可切换“含停售”。版本页
显示 `supersedes` 前后版本的链接。

## 6. 迁移现有 27 条（PV-1）

- 按条款号（`clause_codes`）到仓库 manifest 逐条匹配，补 `version_key`、`plan_code`、`version_no`、销售期、`year_tag`、
  `family_key`、`metadata_source`；零模型调用、确定性、可重放。
- 匹配不到或一号多版本（仓库中 10 个条款号被共用）时不猜：字段留空，报告列出，人工决定。
- **id 不变**：种子条目的 id 本就是 planCode；`sc-` 条目保留 id，新增 `plan_code` 字段。Release slug 不变。
- 登记表合同升为 `product-registry.v2`，读取 v1 时一次性迁移并写回；迁移前备份。

## 7. 数据与代码的边界

- **数据**（版本化策略文件）：品牌前缀、险种后缀、年份标签模式、材料日期模式、类型词表、同步来源配置、问答默认过滤。
- **代码**：登记表 v2 结构与迁移；同步命令（差异与建议）；候选生成与排序；Release 实体属性与合同；页面分组与问答过滤。
- **守卫**：不按产品编号、品牌名或样例文件写特判；文件夹/清单只作辅助证据；品牌永不单独作锚点（方案 A 也要求年份或
  日期明确且候选唯一）；机器结论与人工结论分开记录。

## 8. 风险

| 风险 | 应对 |
|---|---|
| 年份标签与起售年错位（73 例） | 候选同时看 `year_tag` 与销售期，任一命中即候选；两者都对不上不归属 |
| 同系列并行变体多（65 个系列） | 类型词收窄；仍不唯一交人 |
| 老版本缺条款号（157）或条款号共用（10） | 版本键用 `planCode-versionNo`；迁移时不猜 |
| 仓库文件放错 | 内容锚点优先；放错的文件按内容判定（通常被隔离） |
| 方案 A 误归 | 只影响销售类字段；评委与抽检兜底；可解除归属回退 |
| 培训材料覆盖多款产品（综合手册） | 首期不挂单一版本（忽略）；“一份材料挂多个版本”另行设计 |
| 仓库爬取过期或缺失 | 同步报告写来源提交与时间；缺失字段留空，不阻断现有流程 |
| PV-4 给 Claim 填 `product_version_ref` | 全部成员 digest 变化，需一次全量发布（零模型调用）；与正常编译轮次错开 |
