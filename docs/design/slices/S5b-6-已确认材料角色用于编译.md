# S5b-6 · 已确认的材料角色用于编译

> 状态：Claude 2026-10-28 提出 ｜ 作者：Claude Code
> 实现方：Claude ｜ 审核方：Codex ｜ 真实模型调用：0 ｜ 数据库迁移：无

## 1. 问题

2026-10-28 线上重编译时，2647（sc-0e2c537610）在发送任何请求之前就失败了：`SourceMapError: MATERIAL_ROLE_UNRESOLVED`。

- 原因：它的 `费率表.pdf` 实际是一份"转换标准表"。文件名里有"费率表"，但开头文字里没有"费率表/金额表"。S4i 的角色识别要求文件名和开头两处信号都命中，所以认不出角色。
- 但登记表里这份材料的角色已经是 `rate_table`：用户 2026-10-27 在待确认页面选了"作为费率表"，同步后记入登记表。
- 编译和发布读材料时只按页面重新识别，没有用登记表里已经确认的角色，所以这个产品永远编译不了。

## 2. 规则

**登记表记录的材料角色，在编译和发布时为准**；只有没有记录角色时，才按页面识别（S4i 规则不变）。

- 来源映射的每一项（`SourceEntry`）新增可选字段 `role`。`ProductRegistry.source_map()` 把每份材料登记的角色带上；手写的来源映射文件不写 `role` 时，行为与现在相同。
- 读材料时，每份文件的角色按下面的顺序确定：
  1. 来源映射里有 `role`：用它。如果它不是材料角色目录中的角色，报 `MATERIAL_ROLE_UNKNOWN`，整批停止。
  2. 没有：按页面识别。仍然认不出时报 `MATERIAL_ROLE_UNRESOLVED`，整批停止（失败关闭，不变）。
- 角色确定之后的用法不变：能否作为证据由角色的 `evidence` 决定；表头输入按信任策略的 `header_rules` 取。

**记录的角色与页面识别不一致时，以记录为准。** 理由如下：

- 登记表里的角色，要么是人确认的（待确认答复），要么是登记时按同样的 S4i 信号识别并留档的。它是有审计记录的决定。
- 材料本身没有变（同一个 knowledge 和 parse attempt）；页面识别结果变化，只可能是因为角色目录改了。如果因此悄悄改变一份已确认材料的用途，就违反了"人确认的事不被自动推翻"。
- 要改一份材料的角色，应当通过待确认流程重新确认，不能在编译时临时推断。

## 3. 改动范围

- `harness/src/insurance_harness/ingest/source_map.py`：`SourceEntry.role`；`_read_sources` 收集记录的角色，并传给 `load_pages` 和 `load_trusted_pages`；
- `harness/src/insurance_harness/identity/material_roles.py`：`document_roles`、`evidence_pages` 接受记录的角色；
- `harness/src/insurance_harness/catalog/trust_policy.py`：`trusted_pages` 接受记录的角色；
- `harness/src/insurance_harness/ingest/registry.py`：`source_map()` 带上角色；
- 测试。

不改平台、`contracts/`、登记表格式、角色目录和信任策略。

## 4. 验收（RED，受保护）

`harness/tests/ingest/test_recorded_material_roles.py`，全部离线：

1. 页面认不出角色、但记录为 `rate_table` 的文件：读材料成功，不作为证据，并作为 `premium_payment_term` 的表头输入。
2. 同一文件没有记录角色：仍报 `MATERIAL_ROLE_UNRESOLVED`。
3. 记录角色与页面识别不一致（页面像说明书，记录为条款）：按记录的条款处理。
4. 记录了目录中不存在的角色：报 `MATERIAL_ROLE_UNKNOWN`。
5. `load_pages`（只取证据页的路径）同样使用记录的角色。
6. `ProductRegistry.source_map()` 带出登记的角色；不带 `role` 的来源映射 JSON 仍能加载，行为不变。

受保护的 `tests/ingest/test_registry.py` 中有三处断言写死了不带角色的来源映射。本切片有意让来源映射带上角色，所以这三处需要更新期望：单独提交，断言意图不变。
