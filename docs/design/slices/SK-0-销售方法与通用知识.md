## 0. 背景与方向

接入培训材料时出现一类材料：讲的是**销售方法**——按人生阶段做家庭保障需求分析的讲解步骤、讲解逻辑与关键句，
转保沟通的步骤，异议应对，促成方法等。它们不是某个产品版本的事实：硬挂到一个产品上不对（PV-0 已规定培训材料与产品
严格按年份/版本对应，综合手册不挂单一版本），直接忽略又浪费。用户 2026-11-01：

- “这些内容虽然不是挂在某个版本上，但里面这些销售经验其实是有价值的……是不是可以关联到某些地方，比如这些方法其实是
  适合某类保险（分红、重疾、医疗等等）的销售的”；
- “知识分客观知识、也有一些销售技巧，技术、方法论这些其实并不一定过期”。

由此确定的方向（本 Spec 不再重新请求确认）：

1. 知识分两类：**产品事实**（按版本、严格对应年份，现有链路）与**方法知识**（销售技巧、讲解方法、方法论；不挂版本，
   不自动过期）。
2. 方法知识关联到**适用范围**（险种类别、产品形态如分红型、客户场景/人生阶段、销售环节），不关联到产品版本。
3. 蓝图 §2.4 把“销售经验、培训材料”列在第三期；本设计按用户要求**提前试点**销售方法这一类（§14 记录），其余培训类
   知识（核保、理赔培训等）仍按原分期。
4. **可见范围**（用户 2026-11-01）：首期与产品知识一样，**整个 Space 可见**，现在不做按角色的权限（§3.5）。
5. **话术中的产品信息**（用户 2026-11-01）：**原样保留**，显示来源材料日期，并提示“以条款与已发布知识为准”；**从不**
   作为产品事实发布（§3.2）。

## 1. 两类知识

| | 产品事实（版本知识） | 方法知识（非版本知识） |
|---|---|---|
| 内容 | 某个报备版本的条款事实与四个销售字段（S11c） | 销售方法、讲解步骤与逻辑、关键句、异议应对、促成、转保沟通 |
| 挂载 | 产品版本（PV-0：`planCode-versionNo` 对应的登记条目与发布实体） | 方法实体，按适用范围关联，**从不挂版本** |
| 年份 | 严格对应（PV-0 §0.1） | 不需要对应；显示来源材料日期 |
| 时效 | 随版本销售期与有效期 | **不自动过期**；只有更新的指导明确接替（`supersedes`）或人工复核撤下时才不再作为当前方法 |
| 证据 | 条款/说明书原文（费率表按 TrustPolicy） | 培训材料原文块（Office/PDF locator） |
| 标注 | 已发布知识（审核过） | “销售方法（培训材料，非产品事实）” |

**同一份材料可以两边都贡献**：一份课件按 PV-3 唯一匹配到某个版本时，其中关于该产品的话术进入该版本的四个销售字段
（S11c，范围不变）；其中通用的方法部分**同时**进入方法知识。匹配不到版本的材料（多个并行版本、版本未登记、综合手册）
不再因此被整体丢弃：方法部分照样进入方法知识，产品事实部分不发布。

**客观知识里的“数据”**（如人群统计、行业数据）随方法一起出现时，按“引用数据”处理：保留原话、标来源材料与日期，不由
模型补充或更新数字；它们会过时，所以页面显示日期（§3.3），但不因此让方法本身过期。

## 2. 方法知识的单元

### 2.1 实体与字段

- **实体**：`entity_type = "sales_method"`（Entity 合同的 `entity_type` 是 Catalog 配置的字符串，无需改合同）。
  `entity_id` 由方法键确定（`sm-` + 规范化方法键摘要，与 PV-0 内部 ID 规则同类，确定、可去重）；`names` 为方法名，
  `aliases` 收录不同材料里的叫法（合并时累积）。
- **事实**：方法的各个方面作为 Claim 发布在该实体上（`product_version_ref` 为空——蓝图 §5.1 只对“产品特定事实”必填），
  谓词为方法卡（数据，`catalog/method_cards.json`，与字段卡同构）中的固定几项：

  | 谓词 | 内容 | 值类型 |
  |---|---|---|
  | `method_summary` | 这个方法解决什么问题、核心逻辑（一两句） | 文本 |
  | `method_steps` | 讲解或操作步骤（有序列表），每步一句 | 有序列表 |
  | `key_phrases` | 材料中的关键句/示范话术（逐字引用） | 列表 |
  | `applicable_scenario` | 适用的客户情形与时机（文字说明） | 文本 |
  | `cautions` | 材料写明的注意事项、禁忌 | 列表 |

  每个 Claim 的每一项都带 Evidence（逐字引文 + 原文块 locator），沿用 S12 第二步的“段落编号 → 引文”机制与 S11 的块切分
  （证据不跨块）。没有原文支撑的方面不发布（`unknown`，带原因），**不由模型补写**。
- **来源分类**：`SOURCE_SUPPORTED`（来自培训材料原文）。材料角色为 `sales_method`（新角色，§4.1），TrustPolicy 规定该角色
  **只能作为方法卡谓词的证据**，与 S11c 的 `sales_training`（只服务四个销售字段）分开，互不放宽。

### 2.2 适用范围（版本化数据，不是代码）

适用范围用 `classification_labels` 表达——这是导航按“领域 → 险种分组”匹配实体时已经在用的机制（蓝图 §14 2026-10-18；
`catalog/navigation.json`、Go `knowledge/index.go` 按 `entity_types + classification_labels` 匹配），不新增匹配逻辑：

| 维度 | 标签形式 | 取值来源 |
|---|---|---|
| 险种类别 | 与 SchemaPack 分组相同的标签（如 `critical_illness_insurance`、`medical_insurance`） | `schema_packs` 现有标签 |
| 产品形态 | `plan_type:participating` / `universal` / `ordinary` / `unit_linked` | 新词表 `catalog/sales_taxonomy.json` |
| 客户场景/人生阶段 | `life_stage:single` / `family_formation` / `family_growth` / `mature` / `retirement` 等 | 同上 |
| 销售环节 | `sales_stage:approach` / `needs_analysis` / `presentation` / `objection` / `closing` / `transfer` / `after_sale` | 同上 |
| 通用 | `scope:general`（不限险种） | 同上 |

- 一个方法可以有多个标签（如同时适用于重疾与医疗）；词表带版本，变化只影响分组与检索，不进入编译任务键（蓝图 §6.1）。
- **品牌系列**：材料只针对某个系列的方法，用 Relation `relates_to_product_family`（`to` 为 PV-0 的 `product_family.key`），
  只作“相关产品”导航；**从不**指向产品版本或产品事实。
- **概念**：方法涉及已有概念（如“等待期”“保证续保”）时用既有 `relates_to_concept`。

## 3. 底线

1. **方法知识不产生产品事实**：方法 Claim 不写入、不修改任何产品版本的 Claim；问答回答产品事实只用产品 Claim。
2. **方法里出现的产品信息**（价格、保额、年龄、比例、责任描述；用户 2026-11-01 裁定，§0.5）：不抽成事实，不替换、不删改；
   在关键句里**原样保留**，显示来源材料日期，页面在该方法上方固定提示“以条款与已发布知识为准”。确定性检查：方法 Claim
   的值里出现货币金额、百分比、年龄区间与已登记产品名/品牌同句时，该成员不走机器上线，进人工队列（审核标注“含产品信息”），
   人工确认的也只是“作为话术原文展示”，不生成任何产品 Claim。
3. **引用数据**：统计与外部数据只能原话引用并带来源材料与日期；模型补充（`MODEL_GENERATED`）不允许出现数字。
4. **不过期但可接替**：新材料里同一方法（同方法键）有更新的说法时，以新成员 `supersedes` 旧成员；旧成员保留可读并标
   “已有更新版本”。没有接替时永远是当前方法；人工可撤下（复用 S5b 的撤回/`detach` 机制与专家编辑，不新建流程）。
5. **访问范围**（用户 2026-11-01 裁定，§0.4）：首期整个 Space 可见，方法成员 `access_scope="space"`，与产品知识相同，
   沿用蓝图 §7.5 与 §14 2026-10-17 的会话只读规则；现在不做按角色（如只对销售/培训人员）的权限。以后若要收窄，需要平台
   按角色分权，另开设计与切片。
6. **私有材料**：试点用的业务样本只在线上与本机处理；仓库、Issue、PR、日志只作抽象描述，不写文件名、标题、引文或截图。

## 4. 接入与归属

### 4.1 材料角色

- 新角色 `sales_method`（`identity/material_roles.json` 数据）：名称与开头信号为方法类用语（如“销售方法”“讲解步骤”“讲解
  逻辑”“关键句”“需求分析”“异议”“促成”“转保”“实操”，词表为数据）。与 `sales_training` 的区别：前者讲**怎么卖、怎么讲**，
  后者是某产品的话术与 Q&A。一份材料可同时带两种信号——这正是“两边都贡献”的情形：角色记为主角色，方法抽取按内容块
  进行，不依赖主角色（§5.2 只从命中方法信号的块抽取）。
- `evidence: false`（不进入普通证据），TrustPolicy 新增范围规则：`sales_method` 只服务方法卡谓词。新增角色不得改变任何
  现有材料的识别结果（以数据集全部材料回归，同 S11c）。

### 4.2 新的归属结果：方法材料

在 PV-0/PV-3 的判定之后增加一步（顺序：强内容锚点 → 方案 A 版本匹配 → 方法材料）：

| 情况 | 结论 |
|---|---|
| 唯一匹配某版本（PV-3） | 照旧挂版本；若含方法信号，**另外**登记为方法来源（同一材料两种用途，各自记录） |
| 无版本可挂（`no_registered_version`、多系列、综合手册、版本歧义且未由人选定）且含方法信号 | 新结论 `METHOD_MATERIAL`：挂到“销售方法”领域，不再隔离 |
| 既无版本也无方法信号 | 照旧隔离（`no_product_anchor` 等），可忽略 |
| 日期信号互相矛盾（PV-0 §4.3） | 不影响方法材料判定——方法不需要年份；但不挂任何版本 |

- **险种类别候选**：确定性词表（数据，`sales_taxonomy.json`：如“重疾”“医疗/百万医疗”“年金/养老”“分红”“终身寿”“意外”
  “护理”）在材料中的命中给出候选标签；命中唯一一类或明确写“通用”→ 自动打标签（机器结论）；命中多类或一类都没有
  → 交人选择，记人工结论。人生阶段与销售环节标签在方法抽取时按方法逐个判定（§5.2），不在材料级别询问。
- **确认页**：新问题类型“方法材料：选择适用范围”。现有确认页是单选（S5b-3a 通用待确认项）；首版不改为多选，选项为：
  系统建议的类别组合 / 通用（不限险种）/ 各单一类别 / 忽略。“忽略”语义不变：这份文件不再参与归属与抽取。多选留待
  页面需要时另做。
- **重判**：现有被隔离的此类材料（综合手册、版本未登记的课件）在 SK-1 上线后按 S5b-7 的重判路径重新判定，旧问题按
  “已过时”关闭，不记为人工答复。

## 5. 抽取与准入

### 5.1 候选来源：原生 discover/cite

按蓝图 §7.2，开放知识的候选来源是 WeKnora 原生 discover/cite，Harness 不恢复自有发现路径：

- 方法材料放入专门的方法发现库（与 S6c 的产品发现库同一机制，但按领域而不是按产品组织；只放 `METHOD_MATERIAL`
  与带方法信号的材料）；原生 Wiki 生成候选页面（模型与思考模式按现行配置，DeepSeek）。
- 候选页面**不直接发布**（S6c 的 `wiki_page` 是另一条路径，本设计不复用其发布）。

### 5.2 Harness 准入（身份、去重、结构化、引文）

1. **身份**：从候选页提取方法名，规范化为方法键；与已发布方法按名称/别名比对——同键合并（证据与别名累积），相近但不同的
   不合并（只在名称规范化后完全相同或别名命中时合并；拿不准时作为新方法，并在审核标注“可能重复”）。
2. **结构化 + 引文**：对每个候选方法，在其来源材料的块（S11 块切分）上用方法卡做一次取值（与 S12 第二步同构：给定方法卡
   与带编号段落，返回各谓词的值与段落编号）。值的每一项必须能在所引段落中逐字找到（关键句）或被所引段落支持（步骤、
   摘要）；平台按 S11d 回验引文。
3. **标签**：险种类别继承材料级结论（§4.2）；人生阶段、销售环节由同一次取值返回候选标签，必须落在词表内，并各自带支撑段落；
   不在词表内的丢弃。
4. **确定性检查**（§3.2 的产品数字检查、引文回验、空值、词表）不过 → 不发布，生成 ReviewItem。
5. **发布**：同一 CandidateBundle 带方法实体、方法 Claim、Relation；`origin=compile`；审核走 ReviewPolicy，方法类单独一个
   “pack”（`methods_sales`）门槛，未准入前一律进人工队列（与产品 pack 准入同一纪律，蓝图 §6.3）。

### 5.3 预算估计（试点）

| 环节 | 估计 |
|---|---|
| 原生 discover（6 份材料的方法部分） | 约 20–40 次 DeepSeek（按块组生成） |
| 准入取值（每个候选方法 1 次） | 约 40–60 次 DeepSeek |
| 独立审核打分（每个方法 1 次，deepseek-flash） | 约 40–60 次 |
| 离线评判（GPT-6 Astra xhigh） | ≤ 4 个会话 |

合计约 ≤ 160 次 DeepSeek、≤ 4 个 GPT-6 会话；SK-4 的 Issue 按实测上限再定。

### 5.4 评测（离线）

评判模型（与生产不同族，蓝图 §7.7）按方法逐个打分，量表（数据）：

| 维度 | 判定 |
|---|---|
| 忠实 | 每个步骤、关键句都能在所引原文中找到；无编造 |
| 无产品事实 | 没有把产品数字/责任当作方法结论；产品信息只作带日期引用 |
| 适用范围 | 险种、人生阶段、销售环节标签与原文一致；不过度泛化 |
| 去重 | 没有把不同方法合并，也没有把同一方法拆成多条 |
| 可用 | 步骤可执行、顺序正确，关键句完整 |

试点先请业务抽检 10–20 条作校准（与产品 Golden 同一做法），一致性达标后用于准入门槛。

## 6. 阅读与问答

- **导航**：`navigation.json` 新增领域“销售方法”（`entity_types: ["sales_method"]`），分组复用险种分组标签，另加“通用”。
  每个方法一页（由同一 Release 的数据生成，蓝图 §5.2“Schema 外知识页”）：方法名、适用范围标签、摘要、步骤、关键句、
  注意事项；每项可点开原文（S11e 的 Office 查看器 / PDF 查看器）；显示来源材料与日期；顶部标“销售方法（培训材料，非产品
  事实）”；被接替的显示“已有更新版本”。
- **产品页交叉链接**：产品页（schema_wiki 之外）显示“相关销售方法”：按产品的险种标签与产品形态匹配方法标签，另加
  `relates_to_product_family` 指向该产品所属系列的方法；方法内容**不进入**产品的字段页。
- **问答**：在现有三类来源（已发布知识 / 模型整理 / 原文检索，S6e）之外，方法成员作为“销售方法（培训材料）”来源：
  “怎么卖、怎么讲、如何应对异议”类问题先查方法；产品事实仍只从产品 Claim 回答；一个回答同时用到两类时分段标注来源。
  意图判别用问题词表（数据，同 `question_terms`）。

## 7. 合同与平台影响

- 合同：不新增合同类型。`Entity.entity_type`、`Relation.predicate`、`classification_labels` 均为字符串；方法 Claim 的
  `product_version_ref` 为空，合同已允许。若 SK-3 发现平台不变量把“无版本引用的 Claim”当作错误，在 SK-3 中按“仅非产品
  实体允许为空”收窄规则，并写明。
- 平台（SK-3）：知识索引读取 `sales_method` 实体与其 Claim；按领域/分组列出；方法页与产品页交叉链接；问答来源标注。
  只读接口、固定 Release、权限边界不变。
- 上游补丁：不新增；前端沿用 S11e 的查看器与企业模块注册方式（U-5a）。

## 8. 风险

| 风险 | 处理 |
|---|---|
| 方法与产品话术边界不清，产品信息混进方法 | §3.2 确定性检查 + 审核量表“无产品事实”维度；进人工队列 |
| 不同材料的同一方法被拆成多条，或不同方法被合并 | 只在规范化名称/别名完全相同时合并；“可能重复”标注；评测“去重”维度 |
| 原生 discover 对 Office 课件的候选质量不稳定 | 准入只认能逐字回验的方面；候选少时不补写 |
| 统计数据过时 | 只原话引用并显示日期；不让模型更新数字 |
| 访问范围 | 用户裁定首期 Space 级；需要收窄时另开设计与切片 |
