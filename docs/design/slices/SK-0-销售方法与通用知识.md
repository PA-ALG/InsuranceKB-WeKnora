## 0. 背景与方向

接入培训材料时出现一类材料：讲的是**销售方法**——按人生阶段做家庭保障需求分析的讲解步骤、讲解逻辑与关键句，
转保沟通的步骤，异议应对，促成方法等。它们不是某个产品版本的事实：硬挂到一个产品上不对（PV-0 已规定培训材料与产品
严格按年份/版本对应，综合手册不挂单一版本），直接忽略又浪费。用户 2026-11-01：

- “这些内容虽然不是挂在某个版本上，但里面这些销售经验其实是有价值的……是不是可以关联到某些地方，比如这些方法其实是
  适合某类保险（分红、重疾、医疗等等）的销售的”；
- “知识分客观知识、也有一些销售技巧，技术、方法论这些其实并不一定过期”。

由此确定的方向（本 Spec 不再重新请求确认）：

1. 知识分两类：**产品事实**（按版本、严格对应年份，现有链路）与**方法知识**（销售技巧、讲解方法、方法论；不挂版本，
   不自动过期）。
2. 方法知识关联到**适用范围**（险种类别、产品形态如分红型、客户场景/人生阶段、销售环节），不关联到产品版本。
3. 蓝图 §2.4 把“销售经验、培训材料”列在第三期；本设计按用户要求**提前试点**销售方法这一类（§14 记录），其余培训类
   知识（核保、理赔培训等）仍按原分期。
4. **可见范围**（用户 2026-11-01）：首期与产品知识一样，**整个 Space 可见**，现在不做按角色的权限（§3.5）。
5. **话术中的产品信息**（用户 2026-11-01）：**原样保留**，显示来源材料日期，并提示“以条款与已发布知识为准”；**从不**
   作为产品事实发布（§3.2）。

## 1. 两类知识

| | 产品事实（版本知识） | 方法知识（非版本知识） |
|---|---|---|
| 内容 | 某个报备版本的条款事实与四个销售字段（S11c） | 销售方法、讲解步骤与逻辑、关键句、异议应对、促成、转保沟通 |
| 挂载 | 产品版本（PV-0：`planCode-versionNo` 对应的登记条目与发布实体） | 方法实体，按适用范围标签分组，**从不挂版本** |
| 年份 | 严格对应（PV-0 §0.1） | 不需要对应；显示来源材料日期 |
| 时效 | 随版本销售期与有效期 | **不自动过期**；只因来源撤回/解除、读时权限或人工撤下而不再可见（§3.4） |
| 证据 | 条款/说明书原文（费率表按 TrustPolicy） | 培训材料原文块（Office/PDF locator） |
| 标注 | 已发布知识（审核过） | “销售方法（培训材料，非产品事实）” |

**同一份材料可以两边都贡献**（“双用途”，§4.1）：一份课件按 PV-3 唯一匹配到某个版本时，其中关于该产品的话术进入该版本
的四个销售字段（S11c，范围不变）；其中通用的方法部分**同时**进入方法知识。匹配不到版本的材料（多个并行版本、版本未登记、
综合手册）不再因此被整体丢弃：方法部分照样进入方法知识，产品事实部分不发布。

**客观知识里的“数据”**（如人群统计、行业数据）随方法一起出现时，按“引用数据”处理：保留原话、标来源材料与日期，不由
模型补充或更新数字；它们会过时，所以页面显示日期（§3.3），但不因此让方法本身过期。

## 2. 方法知识的单元

### 2.1 实体、身份与事实

- **实体**：`entity_type = "sales_method"`（Entity 合同的 `entity_type` 是 Catalog 配置的字符串，无需改合同）。
- **方法登记**：方法与产品一样在 Harness 登记表中有条目（登记表 v2 新增 `methods` 段，SK-1；不是第二套证据生命周期，
  证据仍指向原始 RAW KB 的来源修订）。每个条目：方法键、内部 ID、`names`、`aliases`、适用范围标签、来源材料集合（§4.1 的
  方法用途记录）、`suppressed`（人工撤下，§3.4）。
- **身份**：方法键 = 方法名按归属策略的同一规范化（NFKC、空白、全半角括号，复用 PV-1 的 `normal_*` 规则）；内部 ID =
  `sm-` + 方法键摘要，**一旦分配不再改变**——之后经别名命中并入的材料沿用该 ID，别名只累积不改 ID。两个候选只在规范化后
  的名称或别名**完全相同**时合并；拿不准时作为新方法并在审核标注“可能重复”，由人决定合并（合并 = 把一方的材料与别名并入
  另一方，被并入方按 §3.4 撤下）。
- **事实**：方法的各个方面作为 Claim 发布在该实体上，`subject_ref` = 方法实体 ID，`product_version_ref` **为空**（蓝图 §5.1
  只对“产品特定事实”必填；与 PV-0 附录 A §2 的接口约定见 §7）。谓词为方法卡（数据，`catalog/method_cards.json`，与字段卡
  同构）中的固定几项：

  | 谓词 | 内容 | 值类型 |
  |---|---|---|
  | `method_summary` | 这个方法解决什么问题、核心逻辑（一两句） | 文本 |
  | `method_steps` | 讲解或操作步骤（有序列表），每步一句 | 有序列表 |
  | `key_phrases` | 材料中的关键句/示范话术（逐字引用） | 列表 |
  | `applicable_scenario` | 适用的客户情形与时机（文字说明） | 文本 |
  | `cautions` | 材料写明的注意事项、禁忌 | 列表 |

  列表值的**每一项**单独关联自己的 Evidence（逐字引文 + 原文块 locator，沿用 S12 第二步的“段落编号 → 引文”机制与 S11 的
  块切分，证据不跨块）；具体合同形状（列表项与证据的对应方式）在 SK-2 的合同与 RED 中确定。没有原文支撑的方面不发布
  （`unknown`，带原因），**不由模型补写**。
- **来源分类**：`SOURCE_SUPPORTED`（来自培训材料原文）。证据角色为 `sales_method`（§4.1），TrustPolicy 规定该角色**只能作为
  方法卡谓词的证据**，与 S11c 的 `sales_training`（只服务四个销售字段）分开，互不放宽。

### 2.2 适用范围（版本化数据，不是代码）

适用范围全部用方法实体的 `classification_labels` 表达——这是导航按“领域 → 险种分组”匹配实体时已经在用的机制（蓝图 §14
2026-10-18；`catalog/navigation.json`、Go `knowledge/index.go` 按 `entity_types + classification_labels` 匹配）。标签是
**属性，不是引用**，不进入成员引用闭包（蓝图 §6.2），不新增任何 Relation 目标：

| 维度 | 标签形式 | 取值来源 |
|---|---|---|
| 险种类别 | 与 SchemaPack 分组相同的标签（如 `critical_illness_insurance`、`medical_insurance`） | `schema_packs` 现有标签 |
| 产品形态 | `plan_type:participating` / `universal` / `ordinary` / `unit_linked` | 新词表 `catalog/sales_taxonomy.json` |
| 客户场景/人生阶段 | `life_stage:single` / `family_formation` / `family_growth` / `mature` / `retirement` 等 | 同上 |
| 销售环节 | `sales_stage:approach` / `needs_analysis` / `presentation` / `objection` / `closing` / `transfer` / `after_sale` | 同上 |
| 通用 | `scope:general`（不限险种） | 同上 |
| 品牌系列（可选） | `family:<product_family.key>` | PV-0 附录 A §1.2 的分组键 |

- 一个方法可以有多个标签；词表带版本，变化只影响分组与检索，不进入编译任务键（蓝图 §6.1）。
- **品牌系列**：不建系列实体，也不发 Relation（PV-0 附录 A §1.2 只发布报备版本的 `product` 实体，`product_family` 是其属性，
  Release 中没有可指向的系列成员）。方法针对某个系列时打 `family:<key>` 标签；读取侧（SK-3）把它与同一 Release 中产品实体
  的 `product_family.key` 属性对上，作“相关销售方法”交叉链接。PV-4 之前产品实体还没有该属性，交叉链接只按险种标签。
- **概念关联**：首期不发 `relates_to_concept`（目标概念实体是否在同一 Release 中由概念切片决定，首期不引入跨切片引用）。

## 3. 底线

1. **方法知识不产生产品事实**：方法 Claim 不写入、不修改任何产品版本的 Claim；问答回答产品事实只用产品 Claim。
2. **方法里出现的产品信息**（价格、保额、年龄、比例、责任描述；用户 2026-11-01 裁定，§0.5）：不抽成事实，不替换、不删改；
   在关键句里**原样保留**，显示来源材料日期，页面在该方法上方固定提示“以条款与已发布知识为准”。货币金额、百分比、年龄
   区间与已登记产品名/品牌同句是**人工路由信号**（不是正确性判定）：命中的成员不走机器上线，进人工队列（审核标注“含产品
   信息”）；人工确认的也只是“作为话术原文展示”，不生成任何产品 Claim。
3. **引用数据**：统计与外部数据只能原话引用并带来源材料与日期；模型补充（`MODEL_GENERATED`）不允许出现数字。
4. **不过期，但会因来源与人工动作而失效**（§3.4 定义；“不自动过期”不取消撤源与读时权限的失败关闭）。
5. **访问范围**（用户 2026-11-01 裁定，§0.4）：首期整个 Space 可见，方法成员 `access_scope="space"`，与产品知识相同，
   沿用蓝图 §7.5 与 §14 2026-10-17 的会话只读规则；现在不做按角色（如只对销售/培训人员）的权限。以后若要收窄，需要平台
   按角色分权，另开设计与切片。
6. **私有材料**：试点用的业务样本只在线上与本机处理；仓库、Issue、PR、日志只作抽象描述，不写文件名、标题、引文或截图。

### 3.4 更新、撤下与读取口径（首期）

- **更新 = 同一 slug 跨 Release 替换**：同一方法 ID 下同一谓词的 Claim 只有一个逻辑 slug（Release 每个 logical_slug 一个
  digest，`release/publish.go` `materialize`）。方法有新说法时，新值作为同 slug 的新成员进入下一个 Release；**不**发布独立的
  “方法修订”成员，也**不**为方法使用 `supersedes` 关系（r1 的“旧成员标已有更新版本”取消）。当前口径 = Active；历史口径 =
  指定历史 Release 读取（蓝图 §7.5）+ Claim 的 `maintenance`（`revision_no`、`last_changed_release_id`），页面显示“更新于 …
  （来源材料 …）”。
- **更新的决定点 = 现有变化判定**：方法 Claim 与产品 Claim 一样走 `changes/decision.py`。来源材料集合中新增材料、而旧来源
  仍有效且值不同 → `CONFLICT` → 进人工队列，由人在同一 Candidate/审核/Head 链中选定；旧来源被撤回/解除 → `SUPERSEDE` 或
  `RETRACT`（无其他来源支撑时）。首期**不做**“新材料自动胜出”。
- **首期允许的撤下动作**：
  1. **来源修订撤回**（平台既有）：读时立即失败关闭（蓝图 §7.5），下一轮编译按变化判定 `RETRACT`/`SUPERSEDE`。
  2. **材料级解除**：PV-3 的 `uploads detach`（材料级，影响这份材料的**全部**用途——产品销售字段与方法都按变化判定处理）。
     SK 依赖 PV-3 合并；未合并前只有来源撤回。
  3. **单个方法撤下**：新增 Harness 命令 `methods withdraw <方法键>`（SK-2）：在登记表中把该方法标 `suppressed`（之后的编译
     不再产生它），并提交一个只含该方法成员 `removals` 的 CandidateBundle（`origin=feedback`），按 ReviewPolicy 交人工决定后
     激活；不影响同一材料的其他方法与产品字段。恢复 = 取消 `suppressed` 后重新编译。
- **首期不允许专家编辑方法 Claim**：专家编辑把证据替换为 `EXPERT_REVISION` 并加 `expert_lock`（`internal/enterprise/expert/
  service.go` `editBundle`），与“每项都有培训原文逐字支撑、无原文不发布”不兼容，且专家锁不随材料撤回自动删除。平台对
  `subject` 的 `entity_type = sales_method` 的专家编辑请求失败关闭（typed error，SK-3）；修正走“撤下 + 修正来源材料 + 重新编译”。
- **来源全部失效后**：方法所有 Claim 被 `RETRACT` 后，组包不再携带该方法实体（实体没有 Claim 时以 `removals` 移出），读取侧
  不再列出；登记表条目保留（无材料）以便将来同键重新出现时沿用 ID。

## 4. 接入与归属

### 4.1 双用途：用途记录与角色传递

现状：材料角色是单值（登记表 `MaterialEntry.role` / 编译输入 `SourceEntry.role`），`document_roles()` 优先用已记录角色，
`trusted_pages()` 按角色分流，编译与发布分别用 `restricted_fields(role)` 检查（`catalog/trust_policy.py`、
`compilers/schema_fields/engine.py`、`compilers/schema_fields/claims.py`）；`role_of()` 把两类信号并存视为未识别。这些**都不变**。

- **用途记录**：一份材料可以有多条**用途**，每条用途绑定同一原始来源 `knowledge_id + parse_attempt + sha256`，各有自己的
  角色与去向，分别确认、分别记录：
  - **版本用途**（现有）：材料条目挂在产品登记条目下，`role` 为该用途的角色（如 `sales_training`），由 PV-3 判定；
  - **方法用途**（新增，SK-1）：材料登记在方法登记（§2.1）的来源集合中，`role = "sales_method"`，附方法信号命中的块范围
    （块 ID 列表，来自 S11 块切分）与险种类别结论（§4.2）。
- **方法信号与主角色分开**：方法信号（“销售方法”“讲解步骤”“讲解逻辑”“关键句”“需求分析”“异议”“促成”“转保”“实操”等，
  数据）由**独立的方法信号检测**在块级判断，**不进入** `role_of()`，因此现有材料的角色识别结果不变（SK-1 以数据集全部材料
  回归）。`material_roles.json` 中 `sales_method` 只作为方法用途的角色值与 TrustPolicy 范围规则的键，不加入主角色的自动识别词表。
- **向编译与发布传递**：两条管线各自只读取属于自己的用途记录，因而每条管线里一份材料仍只有**一个**角色，`restricted_fields(role)`
  的检查方式不变：产品字段编译只看版本用途（`sales_training` → 四个销售字段）；方法编译只看方法用途（`sales_method` → 方法卡
  谓词，且只用记录的块）。两边都不放宽 S11c。
- **方法候选回到已准入记录**：原生 discover/cite 在方法发现库中运行，库里是原材料的**复制件**；复制时记录映射（复制件
  `knowledge_id` → 原始 `knowledge_id + parse_attempt + sha256`，复制件字节摘要必须等于原始 sha256）。候选只用于提出“有哪些
  方法、在哪些块附近”；**证据身份永远是原始来源**：准入阶段在原始 RAW KB 的来源页（S11b）上重新取段与引文，平台按 S11d 回验。
  复制件或生成页面从不作为 Evidence；映射不成立（摘要不符、原始修订已变）→ 丢弃该候选并报告。

### 4.2 新的归属结果：方法材料

在 PV-0/PV-3 的判定之后增加一步（顺序：强内容锚点 → 方案 A 版本匹配 → 方法用途）：

| 情况 | 结论 |
|---|---|
| 唯一匹配某版本（PV-3） | 版本用途照旧；含方法信号时**另记**一条方法用途（两条决定记录，各自的结论与依据） |
| 无版本可挂（`no_registered_version`、多系列、综合手册、版本歧义且未由人选定）且含方法信号 | 新结论 `METHOD_MATERIAL`：只记方法用途，不再隔离 |
| 既无版本也无方法信号 | 照旧隔离（`no_product_anchor` 等），可忽略 |
| 日期信号互相矛盾（PV-0 §4.3） | 不挂任何版本；方法用途照常判定（方法不需要年份） |

- **险种类别候选**：确定性词表（数据，`sales_taxonomy.json`：如“重疾”“医疗/百万医疗”“年金/养老”“分红”“终身寿”“意外”
  “护理”）在材料中的命中给出候选标签；命中唯一一类或明确写“通用”→ 自动打标签（机器结论）；命中多类或一类都没有
  → 交人选择，记人工结论。人生阶段与销售环节标签在方法抽取时按方法逐个判定（§5.2），不在材料级别询问。
- **确认页**：新问题类型“方法材料：选择适用范围”。现有确认页是单选（S5b-3a 通用待确认项）；首版不改为多选，选项为：
  系统建议的类别组合 / 通用（不限险种）/ 各单一类别 / 忽略。“忽略”语义不变：这份文件不再参与归属与抽取。
- **重判旧项**：现有被隔离的此类材料（综合手册、版本未登记的课件）在 SK-1 上线后按 S5b-7 的重判路径重新判定；旧问题
  按“已过时”关闭、不记为人工答复；**已持久化的 Settlement（含已应用、待对账的）保持原意图**，不被新结论覆盖（PV-3/S5b 的
  既有规则）。

## 5. 抽取与准入

### 5.1 候选来源：原生 discover/cite

按蓝图 §7.2，开放知识的候选来源是 WeKnora 原生 discover/cite，Harness 不恢复自有发现路径：

- 方法用途的材料复制到方法发现库（与 S6c 的产品发现库同一机制，但按领域而不是按产品组织；复制映射见 §4.1）；原生 Wiki
  生成候选页面（模型与思考模式按现行配置，DeepSeek）。
- 候选页面**不直接发布**（S6c 的 `wiki_page` 是另一条路径，本设计不复用其发布），也不作证据。

### 5.2 Harness 准入（身份、去重、结构化、引文）

1. **身份**：从候选页提取方法名，按 §2.1 规范化为方法键并查方法登记——完全命中名称/别名 → 并入已有方法；否则新方法。
2. **结构化 + 引文**：对每个方法，在其来源集合中**已记录方法用途的块**上用方法卡取值（与 S12 第二步同构：给定方法卡与带
   编号段落，返回各谓词的值与段落编号）。段落取自原始来源页（§4.1），值的每一项必须能在所引段落中逐字找到（关键句）或
   有所引段落支撑（步骤、摘要）。引文回验只证明“出处存在”，不证明步骤或摘要的语义正确——语义正确性靠审核与抽检（§5.4）。
3. **标签**：险种类别继承材料级结论（§4.2）；人生阶段、销售环节由同一次取值返回候选标签，必须落在词表内，并各自带支撑
   段落；不在词表内的丢弃。
4. **确定性检查**（引文回验、空值、词表、§3.2 的人工路由信号）不过 → 不发布，生成 ReviewItem。
5. **发布**：同一 CandidateBundle 带方法实体与方法 Claim；`origin=compile`；变化判定按 §3.4；审核走 ReviewPolicy，方法类单独
   一个 pack（`methods_sales`），**未准入前一律进人工队列**（与产品 pack 准入同一纪律，蓝图 §6.3）。

### 5.3 预算估计（试点）

| 环节 | 估计 |
|---|---|
| 原生 discover（6 份材料的方法部分） | 约 20–40 次 DeepSeek（按块组生成） |
| 准入取值（每个候选方法 1 次） | 约 40–60 次 DeepSeek |
| 独立审核打分（每个方法 1 次，deepseek-flash） | 约 40–60 次 |
| 离线评判（GPT-6 Astra xhigh） | ≤ 4 个会话 |

合计约 ≤ 160 次 DeepSeek、≤ 4 个 GPT-6 会话；SK-4 的运维 Issue 按实测上限再定。

### 5.4 评测（离线）

评判模型（与生产不同族，蓝图 §7.7）按方法逐个打分，量表（数据）：

| 维度 | 判定 |
|---|---|
| 忠实 | 每个步骤、关键句都能在所引原文中找到；无编造 |
| 无产品事实 | 没有把产品数字/责任当作方法结论；产品信息只作带日期引用 |
| 适用范围 | 险种、人生阶段、销售环节标签与原文一致；不过度泛化 |
| 去重 | 没有把不同方法合并，也没有把同一方法拆成多条 |
| 可用 | 步骤可执行、顺序正确，关键句完整 |

评判与独立审核分数都不是质量准入本身：`methods_sales` 的准入按蓝图 §6.3/§7.7 的同一纪律，先请业务抽检 10–20 条作校准，
一致性达标、门槛留版本后才允许机器上线。

## 6. 阅读与问答

- **导航**：`navigation.json` 新增领域“销售方法”（`entity_types: ["sales_method"]`），分组复用险种分组标签，另加“通用”。
  每个方法一页（由同一 Release 的数据生成，蓝图 §5.2“Schema 外知识页”）：方法名、适用范围标签、摘要、步骤、关键句、
  注意事项；每项可点开原文（S11e 的 Office 查看器 / PDF 查看器）；显示来源材料与日期、“更新于 …”；顶部标“销售方法（培训
  材料，非产品事实）”，含产品信息时另显示“以条款与已发布知识为准”。
- **产品页交叉链接**：产品页（schema_wiki 之外）显示“相关销售方法”：按产品的险种标签与产品形态匹配方法标签，PV-4 之后
  另按 `family:<key>` 与产品实体的 `product_family.key` 匹配；方法内容**不进入**产品的字段页。
- **问答**：在现有三类来源（已发布知识 / 模型整理 / 原文检索，S6e）之外，方法成员作为“销售方法（培训材料）”来源：
  “怎么卖、怎么讲、如何应对异议”类问题先查方法；产品事实仍只从产品 Claim 回答；一个回答同时用到两类时分段标注来源；
  所有来源与原文打开都固定同一 Release，并按当前权限过滤。意图判别用问题词表（数据，同 `question_terms`）。

## 7. 合同、平台与接口约定

- **合同**：不新增合同类型。`Entity.entity_type`、`classification_labels` 为字符串；方法 Claim 的 `product_version_ref` 为空，
  合同已允许。不新增 Relation 目标（§2.2），成员引用闭包不变。
- **与 PV-0 附录 A §2（元数据发布路径）的接口修订**：该路径的“所有 Claim 补 `product_version_ref` = `subject_ref`”只适用于
  **subject 为 `product` 实体的 Claim**。`identity_refresh` 候选包**从不**为方法 Claim（subject 为 `sales_method`）补版本引用，
  也不改动方法实体与方法 Claim——它们属于“保留成员完整投影”的范围，任何改动按该路径的规则整包拒绝；首次全量重发布同样
  只涉及产品事实。本修订已同步写入 PV-0 附录 A §2，由 PV-4 实施；本设计不实现 PV-4。
- **平台（SK-3）**：知识索引读取 `sales_method` 实体与其 Claim；若平台不变量把“无版本引用的 Claim”当作错误，在 SK-3 中按
  “仅 subject 非 `product` 实体时允许为空”收窄并写明；按领域/分组列出；方法页与产品页交叉链接；问答来源标注；专家编辑对
  方法 Claim 失败关闭（§3.4）。只读接口、固定 Release、权限边界不变。
- **上游补丁**：不新增；前端沿用 S11e 的查看器与企业模块注册方式（U-5a）。

## 8. 风险

| 风险 | 处理 |
|---|---|
| 方法与产品话术边界不清，产品信息混进方法 | §3.2 人工路由信号 + 审核量表“无产品事实”维度；进人工队列 |
| 不同材料的同一方法被拆成多条，或不同方法被合并 | 只在规范化名称/别名完全相同时合并；“可能重复”标注；ID 一旦分配不变；评测“去重”维度 |
| 原生 discover 对 Office 课件的候选质量不稳定 | 候选只提出方法与位置；准入在原始来源上取值，只认能逐字回验的方面；候选少时不补写 |
| 两种用途互相放宽采信范围 | 每条管线只读自己的用途记录，`restricted_fields(role)` 不变；SK-1/SK-2 RED 覆盖交叉误用 |
| 统计数据过时 | 只原话引用并显示日期；不让模型更新数字 |
| 需要修正方法内容 | 首期不允许专家编辑；撤下 + 修正来源 + 重新编译 |
