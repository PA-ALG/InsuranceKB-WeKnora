## 0. S5b-3c 的拆分

| 片 | 内容 |
|---|---|
| **S5b-3c-1（本片）** | 纯判定：等人确认的材料有哪些选项；人选了某项之后得出什么归属结论；登记表记下这次人工决定 |
| S5b-3c-2 | 执行：把选项推送成 S5b-3a 的待确认项，读回人的选择，按本片得出结论、写入登记表并关闭待确认项 |

本片不联网，不读写平台。

## 1. 目标

S5b-1 有四种原因会得出 `NEEDS_CONFIRM`。每种原因给出一组固定的选项，人选中一项后，按确定的规则得出一个新的归属结论：

| 原因 | 含义 | 选项（按此顺序） |
|---|---|---|
| `multiple_products` | 同一文件已属于几个产品，或标题点名了几个产品 | 归入每个候选产品；忽略 |
| `pack_unresolved` | 新条款的标题对不上任何险种后缀 | 按每个险种包新建产品；忽略 |
| `role_unresolved` | 产品已知，认不出是条款、说明书还是费率表 | 每种材料角色；忽略 |
| `same_role_differs` | 产品已有同角色、内容不同的材料 | 替换；作为补充；忽略 |

几条原则：

- 人的选择只补上规则缺的那一项（属于哪个产品、是哪种角色、用哪个险种包），其余仍由 S5b-1 的规则判定；
- 规则不会因为人选过就放宽，人也不能选选项之外的东西；
- 选择之后如果还有一个不同的问题，就再问一次。例如选了产品，发现该产品已有同角色材料，就会得出新的 `same_role_differs`。

## 2. 改动

### 2.1 `identity/attribution.py`

- `Outcome` 增加两种结论，都只能由人的选择得出，`attribute()` 自身不会返回：
  - `REPLACE`：替换产品中同角色的已有材料；
  - `IGNORED`：这份材料不归入任何产品。
- `attribute()` 增加三个只能按名字传入的参数，都表示人的选择：
  - `product: str | None = None`：人确认材料属于这个已登记产品。
    - 跳过产品识别（条款编号、标题名称），直接按该产品判定：是重复文件、补充、新版本，还是仍需确认（角色不明、已有同角色材料）。这一步与 S5b-1 §2.3 第 5 步相同，原因记为 `confirmed_by_person`；
    - 不能只拿这个产品重新识别：标题点名几个产品时，单独一个产品名出现在更长的标题里，S5b-1 不认作命中，会落到隔离区；
    - 锚点与人的选择矛盾时，得出 `QUARANTINE / anchor_conflict`：
      - 同一文件已属于其他产品，却不属于这个产品；
      - 条款编号属于其他产品。
  - `role: str | None = None`：人确认的材料角色，代替从文件名和开头文本识别出的角色；
  - `pack: str | None = None`：人为新条款选的险种包，只在本来会得出 `pack_unresolved` 时使用；标题能对上险种后缀时，仍按后缀判定。
- 校验：
  - `product` 必须是已登记的产品；
  - `role` 必须是 `material_roles.json` 里的角色；
  - `pack` 必须是策略 `classifications` 里出现的险种包；
  - 不符合时报 `AttributionInputError("CHOICE_INVALID")`。
- 不传这三个参数时，结果与现在完全相同（S5b-1 的测试照旧通过）。策略版本不变：自动判定的规则没有改动。

### 2.2 新模块 `identity/confirmation.py`

```python
class Choice(BaseModel):            # frozen, strict
    key: str                        # 选项键，即 S5b-3a 的 option key
    kind: Literal["product", "pack", "role", "replace", "supplement", "ignore"]
    value: str | None = None        # 产品 id / 险种包 id / 角色；其余为 None

class ConfirmationError(ValueError):  # .code
    ...

def choices(pending: Attribution, registry: Sequence[RegisteredProduct],
            policy: AttributionPolicy | None = None) -> tuple[Choice, ...]

def conclude(pending: Attribution, key: str, upload: Upload,
             registry: Sequence[RegisteredProduct],
             policy: AttributionPolicy | None = None) -> Attribution
```

**选项键**：

- 符合 S5b-3a 的格式 `^[a-z0-9][a-z0-9:._-]{0,127}$`；
- 产品选项为 `product:` 加产品 id 的 SHA-256 前 16 位十六进制。产品 id 可能有大写字母，不能直接当键；
- 险种包选项为 `pack:<schema_pack_id>`，角色选项为 `role:<role>`；
- 其余三种为 `replace`、`supplement`、`ignore`。

**`choices`**：

- 按 §1 的表、按固定顺序列出选项：
  - 候选产品按 `pending.candidates` 的顺序；
  - 险种包按策略 `classifications` 的顺序，去重；
  - 角色按 `material_roles.json` 的顺序。
- 已不在登记中的产品不列出。`role_unresolved`、`same_role_differs` 的产品已不在登记中时，只列"忽略"。
- 以下情况报 `NOT_CONFIRMABLE`：
  - `pending` 不是 `NEEDS_CONFIRM`；
  - 原因不在 §1 的表里；
  - 选项键重复。
- 选项不超过 S5b-3a 的上限 50 个。

**`conclude`**：

- `key` 不在 `choices(pending, registry, policy)` 中时，报 `CHOICE_UNKNOWN`。
- 按选项得出结论：

  | 选项 | 结论 | 成立条件（不满足报 `CHOICE_STALE`） |
  |---|---|---|
  | 产品 P | `attribute(upload, registry, policy, product=P)` | 结论是 P 的 `DUPLICATE`、`SUPPLEMENT`、`NEW_VERSION`，或 P 的 `NEEDS_CONFIRM`（`role_unresolved` / `same_role_differs`） |
  | 险种包 K | `attribute(upload, registry, policy, pack=K)` | 结论是 `CREATE`，且险种包为 K |
  | 角色 R | `attribute(upload, registry, policy, product=pending.product_id, role=R)` | 结论针对 `pending.product_id`、角色为 R，且是 `SUPPLEMENT`、`NEW_VERSION` 或 `NEEDS_CONFIRM / same_role_differs` |
  | 替换 | `REPLACE / confirmed_replace`：`product_id`、`role`、`clause_code` 取自 `pending`；`replaces` 为该产品同角色已有材料的 knowledge id（排序） | 产品仍在登记中，且仍有同角色材料 |
  | 作为补充 | `SUPPLEMENT / confirmed_supplement`：`product_id`、`role`、`clause_code` 取自 `pending` | 产品仍在登记中 |
  | 忽略 | `IGNORED / confirmed_ignore`：`product_id`、`role`、`clause_code`、`candidates` 取自 `pending` | 无 |

- 结论都带当前策略的 `policy_ref`。
- 结论不会是与 `pending` 相同的"结论 + 原因"，同一个问题不会再问一遍。
- `CHOICE_STALE` 表示提问之后登记已经变化（例如产品改了名字），人的选择已不适用。交 S5b-3c-2 处理：关闭这一项，让材料重新判定。

### 2.3 `ingest/registry.py`

- 新模型 `ConfirmationRef`（strict，禁止多余字段），记录一次人工决定来自哪里：
  - `item_id`、`answer_id`：S5b-3a 的 id，格式 `^[A-Za-z0-9][A-Za-z0-9_-]{0,127}$`；
  - `option_key`：选项键格式；
  - `answerer`：非空，最多 256 字，不含控制字符。
- `DecisionEntry` 增加 `confirmation: ConfirmationRef | None = None`。
  - 旧文件没有这个字段，照常读取；`contract` 仍为 `product-registry.v1`。
- 登记表校验增加两条：
  - `REPLACE`、`IGNORED` 的记录必须带 `confirmation`；
  - 各条记录的 `answer_id` 不重复。
- S5b-2 的 `uploads._apply` 移到这里，改为公开函数：

  ```python
  def record(registry: ProductRegistry, source: RawSource, attribution: Attribution,
             confirmation: ConfirmationRef | None = None) -> bool
  ```

  - 和原来一样：直接修改传入的登记表；产品有变化时返回 True。
  - 自动判定的行为不变。
  - `REPLACE`：与带 `replaces` 的 `SUPPLEMENT` 一样处理，被替换的材料移入 `retired`。不改条款编号：被替换的未必是条款，`clause_code` 也可能只是引用的编号。
  - `IGNORED`：只追加记录，不改产品。
  - 结论仍是 `NEEDS_CONFIRM`（新的问题）时，用新结论替换 `pending` 中这条材料的旧结论。
  - `REPLACE`、`IGNORED` 不带 `confirmation` 时报 `RegistryError("CONFIRMATION_REQUIRED")`，登记表保持不变。
  - 带 `confirmation` 时，以下情况报错，登记表保持不变：
    - 这份材料（knowledge id、解析次数、SHA 都相同）不在 `pending` 中，或不是 `NEEDS_CONFIRM`：`RegistryError("CONFIRMATION_UNEXPECTED")`；
    - 这个 `answer_id` 已经记录过：`RegistryError("CONFIRMATION_RECORDED")`。
- `REPLACE`、`IGNORED` 算作最终决定：`attribute_uploads` 不会再判定这份材料。

### 2.4 `ingest/uploads.py`

- 改为调用 `registry.record`；
- 已决定的结论集合加入 `REPLACE`、`IGNORED`；
- 其余不变。

**不做**：

- 不推送、不读取平台，不写文案（S5b-3c-2）；
- 隔离区（`QUARANTINE`）的材料不交给人：仍按 S5b-2 每次运行重判；
- 不改自动判定的规则与策略版本。

## 3. 验收（RED，Claude 编写，受保护）

`harness/tests/identity/test_confirmation.py` 与 `harness/tests/ingest/test_registry_confirmation.py`。都用 S5b-1 的真实开头文本，至少覆盖两全、重疾、意外、年金四个险种。

1. **选项**：
   - 四种原因各自的选项键与顺序；
   - 不在登记中的候选产品不列出；
   - 选项键都符合格式、不重复，且不超过 50 个；
   - 自动结论与隔离结论报 `NOT_CONFIRMABLE`。
2. **替换、补充、忽略**：
   - 得出 `REPLACE`（替换列表正确）、`SUPPLEMENT`、`IGNORED`；
   - 都带当前 `policy_ref`。
3. **选产品**：
   - 标题点名两个产品时选其一，得出该产品的 `SUPPLEMENT`；只拿该产品重新识别会落到隔离区，这里不会；
   - 该产品已有同角色材料时，得出新的 `same_role_differs`；
   - 两个产品共用别名时，同样按所选产品判定；
   - 同一文件已属于两个产品时，选其一得出该产品的 `DUPLICATE`。
4. **选角色**：
   - 认不出角色的说明书选"说明书"，得出 `SUPPLEMENT`；
   - 选"条款"时，因已有条款，得出 `same_role_differs`。
5. **选险种包**：
   - 两个险种的新条款各选一个险种包，得出 `CREATE`（产品 id、名称、险种包正确）；
   - 标题能对上后缀时，`pack` 不起作用。
6. **拒绝**：
   - 未知的键、另一种原因的键、不存在的险种包：`CHOICE_UNKNOWN`；
   - `attribute()` 收到无效的 `product`、`role` 或 `pack`：`CHOICE_INVALID`；
   - 产品已不在登记中：`role_unresolved`、`same_role_differs` 只剩"忽略"，选其他项报 `CHOICE_UNKNOWN`；
   - 登记已变化，选择已不适用，报 `CHOICE_STALE`：
     - 同角色材料已不在；
     - 文件现在与另一产品的材料相同；
     - 条款编号现在属于另一产品；
     - 标题现在点名了已登记产品。
7. **不重复提问**：以上所有结论都不等于 `pending` 的"结论 + 原因"。
8. **登记表**：
   - `REPLACE` 后，旧材料移入 `retired`、新材料加入，条款编号不变；
   - 人工确认的补充保留两份；
   - `IGNORED` 不改产品，下次 `attribute_uploads` 不再判定这份材料；
   - 选择后得出的新问题替换 `pending` 中的旧结论，仍不重判；
   - 由人选险种包得出的 `CREATE` 建出产品；
   - 这些记录都带 `confirmation`；
   - 拒绝：
     - 材料不在等人确认的 `pending` 中，或解析次数、SHA 不同：`CONFIRMATION_UNEXPECTED`；
     - 同一 `answer_id` 记录两次：`CONFIRMATION_RECORDED`；
     - `REPLACE` / `IGNORED` 不带 `confirmation`：`CONFIRMATION_REQUIRED`；
     - 出错时登记表不变。
   - 文件：
     - 没有 `confirmation` 字段的旧文件照常读取，读写一轮不变；
     - 不带 `confirmation` 的 `REPLACE` / `IGNORED`、重复的 `answer_id`：`REGISTRY_INVALID`。
