## 1. 目标与判断标准

### 1.1 定位

建设大型寿险公司的**企业知识底层服务**。输入覆盖产品条款/说明书/宣传材料，核保、理赔、保全规则，权益与产品服务，医学术语、疾病定义与核保结论，销售与客户经营经验，FAQ，历史知识库的文档片段与 chunk，以及各系统、各团队维护的零散文本；格式含 PDF、扫描件、图片、Word、PPT、Excel 与结构化数据；规模目标为几十万份文档或片段。

输出是持续演进的知识：有明确实体、有适用产品与产品版本、有业务时间、有来源证据、有冲突与缺口治理、有可配置的机器审核与人工批审、有不可变版本、可整版发布与回滚。它以统一的**知识服务接口**同时服务人（Wiki 浏览、审核、专家修订）与 Agent/应用（RAG 快答、产品比较、规则查询、核保理赔权益辅助、关系推理、反馈与缺口上报），双方固定读取同一个 Release。新材料、专家修订与使用反馈驱动下一版。

本项目不是：普通文档库；只做向量检索的 RAG；让模型把文档直接改写成 Markdown；在两个系统里各维护一套线上知识；用强模型在线兜底。

### 1.2 业务问题 → 架构能力

| 业务问题 | 架构能力 | 位置 |
|---|---|---|
| 知识入库后静态，新材料不补旧知识 | 增量编译；GapTask 定向反查补抽 | §7.4、§7.11 |
| 答错不回流，更新滞后 | 反馈飞轮：回答日志、纠错、证据不足 → ReviewItem/GapTask → 新 Candidate | §7.11 |
| 停留在文档/片段层，概念散落 | 实体 + Claim/Relation 统一知识模型；概念与分产品义项；QA 一等对象 | §5、§7.2 |
| 多份材料口径不一致 | TrustPolicy 按字段 × 材料角色裁决；不能裁决即冲突进人工 | §7.3、§7.4 |
| 专家看不到全貌 | 覆盖、缺口、冲突、重复工作台 | §7.11 |
| 准确率低且不可证明 | 原文优先编译、Evidence 回验、独立审核、Golden + Evaluator | §7.1、§7.9 |
| 人和 Agent 读到不同版本、混版 | 唯一 Head；所有读入口 release-aware；原子激活 | §7.7、§7.10 |
| 权限变化后知识继续暴露 | ACL 随 Evidence 传播到 Claim/页面，读时校验，收缩 fail closed | §7.12 |
| 逐页审核无法运营 | 先发布后抽检：确定性检查 + 独立审核打分，高分直接上线并标注"机器审核"，低分与冲突进人工；上线后按风险抽检并校准门槛；人工批量确认 | §7.3 |
| 错误更新无法回退 | 不可变 Release；整版回退与实体级回退都生成新 Release | §4.2、§7.4 |

### 1.3 知识域分期

所有知识域共用同一套实体、Claim、Relation、Evidence、Candidate、Release 合同；差异只在 SchemaPack、FieldExtractionConfig、TrustPolicy、PresentationProfile 等数据配置。新增知识域不改平台与核心编排。

**首期范围（2026-10-01 确认）**：只做产品知识域，作为一个统一体系；11 类险种每类至少上线一款产品，合计几十款；消费方为业务人员（Wiki 浏览与抽检）和问答 Agent（经通用知识服务接口）。一个企业 Space，按业务属主分模块管理，知识保持一个完整、互相关联的体系。

| 期 | 知识域 | 主要实体 |
|---|---|---|
| 第一期 | 产品（11 类险种）、权益与服务、共享概念、权威 FAQ | Product、ProductVersion、Coverage、Exclusion、Service、Concept/Sense、QA |
| 第二期 | 核保、理赔、保全规则；医学术语、疾病定义、核保结论 | Disease、MedicalTerm、UnderwritingRule、UnderwritingConclusion、ClaimRule、ServicingRule |
| 第三期 | 销售与客户经营经验、培训材料、历史 chunk 与零散文本、外部系统结构化数据 | 按 TrustPolicy 作为线索/解释类知识；结构化导入 |

### 1.4 上线判断标准

每项独立判断，不互相推导：

| 维度 | 标准 |
|---|---|
| 质量 | 每个上线险种 pack 在 Golden 上：有材料字段 recall ≥ 90%、present precision ≥ 95%；幻觉事实 = 0；已发布事实来源回跳 = 100%。指标用生产目标模型（DeepSeek v4 flash）测得。业务专家回归前，由离线评判模型（Opus 5.5 或 GPT-6.1 sol）担任专家评判，先在已有人工结论上校准一致性 |
| 流程 | 上传/结构化导入→解析→编译→审核→发布→Wiki、知识服务接口、Search、Agent、MCP 同版读取→来源回跳，覆盖文本 PDF、扫描件/图片、Word、PPT、Excel；增量更新、专家编辑与反馈补编都形成新 Release |
| 服务 | 知识服务接口返回结构化 Claim/Relation、typed value、适用范围、有效期、Evidence、release_id 与稳定标识，并明确表达 unknown/不足/需补充条件；支持 current、as_of_date、release_id 三种读取 |
| 安全 | 一个 scope 只有一个 Head；所有读入口只读 Active 或 pinned Release；受管 KB 的所有写入口拒绝旁路；ACL 不经知识放大，收缩后 fail closed；私有化部署时材料不出内网 |
| 成本与恢复 | 未变化材料不重解析、不重调用；成功结果跨中断复用；新增材料的成本随新增量增长，不随历史总量增长 |
| 规模 | 按配置的 CapacityProfile 验证十万级材料/片段：增量编译、micro-batch、可回放任务、Release 成员按内容寻址去重；审核按整包与风险分层，不随页面数线性增长 |
| 可维护 | 新增知识域、险种 pack 或字段规则只改数据配置；新增 locator 格式只加解析适配与渲染器；核心代码不出现险种名、字段 key 与样本身份 |

## 4. 核心流程

### 4.1 CompileJob（Harness 唯一编排）

```text
RECEIVED
 → MATERIALS_READY      读取 SourceRevision + ParseArtifact，按页重建 PageText；材料角色来自元数据
 → IDENTITY_RESOLVED    MATCH / CREATE / MULTI / NEEDS_CONFIRM / QUARANTINE；歧义不自动合并
 → TASKS_PLANNED        按产品版本组装材料集；按 SchemaPack 与 FieldExtractionConfig 生成 CompileTask
 → TASKS_EXECUTED       插件执行；每个任务独立成功/失败/结果未知
 → CHANGES_COMPUTED     与当前 Active 比对：SAME / ENRICH / SUPERSEDE / COEXIST / CONFLICT / RETRACT
 → REVIEWED             平台硬门 + 独立审核；CONFLICT、MODEL_GENERATED、专家锁冲突进入人工
 → SUBMITTED            按实体组装 CandidateBundle，提交 WeKnora（幂等 digest）
 → 终态 DONE / PARTIAL / FAILED
```

- **任务键**：`hash(产品版本, 相关材料 revision 集, 任务规格, FieldExtractionConfig 版本, 编译器版本, 模型身份与参数)`。键不变即复用成功结果，不重新调用模型。PresentationProfile、分类标签变化不进入任务键，只触发重渲染。
- **恢复**：从任务状态与失效依赖推导待做任务；`UNKNOWN_OUTCOME` 先对账，不自动补发。每条外部调用链只有一个重试 Owner 与明确预算。
- **部分成功**：一个实体失败不阻塞其他实体；实体及其强依赖作为一个原子单元提交。
- **实现复用**：沿用现有 JobStore、租约、代次隔离与 StageCall 调用记账作为 `runtime`，具体保留范围见 [01 §9](01-调研结论.md)；删除 workflow v1–v3 与 checkpoint 多版本分支（历史任务只读）。

### 4.2 WeKnora 侧（平台通用链）

```text
POST /candidates            接收 CandidateBundle（digest 幂等），结构校验 + 平台不变量
GET  /candidates/:id/preview 预览，与 Active 的差异
POST /candidates/:id/decisions  ReviewDecision（机器或人工；绑定 candidate_digest 与审核主体；批量按整包）
POST /activations           expected_release + epoch CAS；单赢家；不同实体的 Candidate 自动 rebase
POST /expert-edits          保存不可变 ExpertRevision 记录，发事件给 Harness
POST /samples/:id/verdicts  上线后抽检结论（正确/错误/需修改），驱动修正 Candidate 与门槛校准
GET  /releases/:id/...       真正的历史 pinned 读取（成员、页面、搜索）
revert                       以旧成员生成新 Candidate，走同一审核与 CAS
```

平台不变量（Go 负责）：canonical JSON 与 digest、成员闭包与引用双射、Evidence 指向的 SourceRevision/ExpertRevision 存在且 quote hash 与原文一致、scope/ACL、base epoch CAS、审核记录与 digest 绑定、服务间认证。**不做**：Schema 字段是否齐全、实体消歧、质量评分、业务文案。

并发：一个企业 Space 一个 Head。Candidate 是相对 base Release 的实体级 delta；激活时若 Head 已前进，而本 Candidate 触及的实体在此期间未被改动，则自动 rebase 到新 Head；否则重新比对后再审。

## 5. 数据合同（唯一来源：Harness pydantic → `contracts/*.schema.json`）

知识层（唯一事实层，进入 Release）：

- Member.kind 由 Harness 声明，每个 kind 附带 JSON Schema；Go 只按 schema 校验与存储，前端按 kind 注册渲染器。
- 比较合同：Claim 的 `logical_key`（subject + product_version + predicate + applicability 维度）、typed value comparator 与 applicability 关系必须先冻结，增量语义（§7.4）才能确定性判定。value 一致性是历史测量中的最弱点（present 检出后值一致率 0.273），typed 归一与比较器是质量工作的最高优先级。

## 7. 关键机制

### 7.1 Schema 字段编译器（迁入 V5）

- 输入：同一产品版本的全部 PageText + 目标 FieldDefinition + FieldExtractionConfig。输出：逐字段 FieldAssertion、准入决定、缺失组成要素、执行完整性状态。
- 内部职责（深模块，调用方只见上述接口）：全页召回与打分 → 上下文与预算 → 字段微批/长字段分片 → Schema 引导调用 → JSON 合同校验 → Evidence 原文回验 → 组成要素与值约束门禁 → 保守替换 → 定向补抽。
- 迁入时保持的质量不变量：先扫全部页面再按预算截断；关键词未命中不证明字段不存在；quote 只允许 NFKC/去空白/去列表符/去脚注号归一，不跨页拼接，不能消歧即不采纳；长字段每个原子项都有直接证据，一个分片失败不能被其他分片掩盖；已知字段不得退化为 unknown；数字、否定、期限不改写；附加险不继承主险权益；截断（finish_reason≠stop）整批拒绝。
- FieldExtractionConfig 键为 `schema_pack_id + field_key + field semantic_sha256`，内容含关键词、语义词、值形态、文档角色要求、邻页范围、分片、组成要素、省略禁用词、字段指令、`audit_kind`。与 FieldDefinition 分开存放，改规则不改变 pack hash。
- 替代 `g3_bounded_model_execution.py`、`product_ingestion/extraction.py` 的字段执行；不迁 V5 的 m15x 编排、预览 API、搜索问答页面。

### 7.2 开放知识与概念补全

- 开放知识发现：受管 KB 内，WeKnora 原生 discover/cite 只产生**候选**（不直接写页面，经服务间认证交给 Harness）；Harness 负责身份、去重、归属（新页/更新已有页/写入实体字段/别名/线索/拒绝）与准入。Harness 自有的发现路径退役。
- 概念补全：允许模型补充通用概念解释，provenance=`MODEL_GENERATED`，页面与 Agent 回答标注"模型补充"，与有原文依据的内容分开显示；不得包含具体产品事实（确定性检查拦截）；按 D19 的分数路由发布。
- 评分只作排序与分流，不能抵消硬门失败；审核模型不能给自己生成的内容打证据分。
- 概念与义项：跨产品复用概念（如"在线问诊"）有一个概念页承载通用口径，各产品下的具体规定作为 Sense 挂在对应产品版本下；具体事实只落在 Sense/产品层，概念页的差异对比与义项索引由编译器从同一 Release 聚合生成。
- QA：首期只做权威 QA（来自已批准 FAQ），作为成员进入 Release 与检索。由 Claim 自动生成问答暂不做；知识服务接口直接查询 Claim 不足以支撑快答时再评估。

### 7.3 材料采信与审核

- **材料角色**：少量可配置类型（正式条款、说明书/面客材料、内部制度、核保/理赔规则、培训材料、销售经验、FAQ、普通片段、未知/混合），由规则与模型自动识别，不要求逐文件配置；不确定时降级人工或隔离。
- **TrustPolicy**：唯一求值入口，按"字段 × 材料角色 × 产品版本 × 有效期"裁决采信。例：正式条款对责任/除外/等待期更权威；说明书不能自动覆盖条款；内部核保规则对核保结论更权威；销售经验只作线索或解释；普通片段不能单独支撑高风险事实。策略变化只重算裁决，不重抽。
- **平台硬门**（确定性）：三态与值类型、Evidence 可回验、scope 与 ACL、闭包完整、专家锁不被覆盖。
- **独立审核**（模型）：与编译器隔离输入与上下文，只判断业务支持度与价值，输出通过/拒绝/需人工及依据。
- **发布流程（D19，先发布后抽检）**：

```text
确定性检查（不通过 → 不发布，生成 GapTask/ReviewItem）
  Evidence 可回验 · 类型与三态 · 无冲突 · 产品事实有原文或专家来源 · 所属 pack 已通过质量准入
→ 独立审核模型打分（与编译器隔离；分数校准到评判模型/专家结论）
  ≥ 门槛 → 直接上线，页面与接口标注"机器审核"
  < 门槛 / 冲突 / 版本歧义 → 人工队列，暂不上线
→ 上线后：按风险与字段分层抽检；系统挑出一批"请确认"交给人工批量确认
  抽检发现错误 → 修正 Candidate，必要时实体级回退；抽检结果回流校准门槛
```

- **ReviewPolicy**（按 Space 版本化配置）：门槛按 pack/字段可分别设置，由人工调整，每次调整留版本；首期不设必须人工先审的字段，全部按分数路由。人工动作按整包或按批确认，不逐页点击。
- **分数的含义**：分数来自独立审核模型而不是编译模型的自评；门槛以"分数达标的成员在评判集上 precision ≥ 95%"为准来设定与复核。

### 7.4 增量更新

- 以现有 `incremental_changes` 判定器为唯一语义 Owner，输入改为已发布 Claim，按 `logical_key` 与 typed comparator 输出 Claim 级 delta；未受影响 Claim 及其投影页沿用旧成员与旧 digest。
- 判定结果最少五类：**不变**（含只补充 Evidence）、**替代**（同一适用范围的新权威值，旧值留在历史 Release）、**并存**（版本/地域/渠道/人群/有效期不同）、**冲突**（同范围矛盾且 TrustPolicy 不能裁决）、**撤回**（来源撤回或失效）。不把所有差异都当冲突，也不只按材料权威分覆盖。
- 冲突不进 delta，保留旧成员并生成 ReviewItem；撤回显式移除成员；旧 Release 在新 Release 激活前完整服务；唯一支持失效的知识及时撤回。
- 时间：Claim 只带业务有效期 `effective_from/effective_to`（半开区间、Space 业务时区日历日；来自材料或继承 ProductVersion 包络，Claim 只能收窄不能扩大；模型不得猜测）。**系统时间轴由不可变 Release 历史提供**：某时刻"系统当时知道什么"即读取该时刻的 Active Release，不在 Claim 上另建系统时间模型。查询支持 current、as_of_date（业务时间）、release_id。
- 实体级回滚：以该实体旧成员作为 delta 生成新 Release，保留其他实体后续修订。
- 触发：新 SourceRevision、SchemaPack 新版本、TrustPolicy 变化、重分类、专家编辑。纯展示/标签变化只重渲染。

### 7.5 专家编辑

```text
WeKnora 编辑界面（复用上游编辑器/diff/history 组件）
 → POST /expert-edits {base_release_id, base_epoch, claim logical_key, base_member_digest, after}
 → WeKnora 保存不可变 ExpertRevision（actor/role/time/before/after，原因与附件可选）
 → event → Harness 生成替换该 Claim 的 Candidate（origin=expert_edit, expert_lock=true，
   Evidence 为 EXPERT_REVISION locator）
 → 同一审核与 CAS 激活；无发布权限者只形成 pending
```

- 不在原生 `wiki_pages` 上原地编辑，不把它当草稿区。
- expert_lock 字段面对后续模型新值只产生 pending CONFLICT，不自动覆盖；只有具名专家的新决定可更新或解锁。

### 7.6 多格式解析与定位

- 所有解析结果统一为版本化 ParseArtifact（由现有 NativeStructure 泛化），带 `locator_space` 与精度声明。
- 文本 PDF：保留现有 pdfium 字符框链路。
- 扫描件/图片：自建 MinerU（或 PaddleOCR-VL）并解析 content_list，locator 标明块级精度；只有纯文本、无坐标的 VLM 结果 fail closed，不作为可回跳 Evidence。
- Word/PPT/Excel：用 python-docx / python-pptx / openpyxl 采集原生结构（段落、表格单元格、slide/shape、sheet/cell 与值快照）；DOCX/PPTX 预览用 soffice 转 PDF 快照复用 pdf.js 高亮，XLSX 原生渲染。转换确定性须先验证。
- 回跳顺序固定：按 Release 读 Evidence → 打开 exact SourceRevision → 核对 hash → 按 kind 解析 → 回验 quote → 渲染；失败返回 typed error，不打开当前版本、不猜相似文本、不跳第 1 页。

### 7.7 读写一致性

- managed 判定统一为一个函数（以 custody 为准），所有 Wiki 写路由（含 POST pages、revert、folders、rebuild-links、auto-fix）挂同一守卫。
- 受管 KB 的所有读入口（Wiki 页面、搜索、Agent、KnowledgeQA、MCP、聊天引用链接）只读 Active 或 pinned Release；Agent 每轮冻结一次 release_id。
- pinned 读取支持真正的历史 Release，不要求等于当前 Head。

### 7.8 模型接入与调用治理

- 按阶段配置 provider/endpoint/model/输出预算，OpenAI 兼容；输出预算同时计入推理 token 与正文 token（DeepSeek 曾出现推理耗尽 16K、正文为 0）。
- 每条调用链一个重试 Owner；限流按供应商提示有界退避；结果未知先对账。成功、失败、取消、超时都记录发送次数、耗时与可得用量，复用与新调用分开统计。
- 模型输入只含本次所需字段、规则、去重后的原文与短引用编号；完整来源身份与审计对象留在服务端。

### 7.9 质量闭环

- Golden 行结构沿用 `goldenset/records.py` 的 GoldenRecord，键为 `pack, product_version, field_key`，期望含 state、值或选项集、组成要素、禁止词、`document_sha256 + 页码 + quote`、审核人。
- Evaluator：逐字段与逐 pack 的 precision/recall、组成要素召回、幻觉数、来源回跳率；零分母 fail closed；模型原始输出与专家修订后结果分开报告。
- **评判模型（业务专家回归前）**：Opus 5.5 或 GPT-6.1 sol，只做离线评测，不进生产流程，与生产编译/审核模型不同族。先在已有人工结论上校准：V5 的 30 条业务反馈（12 条可机器判定）与 31 项原文回归集、`gs-s0q-596-v1`；一致性达标后，用它对每个 pack 的冻结样本逐字段核对原文，产出 Golden。评判模型产出的 Golden 标记为"模型评判"，业务专家回归后抽检复核，不覆盖原记录。开发阶段允许把产品材料发给评判模型。
- 首批 Golden 样本：7 款同条件产品（596、594、1826、1824、1814、1816、1828），之后每个 pack 至少一款上线产品；材料见仓库 `dataset/` 与本机 `shouxian_product` 目录，缺失险种从公司官网补充。
- CI 跑离线回放评测；真实模型评测按 Issue 预算执行，结论只认 DeepSeek v4 flash（上线后为私有化模型）。
- Golden 状态：研发用（模型辅助）→ 准入用（评判模型校准后产出，或专家确认）。覆盖范围随切片增加：字段与条件、Evidence、unknown/absent、实体与版本消歧、增量与冲突。
- 上线后的人工抽检结论也写回 Golden，作为门槛校准与回归集的一部分。
- 每个质量数字绑定 Metric ID（定义、分母、口径、Golden 版本、模型身份），不在文档中写裸数字。

### 7.10 知识服务接口（Knowledge Query API）

- 位置：WeKnora `platform/read`，版本化 REST；MCP 与内部 Agent 工具都是它的薄适配器。接口按通用的知识查询设计，不绑定某一个 Agent 项目。
- 能力：实体查找（按名称/别名/代码/备案号）；按实体与谓词取 Claim（current / as_of_date / release_id）；Relation 有界遍历；Evidence 解析与原文回跳；release-aware 混合检索（覆盖 Claim 值、条件与开放知识正文，不只标题）；同谓词跨实体比较；QA 检索；反馈与缺口上报。
- 每个响应携带 release_id、activation_epoch、稳定标识、provenance 与 unknown/不足的显式状态；一个请求只固定一个 release_id。
- 比较、规则查询等是对通用 Claim/Relation 的查询组合，不在平台写险种逻辑。

### 7.11 反馈飞轮与治理工作台

```text
信号：Agent 证据不足 · 用户纠错 · 专家标错 · 低置信 · Lint（孤立/断链/过期/冲突/缺口）
      · 来源变更 · ACL 收缩 · 模型或模板升级后的评测回归
  → WeKnora platform/feedback 记录（绑定 release_id 与被引用成员）→ event
  → Harness governance：去重归并为 ReviewItem 或 GapTask
  → GapTask：定向检索本实体/版本已有材料，只补抽缺失字段及其条件，保留历史尝试；
             相似产品只提示缺口，不提供替代证据；无证据保持 unknown
  → 新 Candidate → 正常审核与发布（从不直接改 Active）
```

- 回答日志：知识服务接口记录每次回答使用的 release_id 与成员，用于定位"答错了哪条知识"。
- 工作台（复用 WeKnora 审核台）：按实体/知识域展示覆盖率、unknown 及原因、冲突、重复、待审 ReviewItem 与 GapTask 进度；专家据此看到知识全貌。

### 7.12 访问控制、保留与清除

- 每个成员携带由其 Evidence 来源推导的 `access_scope`；页面、检索、Agent、知识服务接口按调用者当前 ACL 过滤，读时校验。
- ACL 收缩：受影响成员立即对无权主体不可见（fail closed），并生成 ReviewItem 重新举证或降敏；同一事实能被低敏来源独立证明时才可降敏发布。
- 首期实现来源撤回与 ACL 收缩。保留期与法律清除按公司合规要求另行设计；合同上只预留一点：历史 Release 中被清除的来源可标记为不可服务，避免通过回滚或 pinned 读取重新暴露。

### 7.13 规模与成本

- 编译只由变化驱动（新 revision、配置版本、反馈）；成本随新增量与影响闭包增长。
- 任务按实体分区、micro-batch、有界并发，共享供应商配额；预算、速率和容量来自版本化 CapacityProfile，不写死为产品上限。
- Release 成员按内容寻址（D17），激活只切 Head；检索索引按 Release 增量构建。
- 历史 chunk 与零散片段先做去重与归属（实体、材料角色），无法归属的进入隔离池，不进入正式知识。

沿用已在 `insurance-agent-harness` 验证的方式：用户决策；Claude 负责调研、架构、切片 Spec、验收测试、架构守卫与审计；Codex 与 V5 同学负责实现，按同一流程领取 Issue。同一时间只有一个实现切片修改同一组件的运行时代码；不同组件、CI/部署切片在写域不重叠时可并行。

| 步骤 | 谁 | 做什么 |
|---|---|---|
| 1 | Claude | 写 Spec（`docs/design/slices/SN-*.md`）与验收测试（`tests/acceptance/sN/` 或组件内对应目录），推到 `slice/sN`，按 `.github/ISSUE_TEMPLATE/slice.md` 开 Issue，写明开工方式与真实调用预算 |
| 2 | 用户 → Codex | "做 issue #N"（交给 Codex 即视为批准） |
| 3 | Codex | 在 Issue 下复述目标、范围、完成标准并列计划；小切片写完即开工，大切片等确认 |
| 4 | Codex | 在 `slice/sN` 实现，本地过门禁，rebase 到最新 `main`，开 PR（`Closes #N`），按 PR 模板交接 |
| 5 | Claude | 定时检查 GitHub；拉取 PR 分支本地重跑验收、守卫与相关门禁，检查 diff 范围，`gh pr review` 给出批准或编号修改项 |
| 6 | 用户 → Codex | 有修改项时"按 PR #M 的审计意见修改" |
| 7 | 用户 | Squash merge，`main` 上一个切片一个提交 |

- **受保护路径**（Codex 不改）：`docs/design/`、`tests/acceptance/`、`tests/architecture/`（基线只在数字下降时经脚本更新）、`contracts/`（由 pydantic 导出生成，Spec 规定变更时除外）。
- **仓库**：Issue/PR 在私有仓库 `PA-ALG/InsuranceKB-WeKnora-private` 进行；旧公开仓库只保留历史 PR。
- **门禁**：新仓库的 Actions 暂时关闭（免费组织私有仓库分钟数有限，且现有工作流依赖旧仓库的 secrets 与发布目标）；S0 精简 CI 后再启用。启用前以本地门禁为准，Claude 审计时在本地重跑受影响组件——Go 受影响包 `go test`；Harness `uv run pytest`、`ruff check`、`mypy`；前端 `type-check`、测试、`build`。
- **证据**：commit SHA + 测试/评测报告摘要写在 PR 中。真实调用原始输出存仓库外的私有位置，PR 只写摘要与位置；不做逐文件哈希清单，不向仓库提交日志与大体量回执。
- **真实调用与部署**：每个 Issue 写明"场景数 + 发送上限 + 模型"，批准 Issue 即授权该预算。部署、数据库迁移与环境变更单独开 Issue，附回滚方式。
- **署名**：共用账号时，Issue/PR 评论、review、PR 描述第一行写 `**[by Claude Code]**` 或 `**[by Codex]**`。
- **状态入口**：当前进度看 GitHub Issue/PR 与本文 §11；`HANDOFF.md` 冻结为历史，不再追加状态块。
