# 保险知识编译：产品使用反馈补充待办

> **历史输入，已被合并**：当前唯一主 backlog 是 [2026-07-insurance-knowledge-compiler-master-plan.md](2026-07-insurance-knowledge-compiler-master-plan.md)，最高产品/架构口径是 [Enterprise LLM Wiki 北极星设计](../superpowers/specs/2026-07-21-enterprise-llm-wiki-north-star-design.md)。本文件保留原始反馈追溯；出现“自动发布”时一律按“低风险候选可自动推进，但每个生产 ReleaseSnapshot 仍须 Space 授权人最终批准”解释。

## 结论与优先级调整

深度使用反馈表明，当前最高风险不是图谱展示或 Deep Research，而是“输入材料能否可靠归属到正确产品、以何种规则合并、是否可以追溯和回滚”。

因此调整优先级如下：

1. **P0：产品主数据对齐、结构化知识快速接入、事实级合并与版本门禁。**
2. **P0.5：高吞吐批处理、并发安全和冲突工作台。**
3. **P1：产品知识仪表盘、完整度和 Schema 管理。**
4. **P2：智能文档分类与多产品材料的深度编译优化。**
5. **P3：PPTX、音视频和高级多模态能力。**

本清单补充并细化 `2026-07-insurance-knowledge-compiler.md`；如有冲突，以本文件的优先级为准。

## 对当前能力的判断

当前 WeKnora 已有 Wiki ingest 队列、页面级来源引用、增量去重/删除收敛、Wiki 页面链接图、页面问题和前端 Wiki 浏览器。标准 Redis 模式的 `wiki_ingest` 已可让同一知识库并发批次通过“待处理行认领 + 单 slug 锁”运行，Lite 模式仍按 KB 串行。它是良好的任务基础，但没有“产品实体级路由、事实级 merge、批次 commit 与冲突裁决”能力。

`docreader` 已有 PPTX/图片的解析及媒体提取辅助，但其边界是解析；音视频转写、语义分段和产品知识编译不能直接当作已完成能力。

## P0：先让知识正确进入正确的产品

### P0-1 产品主数据与实体解析门禁

**要解决的问题**

- 一份材料可能涉及多个产品；当前不能可靠地将每条知识落入正确产品。
- 产品名存在简称、停售版本、别名、内部代码和相似名称。

**数据模型与迁移**

- [ ] 新增 `insurance_products`：`product_id`、公司/租户、标准名称、产品代码、险种、状态、有效期、当前发布版本。
- [ ] 新增 `product_aliases`：别名、简称、历史名称、内部编码和归一化规则。
- [ ] 新增 `product_documents`：一个文档可关联多个产品，保存候选分数、对齐方式、审核状态。
- [ ] 在 `wiki_claims` 中增加 `subject_entity_id`、`product_id`、`product_version_id`、`routing_confidence`。
- [ ] 禁止“无法确定产品”的 claim 自动写入具体产品；写入 `unassigned` 候选池，待自动或人工归属。

**Python knowledge-compiler**

- [ ] 新增 `ResolveProducts` 阶段：规则（产品代码、统一名称）优先，向量召回和 LLM 判别仅用于候选排序。
- [ ] 为每个 claim 输出 `product_candidates[]`，包括实体 ID、证据、分数、判别原因；支持一对多归属。
- [ ] 新增跨产品拆分器：先按章节、表格、标题和产品锚点切分，再对段落/事实做产品对齐；不得以整篇文档只绑定一个产品为默认策略。
- [ ] 定义低置信阈值和同分阈值，命中时产生 `product_routing_review`，不得自动推进候选。

**Go 接入**

- [ ] 在 `wiki_compilation.go` 的持久化前执行产品目录/别名校验，防止模型返回不存在或跨租户的产品 ID。
- [ ] 产品路由结果决定 Wiki 路径，例如 `products/{product-code}/{version}/coverage/...`；路径只是展示层，实体 ID 才是唯一归属。
- [ ] 新增产品归属审核 API，复用 KB RBAC 和审计日志。

**前端**

- [ ] 在上传批次详情显示“识别到的产品、未归属事实、低置信归属和跨产品内容”。
- [ ] 提供候选产品确认、拆分/合并和禁止自动归属操作。

**验收**

- 一份涉及 A、B 两款产品的材料可把不同责任、豁免和 FAQ 分别写入 A/B，且每条记录带证据。
- 无法可靠判断的内容不会污染任何产品 Wiki。

### P0-2 结构化知识快速接入（JSON/FAQ/产品库）

**原则**

结构化来源不应走 PDF/Office 文档解析，也不应被转换为单个大文本再让模型重抽取。应采用“Schema 映射 -> 规范化事实 -> 差异合并”的快速路径；LLM 仅处理字段映射不确定、自由文本补充和实体对齐。

**Python knowledge-compiler**

- [ ] 新增 `StructuredImport` RPC，输入 JSON、JSONL、CSV 或 FAQ 数据及映射配置，输出规范化 `Product/Claim/QA` 批次。
- [ ] 内置保险产品、保障责任、费率/保额规则、除外责任、监管规则和 FAQ 映射器。
- [ ] 对不符合模板的 JSON 先推断候选 Schema/映射草案，再由用户确认；不得直接假定字段语义。
- [ ] 建立字段值规范化：日期、年龄区间、金额、百分比、疾病编码、产品代码、枚举值。

**Go 接入**

- [ ] 新增结构化导入任务类型与对象存储上传入口；跳过 docreader，直接调用 Compiler。
- [ ] 为外部系统记录 `source_system`、`external_record_id`、`source_revision`、幂等键；重复推送只能更新同一事实链，不可创建重复页面。
- [ ] 新增导入预检 API：返回记录数、产品匹配率、字段缺失、待确认映射、预计新增/更新/冲突数。
- [ ] 支持 API 推送、文件导入和 datasource connector 三种入口，但三者归一到同一批次模型。

**前端**

- [ ] 新增“结构化知识导入”入口：选择文件/API、映射预览、校验报告、dry-run、确认提交。
- [ ] 支持保存和复用导入映射模板。

**验收**

- 10 万条结构化 FAQ/产品记录无需 docreader 解析，可幂等导入并在预检中显示产品匹配与冲突统计。

### P0-3 非显式字段抽取：以事实候选而非字段缺失结束

**问题**

例如“豁免”经常不出现在标题或固定字段中，可能出现在责任描述、附加条款、表格脚注或反向表述里；依赖字段名的提取会漏失。

**待办**

- [ ] Python 对每个必填领域字段定义“证据模式”：同义词、否定表达、规则模式、上下文窗口和表格列组合。
- [ ] 模型必须返回 `present`、`absent_explicitly`、`unknown` 三态；不得把“未抽到”解释为“不存在”。
- [ ] 当字段为 `unknown` 时生成可定位的缺口任务，而不是生成空字段。
- [ ] 对豁免、等待期、除外责任、理赔限制等高风险字段采用二次抽取/验证提示词，并要求证据片段。
- [ ] 建立字段级 precision/recall 金标准测试集，作为发布门槛。

## P0：更新、版本、删除与回滚

### P0-4 基于来源权威度、发布时间和完整度的合并策略

**合并规则**

同一产品实体的新材料不应直接覆盖旧知识。系统应比较“同一主语 + 属性/关系 + 适用版本”的 claim，再决定新增、补充、替换、冲突或撤销。

建议优先序：正式条款/监管文件 > 已批准产品说明/FAQ > 内部流程资料 > 培训材料 > 销售材料 > 外部研究。相同权威度时，先比较适用期间和来源发布时间；完整度只能作为候选排序因素，不能取代权威度。

**Python**

- [ ] 扩展 `CompareRevision`：按 canonical entity/property/product version 对比，输出 `add`、`enrich`、`supersede`、`conflict`、`retract`。
- [ ] 为每个决定返回原因、比较证据、权威度、发布时间、完整度和置信度。

**Go**

- [ ] 新增 `knowledge_change_sets`、`knowledge_change_items`、`knowledge_conflicts` 和 `knowledge_version_snapshots`。
- [ ] 每批导入先生成不可变 change set，按策略自动应用低风险项，将冲突和高风险替换转审核。
- [ ] 发布时把相关 Wiki 页、事实、QA 和图谱边作为同一逻辑版本提交；支持按 batch/version 回滚。
- [ ] 删除来源时按证据引用计数撤销/降级事实，不直接删除仍被其他权威来源支持的知识。
- [ ] 变更日志至少显示：谁/哪个系统、何时、哪条来源、变更前后、合并决策、审核决定和回滚批次。

**前端**

- [ ] 新增产品级 Change Log、变更集详情、差异对比与版本回滚确认页。
- [ ] 在 Wiki 页显示“当前版本、历史版本、有效期、来源变更”。

**验收**

- 第二、三批资料能补齐第一批未知字段；发生矛盾时创建冲突而不静默覆盖；回滚一个批次后，Wiki、事实、QA 和索引回到一致状态。

## P0.5：大批量并发加工与一致性

### P0.5-1 面向产品的分片、归并和限流

现有 Wiki 队列已经处理文档级并发与 slug 锁。新增设计不能破坏该机制，应增加产品级聚合层：文档可并行解析/抽取，同一产品版本的事实 merge 则必须串行或使用乐观并发控制。

**待办**

- [ ] 以 `tenant + knowledge_base + product_id + product_version` 作为 merge 分片键；不同分片可并发。
- [ ] 在 Python 侧支持批量抽取、微批请求、模型限流、指数重试和失败隔离。
- [ ] Go 侧用 task pending ops 保存每文档处理状态；复用 asynq 标准模式和 Lite sync executor，不新增不兼容队列。
- [ ] 为同一分片引入 change-set 版本号/乐观锁；过期 worker 结果重新比较，不允许覆盖较新提交。
- [ ] 设置并发上限：全局、租户、KB、产品和模型 provider 五层；显示排队原因。
- [ ] 实现死信重放，但重放必须使用原始 schema/model/version 和来源快照。
- [ ] 采用两阶段处理：并行 extract -> 按产品分片 merge -> 批次 finalize/index；避免每份材料都重建全局索引。

**前端**

- [ ] 批次控制台展示总量、吞吐、分片、重试、冲突、待审核和死信；支持取消未开始任务与受控重试。

**验收**

- 千份混合材料导入时，不同产品可并行；同一产品不丢更新；失败文档不阻塞其他产品；前端可定位每一条失败/冲突。

## P1：产品知识仪表盘与 Schema 工作台

### P1-1 产品知识全貌与完整度

**核心设计**

完整度不应只看“字段是否非空”。按产品/版本/险种 Schema 的必填、条件必填、未知、冲突、过期、无证据和未审核状态计算。

**后端**

- [ ] 新增 `ProductKnowledgeOverviewService`，汇总产品、版本、实体、事实、QA、冲突、缺口与证据健康度。
- [ ] 新增 `knowledge_completeness_snapshots`，异步计算并缓存评分，避免仪表盘实时全表扫描。
- [ ] 定义质量分：字段覆盖、来源权威度、证据完整度、版本新鲜度、冲突扣分、审核状态和 Wiki 链接健康度。
- [ ] 对每个缺口生成可执行建议：补充已有材料、指定材料重编、发起研究或人工确认“不适用”。

**前端**

- [ ] 支持按产品、版本、险种、状态筛选，展示知识全貌树、字段矩阵、质量分、缺口、冲突、来源和变更趋势。

### P1-2 Schema 与提取提示词工作台

- [ ] 新增 `knowledge_schemas`、`knowledge_schema_versions`、`extraction_profiles`，Schema/提示词须版本化且可回滚。
- [ ] 前端提供 JSON Schema 或表单式编辑、字段类型、同义词、必填条件、示例、证据要求、风险等级和预览。
- [ ] 根据“知识背景介绍 + 样本文档 + 产品线”由 Python 生成 Schema/提示词草案；必须人工确认后才能用于正式批次。
- [ ] 提供 dry-run：展示将抽取哪些字段、漏项、成本和与现有 Schema 的差异。
- [ ] Schema 变更不能隐式重写已发布知识；必须创建再编译计划和影响范围报告。

## P1：QA 的正确建模

不建议将 QA 仅作为产品/服务主实体中的一个非结构化 `qa` 字段。这样会丧失多来源、版本、审核、检索和复用能力。

建议新增一等对象 `knowledge_qa_items`：

- [ ] 字段：`question`、`normalized_intent`、`answer_claim_ids[]`、`subject_entity_ids[]`、`product_id`、`product_version_id`、`effective_range`、`source_refs`、`status`、`quality_score`。
- [ ] 一个 QA 可关联多个产品/服务/实体；产品页面只聚合显示其相关 QA。
- [ ] Python 从 FAQ、条款和服务资料提取候选 QA，去重并与已有 QA 对齐；答案必须引用 claims，不能只保存模型生成文本。
- [ ] Go 在 RAG/Agent 中将 QA 作为高精度候选，仍执行版本、权限、审核和证据过滤。
- [ ] 前端新增 QA 列表、相似问题合并、答案差异、来源和审核操作。

## P2：智能文档分类与编译路由优化

### P2-1 分类与险种处理配置

- [ ] Python 先判定文档类型：条款、产品说明书、FAQ、理赔、核保、监管、培训、营销、案例、音视频转写等。

- [ ] 前端在上传前/后显示分类和选择的处理逻辑，允许有权限用户覆盖，但保留原始判定和理由。

### P2-2 多产品文档的精度评估

- [ ] 建立“单文档多产品”标注集，分别测试文档分类、产品归属、字段抽取和跨产品污染率。

- [ ] 核验并补足 docreader 对 PPTX 的标题层级、备注、表格、讲稿、图片/OLE 对象和跨页上下文提取。

## 上线门槛

- 任何低风险候选自动推进必须通过产品归属、版本有效期、来源权威度、证据存在和 Schema 校验五个门禁；进入生产还必须由 Space 授权人批准绑定完整制品 hash 的 ReleaseSnapshot。
- 结构化导入必须支持 dry-run、幂等键、change set 和回滚后才允许接入生产产品库。
- 对同一产品的并发 merge 必须有乐观锁或等价串行化保证，并通过故障重试测试。
- 仪表盘质量分必须可解释至字段、来源和证据，不能作为黑盒分数。
